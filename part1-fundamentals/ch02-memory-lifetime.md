# 第2章 C++ 内存与生命周期

> 资深服务端工程师对"内存"的理解，不在 new/delete 的语法，而在**对象在内存里的真实布局、一次分配的真实代价、cache 与 CPU 的交互，以及对象生命周期的确定性**。这一章把"对象怎么放、怎么分、怎么活得久、怎么死得干净"讲透——它是性能优化与线上故障排查的底层地基。

## 原理体系

### 1. 对象内存布局与虚函数表

一个 C++ 对象在内存里是什么样子，取决于它的特性：

- **POD / 平凡类型**：就是成员的平铺，无额外开销。
- **含虚函数的类**：对象首部（绝大多数实现）多一个指针 **vptr**，指向该类的 **vtable**（虚函数表）。
- **有虚基类**：还会有虚基类指针/偏移信息（见第 2 节）。

**vtable 是 per-class 的**（每个多态类一张，存在只读数据段）；**vptr 是 per-object 的**（每个对象首部存一个 vptr，指向其动态类型对应的 vtable）。构造时，编译器在基类构造函数里把 vptr 设为基类 vtable，派生类构造函数再把它改指派生类 vtable——这正是"基类构造期间虚调用只调基类版本"的底层原因（见第 1 章 RAII 节）。

**虚调用的代价**：一次虚函数调用 = 经 vptr 间接读 vtable 项 + 间接跳转。两次内存访问，且目标地址运行期才知道，CPU 分支预测可能失败、阻碍内联。游戏里"每帧/每 tick 大量调用"的热点路径应避免虚函数，改用模板/CRTP（静态分发）或手动函数指针表。

### 2. 多重继承与虚继承布局

单继承下，派生类对象 = 基类子对象 + 派生新增成员，一个 vptr。**多重继承**下，对象里有**多个基类子对象**，每个含虚函数的基类子对象各带一个 vptr；`static_cast<Base*>(d)` 可能要做指针偏移调整。`dynamic_cast` 沿继承图搜索，开销更大。

**虚继承**解决菱形继承（D 继承 B、C，B/C 都虚继承 A）下 A 子对象被复制两份的问题：虚继承下 A 只存一份，但代价是 B/C 子对象里要存**虚基类指针/偏移（vbptr / vbtable）**来定位那个共享的 A。访问虚基类成员要经 vbptr 多一次间接——更慢、布局更复杂。游戏服务端几乎不用虚继承，通常用**组合替代继承**来规避。

### 3. 内存对齐与 padding

CPU 按字长（x86-64 上 8 字节）对齐访问内存最快；未对齐访问在某些架构直接异常，x86 上能跑但慢，跨 cache line 时要两次访问。所以编译器给结构体插入 **padding**，让每个成员落在其自然对齐（通常 = 成员大小）上，结构体整体大小是其最严对齐成员的整数倍。

```cpp
struct Bad {        // 浪费
    char a;         // 1B + 7B padding
    double b;       // 8B
    char c;         // 1B + 7B padding
};                  // sizeof = 24
struct Good {       // 紧凑：大对齐放前，小的聚拢
    double b;       // 8B
    char a, c;      // 2B + 6B padding
};                  // sizeof = 16
```

**把大对齐成员放前面、小的聚拢在后**能省一半内存——这是热数据结构的基本功。`#pragma pack(n)`、`alignas(N)` 可强制改变对齐（慎用：跨平台 ABI 不一致、可能触发未对齐慢路径）。跨进程/跨平台传输的二进制结构尤其要警惕对齐与字节序（设计 `__attribute__((packed))` 时常伴随未对齐访问的性能陷阱）。

### 4. 堆分配的代价：new / malloc 到底在做什么

`new T` 通常 → `operator new` → `malloc` → 向 OS/分配器请求内存。一次堆分配的代价：

- **找空闲块**：分配器（ptmalloc / tcmalloc / jemalloc）维护空闲链表/size-class 桶，要查找，多线程下还要加锁。
- **系统调用**：不够时 `brk` / `mmap` 向 OS 要页，用户态↔内核态切换，昂贵。
- **元数据 + 取整**：每块要存大小/边界标记，且按 16/32 字节对齐取整 → 内部碎片。
- **外部碎片**：频繁 alloc/free 后空闲块不连续，凑不出大块，RSS 居高不下。
- **锁竞争**：ptmalloc 的 arena 锁是多线程热点；tcmalloc/jemalloc 用 thread-local cache 缓解。

游戏服务端每 tick 可能分配成千上万个小对象（消息、事件、临时实体），通用堆分配是性能黑洞——所以才需要对象池与 arena。

### 5. 内存池与 arena 分配器

**arena（monotonic allocator，单调递增分配器）**：预分配一大块，分配时只移动一个游标指针（bump pointer），O(1)、无碎片、无锁。代价：**不支持单个释放，只能整批 reset**。非常适合"一帧/一次请求内分配、用完整体丢弃"的临时对象。

```cpp
struct Arena {
    char* base; std::size_t cap, off = 0;
    template<class T> T* alloc() {
        std::size_t a = (off + alignof(T) - 1) & ~(alignof(T) - 1);  // 对齐
        if (a + sizeof(T) > cap) throw std::bad_alloc();
        T* p = reinterpret_cast<T*>(base + a);
        off = a + sizeof(T);
        return new (p) T();        // placement new，原地构造
    }
    void reset() { off = 0; }      // 整批丢弃；不会调用任何析构！
};
```

注意 `reset()` 不调用析构——所以 arena 适合 POD 或"不持有需析构资源"的对象；带析构语义的对象要显式管理生命周期，否则资源泄漏。

**对象池（object pool）**：固定大小对象的预分配数组 + 空闲链表。分配/回收 O(1)、无堆分配、数据局部性好（对象密集存放）。游戏实体、网络消息、粒子等常驻对象池；回收的对象复用，避免反复 new/delete 的开销与碎片。

### 6. cache 友好的数据布局：SoA vs AoS

CPU 访问内存按 **cache line**（通常 64 字节）整条载入。访问一个字段，整条 line 进缓存，相邻字段"免费"。所以**数据局部性**是性能关键。

- **AoS（Array of Structs）**：`struct Entity{ Vec3 pos; Vec3 vel; int hp; ... } ents[N];`。遍历只读 hp 时，每个 Entity 的 pos/vel 也被载入 cache → 浪费带宽。
- **SoA（Struct of Arrays）**：`hp[N]`、`pos[N]`、`vel[N]` 分开。只读 hp 时连续载入 N 个 hp，cache 利用率拉满。

ECS（Entity-Component-System）架构的核心就是 SoA + 按组件连续存储 + 按系统批量处理，让数据布局匹配访问模式。游戏里"按某属性批量处理所有实体"的路径（战斗每帧算伤害、AOI 更新位置、广播视野），SoA 常带来数倍提升。代价：单实体跨多属性访问不连续（可用 AoSoA / 分块折中）。

### 7. false sharing（伪共享）与 cache line 对齐

两个线程各写**不同**变量，但两个变量落在**同一条 cache line** 上 → **false sharing**。缓存一致性协议（MESI）让这条 line 在两个核间反复 invalidate/同步，写操作被串行化，性能暴跌——即使两个线程逻辑上毫无共享。

```cpp
struct Counter {
    long a, b;            // a、b 同一条 64B cache line → false sharing
};
// 线程1 疯狂 ++a、线程2 疯狂 ++b → 慢得像单线程

struct Counter {
    alignas(64) long a;   // 各自独占一条 cache line（C++17 可用 std::hardware_destructive_interference_size）
    alignas(64) long b;
};
```

修复：用 `alignas(64)` 让并发写的字段各占一条 cache line。这是多线程性能题的高频考点，也是无锁结构常踩的坑。

### 8. 内存泄漏、内存增长与检测

泄漏 = 分配了不再可达、却不释放。C++ 无 GC，泄漏全靠纪律 + 工具：

- **ASan（AddressSanitizer）**：编译期插桩，运行期检测 use-after-free、heap-overflow、leak（退出时报告仍可达的堆块）。开销约 2x，CI/压测必开。
- **valgrind/memcheck**：无源码插桩，运行期解释执行检测，开销大（10–50x），定位细但慢。
- **自建分配追踪**：重载 `operator new` 记录分配点（文件:行 → 指针），周期性 dump 未释放项——游戏服务端常自建轻量版。

关键认知：**"内存增长（RSS 上涨）"不一定是泄漏**。还可能是：内存碎片（malloc 可用率下降）、arena 长期不 reset、`weak_ptr` 持留导致 `make_shared` 单块不释放（见第 1 章）、容器只增不减、缓存无淘汰策略。定位时先区分这几种，别一上来就找"哪里忘了 delete"。

### 9. 对象生命周期与对象池设计

游戏高频对象（Entity / Message / Event / Timer）的生命周期管理是服务端核心工程问题：

- **谁拥有、谁释放**：明确所有权（unique_ptr 独占 / shared_ptr 共享 / 池统一管理）。
- **悬垂引用**：对象被池回收复用后，外部若仍持有旧指针 → 访问到"新对象"或已重置数据。解法：**代际 ID**（generation counter）= 索引 + 版本号，对象回收时版本号递增，旧引用校验版本号失败即视为失效（见下文章节题）。
- **池满策略**：扩容、阻塞等待、或拒绝（丢消息 + 计数告警）。游戏消息常"丢弃 + 告警"。
- **热/冷数据分离**：每帧访问的字段（位置、状态）密集存放（热），不常访问的（背包、社交关系）分开（冷），提升 cache 命中。
- **构造/析构成本**：池对象复用时不反复构造析构，用 placement new 重建 + 显式析构。

## 面试题

### 【专家】深挖追问 · 对象内存布局与虚调用机制

> 一个含虚函数的类 `class A{ virtual void f(); int x; };`，`sizeof(A)` 在 64 位下通常是多少？为什么？虚调用在底层是如何发生的？

**参考思路**：通常 16 字节——一个 vptr（8B）+ int x（4B）+ 4B padding（对齐到 8）。vptr 在对象首部，指向 per-class 的 vtable（存在只读数据段）。虚调用 `pa->f()` 编译为：读 `pa` 处的 vptr → 得到 vtable 地址 → 按 f 在 vtable 中的偏移读出函数指针 → 间接调用。两次内存间接，目标运行期才确定，所以难内联、可能预测失败。

**考点解析**：vptr per-object、vtable per-class；虚调用的真实代价（间接 + 预测）；64 位指针 8B 与对齐。资深要能从对象布局一路讲到性能影响。

**常见误区**：以为虚函数本身占对象空间（不占，是 vptr 占）；以为 vtable 每对象一份（是每类一份）；忽略对齐 padding。

**追问方向**：
1. 构造期间 vptr 指向哪？（基类构造时指基类 vtable，派生构造改指派生 vtable → 基类构造期虚调用只调基类版本。）
2. 析构期间呢？（逆序：派生析构时 vptr 仍指向派生 vtable，故派生析构体里的虚调用正确分派到派生类；派生析构结束后进入基类析构时编译器才把 vptr 改指基类 vtable，与构造过程严格逆序。）
3. 热点路径如何去掉虚调用？（CRTP/模板静态分发、函数指针表、或把多态数据 SoA 化后按类型批量处理。）

### 【进阶】原理辨析 · 虚继承与菱形布局

> 菱形继承 `D: B, C`，`B: virtual A`，`C: virtual A`。D 的对象里 A 子对象有几份？虚继承为此引入了什么、代价是什么？

**参考思路**：虚继承下 A 子对象只有**一份**（共享）。代价：B、C 子对象各引入 **vbptr/vbtable**（虚基类指针/表）记录到共享 A 的偏移，访问 A 的成员要经 vbptr 多一次间接，更慢、布局更复杂。非虚继承下 A 会有两份，访问无歧义但浪费且语义混乱。

**考点解析**：虚继承解决的问题（重复基类）与代价（间接访问 + 布局复杂）。资深要知道为什么游戏服务端几乎不用虚继承（慢 + 难维护），改用组合。

**常见误区**：以为虚继承免费；不知道 vbptr 的存在；混淆虚继承与虚函数。

**追问方向**：游戏里要复用 A 的能力，更推荐怎么做？（组合持有 A 的实例，或提取为独立组件。）

### 【专家】深挖追问 · 内存对齐的工程影响

> 为什么要有内存对齐？下面两个结构体 sizeof 各是多少？设计一个跨进程传输的二进制协议头要注意什么？
> ```cpp
> struct S1 { char c; int i; short s; };
> struct S2 { int i; short s; char c; };
> ```

**参考思路**：对齐源于 CPU 访问机制（按字对齐一次取，未对齐要跨 line 或异常）与硬件原子性。S1：c(1)+3pad+i(4)+s(2)+2pad = 12；S2：i(4)+s(2)+c(1)+1pad = 8。重排成员（大对齐在前）能省内存。跨进程/跨平台二进制协议头要**显式控制布局**：要么 `#pragma pack(1)` 省空间但接受未对齐代价（适合带宽极敏感的纯收发，触发未对齐慢路径甚至某些平台原子操作失效），要么显式 padding 保证对齐后再用定宽类型——并统一字节序（网络序大端）、用定宽类型（`uint32_t` 而非 `int`/`long`）、版本化。注意跨进程结构直接 memcpy 本身就有 ABI/字节序风险，更稳妥的是显式序列化（serialize 到对齐 buffer）。

**考点解析**：对齐的根因、padding 计算、紧凑布局技巧、跨平台 ABI 风险。资深要能算 sizeof 并讲清 packed 的性能陷阱。

**常见误区**：忽略 padding；以为 packed 是纯收益（它会触发未对齐访问慢路径，甚至某些原子操作失效）；跨平台用 `long`（宽度不定）。

**追问方向**：`#pragma pack(1)` 后，对一个 `int` 字段的原子读还安全吗？（未对齐的原子操作在某些平台/指令上不保证，可能撕裂或退化。）

### 【进阶】权衡 · 游戏服务端高频小对象为什么不能直接 new

> 每帧要创建/销毁数万个临时小对象（消息、事件）。为什么直接 `new`/`delete` 是性能黑洞？malloc 的开销来自哪里？

**参考思路**：单次 malloc 的开销 = 查空闲块 + 可能的系统调用（brk/mmap）+ 元数据取整 + 多线程锁竞争。高频小对象下，这些开销叠加成主线程瓶颈，还会产生外部碎片使 RSS 节节攀升。游戏服务端的解法是 arena（同生命周期批量分配、整体 reset）或对象池（固定大小、空闲链表、O(1) 无锁/低争用）。

**考点解析**：malloc 的真实代价（不是 O(1) 免费）；碎片；为什么游戏需要自定义分配策略。资深要能讲清分配器的 size-class/arena/thread-cache 机制。

**常见误区**：以为 new 是常数时间无开销；忽略锁竞争与碎片；不知道 tcmalloc/jemalloc 为何更快（thread-local cache + size-class）。

**追问方向**：换了 jemalloc 还要不要对象池？（要——jemalloc 降低了通用堆开销，但 arena/池还能消除分配本身、提升局部性、控制生命周期，收益叠加。）

### 【专家】系统设计 · 设计一个 arena 分配器

> 为"单帧内的大量临时对象"设计一个 arena 分配器。它怎么分配、怎么回收？有什么必须注意的正确性问题？

**参考思路**：预分配大块（如 1MB），分配时 bump pointer 推进并按 alignof(T) 对齐，O(1) 无锁；帧末整体 reset（off 归零）。正确性要点：① **reset 不调用析构**，所以只适合 POD 或无析构资源的对象——持 std::string/vector 等会泄漏；② 越界保护（cap 检查）；③ 跨线程用要加锁或每线程一个 arena；④ 大对象不要进 arena（浪费且难管理）。可演进为"带析构登记表"的 arena（记录需析构对象，reset 时逆序析构）以支持非平凡对象。

**考点解析**：bump allocator 原理、O(1) 分配的代价（牺牲单释放）、析构语义的正确处理。资深要主动指出"reset 不析构"这个坑。

**常见误区**：把带析构的对象塞进 arena 却不析构 → 资源泄漏；忘记对齐；线程不安全却跨线程用。

**追问方向**：
1. 如果临时对象里有 `std::string` 怎么办？（arena 记录析构函数指针表，reset 时逆序调用；或限制只用 string_view 指向 arena 内部。）
2. arena 一直不 reset 会怎样？（内存不回收，等同泄漏——所以要确保生命周期边界清晰。）
3. 为什么不直接用 C++17 的 `std::pmr::monotonic_buffer_resource` + `std::pmr::vector`？（PMR 正是标准化的同款机制：`monotonic_buffer_resource` 就是 bump allocator，配合 `std::pmr::polymorphic_allocator` 可让容器内的分配自动落到 arena 上——比自己手写更标准、能直接复用标准容器。手写版的意义在于完全可控的内存来源与无虚调用开销。）

### 【进阶】原理辨析 · SoA vs AoS 与 ECS

> 什么是 SoA 和 AoS？为什么 ECS 架构推崇 SoA + 连续存储？给一个游戏里受益的具体场景。

**参考思路**：AoS 把对象的所有字段聚在一起连续存（`Entity[N]`），SoA 把每个字段分开连续存（`pos[N]`、`hp[N]`）。CPU 按 cache line 载入，AoS 遍历单字段时把无关字段也载入，浪费带宽；SoA 只载入需要的字段，cache 命中率最高。ECS 把每个 Component 按 SoA 连续存储，System 按组件批量处理，数据布局匹配访问模式。受益场景：战斗系统每帧遍历所有实体的 hp 算伤害（只读 hp）、AOI 每帧更新所有 position（只读/写 pos）——SoA 让这些"窄遍历"极速。

**考点解析**：cache line、数据局部性、数据导向设计（DOD）。资深要能讲清"为什么内存访问模式比算法复杂度更决定性能"。

**常见误区**：以为 SoA 总是更好（单实体跨多字段访问时不连续，需 AoSoA 折中）；忽略 cache line 大小。

**追问方向**：单实体频繁访问自己的 pos+hp+vel 多个字段，SoA 反而慢，怎么折中？（AoSoA：每 16/32 个实体为一个 AoS 块，块间 SoA。）

### 【专家】深挖追问 · false sharing 的定位与修复

> 线程 1 疯狂 `++a`、线程 2 疯狂 `++b`，两者互不相关，但多线程跑下来比单线程还慢。怎么回事？怎么修？

**参考思路**：典型 **false sharing**——a、b 虽逻辑无关，但落在同一条 64B cache line 上。缓存一致性协议（MESI）让这条 line 在两核间反复 invalidate/迁移，写操作被迫串行化，反而比单线程慢。修复：用 `alignas(64)`（或 C++17 `std::hardware_destructive_interference_size`）让并发写的字段各占一条 cache line；或在并发计数器间填充 padding。

**考点解析**：cache line、MESI、伪共享的机理与症状（多线程比单线程慢）。资深要能在性能分析时主动怀疑 false sharing。

**常见误区**：只看逻辑无关就以为无竞争；不知道 cache line 这一硬件层；误用粗锁掩盖了伪共享却没解决。

**追问方向**：
1. 怎么用工具定位？（perf c2c、或观察多线程 scaling 反常——核数增加性能反降。）
2. 反过来，**构造性局部性（constructive interference）**——同一线程热点访问的多个变量希望落在同一条 cache line 上，对应 `std::hardware_constructive_interference_size`。destructive（避免 false sharing）与 constructive（提升局部性）如何取舍？

### 【专家】故障复盘 · 线上 RSS 持续增长但查不到泄漏

> 服务上线后 RSS 缓慢持续上涨，ASan/valgrind 都没报泄漏。可能是什么原因？怎么排查？

**参考思路**："内存增长 ≠ 泄漏"。排查方向：① **内存碎片**——频繁 alloc/free 后空闲块不连续，malloc 拿不回还给 OS，RSS 居高（`malloc_trim`、换 jemalloc 验证）；② **arena 未 reset**——某段代码的 arena 生命周期边界错了，一直累积；③ **`make_shared` + 长期 weak_ptr**——对象析构了但整块内存（含对象本体）因 weak 持留不释放；④ **容器只增不减**——cache/map 只插不删，或删了不 shrink；⑤ **缓存无淘汰**——LRU 没生效或上限设太大；⑥ **内存池预分配过大**。手段：`pmap`/`/proc/<pid>/smaps` 看 RSS 构成、`malloc_trim(0)` 试探、换分配器对比、给关键容器加大小监控、jemalloc 的 `malloc_stats_print`。

**考点解析**：区分"泄漏"与"高水位/碎片/持留"。资深不会上来就找 delete，而是先定位增长来自堆碎片、arena、weak 持留还是容器膨胀。

**常见误区**：把碎片当泄漏修（改代码没用）；只看虚拟内存不看 RSS；忽略 weak_ptr 对 make_shared 内存的延迟释放。

**追问方向**：
1. 怎么区分碎片和真泄漏？（定期 `malloc_trim` 后 RSS 是否回落；换 jemalloc/tcmalloc 增长是否消失——若消失倾向碎片；若依旧倾向逻辑持留/泄漏。）
2. 为什么排查时不能只看 RSS？（RSS 含共享库/共享内存，会被多进程重复统计——游戏服务端常见多进程 worker 共享 so、共享内存区。看 `/proc/<pid>/smaps` 里的 **PSS**（按比例分摊共享页）和 **USS**（独占页）更接近真实占用。glibc malloc 还有 `MMAP_THRESHOLD` 决定大块走 `mmap`（可单独还给 OS）还是 `brk` 堆区（trim 后才能还），影响 RSS 回收行为。）

### 【专家】系统设计 · 游戏实体的对象池

> 设计一个游戏实体（Entity）的对象池。如何避免外部持有旧引用导致的悬垂访问？池满了怎么办？

**参考思路**：
- **结构**：预分配 `Entity[N]` 数组 + 空闲索引链表。分配 = 取一个空闲槽并构造；回收 = 显式析构 + 槽归还链表。
- **防悬垂（关键）**：对外不返回裸指针，而返回**代际 ID** = `(index, generation)`。槽被回收时 generation++。外部每次用 ID 访问池时，校验 `slot[index].generation == id.generation`，不符即视为失效对象。这样旧 ID 引用不会误访问到复用后的新对象。
- **池满**：策略可选——扩容（重新分配更大数组、迁移）、阻塞等待、拒绝（对实体常扩容；对消息常拒绝+告警）。
- **热/冷分离**：每帧访问字段（pos/state）连续紧凑存放，不常用字段分开。
- **复用不重构造**：用 placement new 在槽上重建，避免反复调用构造/析构的开销。

**考点解析**：对象池设计 + 代际 ID 防悬垂（这是游戏服务端的经典范式）。资深要主动提出代际 ID，并讨论池满策略与生命周期边界。

**常见误区**：返回裸指针/裸 index，对象复用后外部悬垂访问；池满时静默丢弃无告警；不分离热冷数据。

**追问方向**：
1. 代纪 ID 用多少位？（典型：32 位 = 20 位 index + 12 位 generation，或在 64 位下更宽。generation 回绕风险？实践中 generation 用足够宽的位 + 回绕极罕见。）
2. 如果要支持"延迟回收"（当前帧还在用，下帧才回收）怎么设计？（引用计数或延迟队列，引用归零才归还池。）

### 【进阶】原理辨析 · placement new 与手动生命周期

> 什么场景需要 placement new？手动"析构 + placement new 重建"一个对象有什么风险？

**参考思路**：placement new 在**已分配的内存**上原地构造对象（不分配），常用于：对象池槽位复用、arena、容器内部（vector 在 reserve 的原始内存上构造）、`std::vector` 的 `emplace_back`。手动生命周期：先 `p->~T()` 显式析构，再 `new (p) T(...)` 重建。风险：① 必须成对——只析构不重建是悬垂，重建不析构旧对象是泄漏/UB；② 对齐要匹配（placement 内存必须满足 alignof(T)）；③ 重建若抛异常，对象处于已析构状态，访问即 UB；④ 混用 `delete` 会双重释放（placement new 的对象不能 delete，只能析构 + 手动释放底层内存）。

**考点解析**：placement new 的用途与正确配对；对象生命周期的手动控制。资深要能讲清"分配 vs 构造"分离的语义。

**常见误区**：对 placement new 的对象调用 delete；忘记先析构就重建；忽略对齐与异常安全。

**追问方向**：`std::vector` 内部如何用 placement new + 显式析构管理元素？（原始内存 allocate → emplace 构造 → erase 时析构 → 最后 deallocate，分配与构造解耦。）

### 【进阶】权衡 · 三种降低分配开销的手段如何选

> 降低高频分配开销有三种思路：对象池、内存池/arena、换全局分配器（tcmalloc/jemalloc）。怎么选？

**参考思路**：按"可控性 vs 通用性"取舍：
- **换全局分配器**（tcmalloc/jemalloc）：改动最小，对全程序所有堆分配生效，缓解锁竞争与 size-class 开销。适合"不想改业务代码、整体提升"。
- **arena**：对**同生命周期、批量分配整体释放**的临时对象最优（每帧临时量、单次请求 buffer），O(1) 无锁无碎片。适合边界清晰的临时区。
- **对象池**：对**固定大小、高频创建销毁、需稳定地址或代际 ID** 的对象（实体、消息）最优，还能控制生命周期与悬垂。适合核心业务对象。
三者叠加：全局用 jemalloc 兜底 + arena 处理帧内临时 + 对象池管理实体。不是二选一。

**考点解析**：三种手段的适用边界与组合。资深要能根据对象特征（大小是否固定、生命周期是否整齐、是否需稳定地址）选型。

**常见误区**：把对象池当万能；以为换了 jemalloc 就不需要池；忽略 arena 的"不析构"约束。

**追问方向**：对象池里的对象大小不固定怎么办？（按 size-class 分桶，每桶一个池；或退化为 arena。）

> **本章小结**：内存与生命周期的主线是"**对象在内存里怎么放（布局/对齐/SoA）→ 怎么分（堆/arena/池）→ 怎么被 cache 命中（局部性/false sharing）→ 怎么活得干净死得确定（所有权/代际 ID/析构配对）**"。这四个环节是性能优化与故障排查的底层地基，后续网络、并发、性能优化章节会反复回到这条链。
