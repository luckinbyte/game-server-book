# 第4章 数据结构与算法（游戏向）

> 游戏服务端的算法题不像 LeetCode 刷题——它考的是"**为什么选这个结构、复杂度与常数的工程权衡、它如何贴合游戏的访问模式**"。本章把游戏高频结构（并查集/堆/跳表/线段树/trie）、空间划分（四叉树/八叉树/BVH/AOI）、海量数据处理（Top-K/外部排序/布隆/一致性哈希）和寻路前置（A*）串起来。核心心法：**结构服务于访问模式**，先想清楚"怎么访问、谁热谁冷、多大体量"，再选结构。

## 原理体系

### 1. 选型心法：结构服务于访问模式

选数据结构前先回答三个问题：
1. **访问模式**：批量遍历？按 key 查找？范围查询？最值？插入/删除频率？
2. **体量**：万级、百万级、还是海量（放不下内存）？
3. **实时性**：热路径（每 tick/每帧）还是低频（登录、匹配）？

错误示范：给所有"按 id 查对象"都用 `std::map`（O(log n) + 红黑树节点分散、cache 不友好），其实玩家对象用 `unordered_map` 或直接数组+代际 ID 更快。正确心法：热路径要 cache 友好的连续结构，低频才容忍树/哈希的间接。

### 2. 并查集（Union-Find）

并查集解决"**动态连通性**"——快速判断两点是否在同一集合、合并两个集合。

- **表示**：每个元素存一个父指针，根代表集合。`find(x)` 沿父指针找到根；`union(a,b)` 把一棵树的根挂到另一棵的根下。
- **两大优化**：
  - **路径压缩**：`find` 时把沿途节点直接挂到根，让树变扁。
  - **按秩/大小合并**：总把小树挂到大树下，控制树高。
- **复杂度**：两者配合后，单次操作均摊 **O(α(n))**（α 是反阿克曼函数，对任何实际 n ≤ 4），工程上视为**常数**。

游戏场景：连通区域判定、组队/帮派合并、地图区块归属、社交关系连通分量。比 BFS/DFS 增量维护连通性高效得多。

### 3. 堆 / 优先队列

**二叉堆**：完全二叉树，父节点 ≤（或 ≥）子节点。插入/删除最值 O(log n)，查最值 O(1)，数组实现（cache 友好）。

游戏场景：
- **定时器**：按到期时间组织成最小堆，每次 tick 取堆顶看是否到期（见下文与时间轮的对比）。
- **任务调度**：按优先级出队。
- **Top-K**：维护大小为 K 的最小堆，流式选最大的 K 个（见海量数据节）。
- **A\* 的开放表**：按 f = g + h 排序取最小（见寻路节）。

注意 `std::priority_queue` 默认是最大堆且不支持删除任意元素/降低键——需要 decrease-key 或删除中间元素的场景要用 `std::multiset` 或手写索引堆。

### 4. 跳表（Skip List）

跳表是**有序**结构，用多级索引链表实现 O(log n) 的查找/插入/删除，平均性能与平衡树相当，但实现简单、且**对并发更友好**（局部加锁即可，而红黑树再平衡会大范围改动）。

游戏典型场景：**实时排行榜**——按分数有序、频繁插入/更新/按名次范围查询。Redis 的 `ZSET` 底层就是跳表 + 哈希表（跳表管有序、哈希表管 O(1) 查成员分数）。

对比：红黑树/`std::map` 也 O(log n) 有序，但跳表实现更简单、并发更友好；堆只能高效取最值，不能高效按名次范围查。

### 5. 线段树 / 树状数组

处理**区间查询/区间更新**的利器：
- **线段树**：把区间 [1,n] 组织成二叉树，每个节点维护一段子区间的聚合（和/最值/max）。点更新 O(log n)、区间查询 O(log n)、**区间更新配合 lazy 标记** O(log n)（延迟把更新下推到子节点）。
- **树状数组（BIT）**：更轻量，支持前缀和类查询（点更新 + 前缀查询，都 O(log n)），代码极短，但功能受限（不易做"区间更新+区间查询"的组合，需要技巧）。

游戏场景：战斗的区间 buff/范围伤害、排行榜的名次区间统计、按等级段聚合的统计。海量在线时的"区间最值/求和"用线段树远优于暴力。

### 6. Trie（前缀树）

Trie 把字符串按公共前缀组织成树，查询/插入 O(L)（L=串长，与串的数量无关）。游戏场景：
- **敏感词过滤**：把敏感词建成 trie，对聊天/昵称做前缀匹配。进阶是 **AC 自动机**（trie + 失败指针，一次扫描文本匹配所有模式串，O(n)）。
- **指令/前缀补全、字符串去重**。

对比：纯哈希只能精确匹配，做不了前缀/模糊；trie 牺牲空间（节点多）换前缀能力。海量敏感词时 trie 内存大，可用**双数组 trie（Double-Array Trie）**压缩。

### 7. 空间划分：四叉树 / 八叉树 / BVH / AOI

2D/3D 空间里"找某点附近的对象"是高频操作（视野、碰撞、范围技能）。线性遍历所有对象 O(n) 不可行，需要空间划分加速。

- **四叉树（2D）/ 八叉树（3D）**：递归把空间切成 4/8 块，直到每块对象数低于阈值。查询时只递归与查询范围相交的子空间。适合**动态**场景（对象移动时更新所属叶子），但频繁插入/删除有开销，且稀疏分布时退化。
- **BVH（Bounding Volume Hierarchy）**：把对象用包围盒（AABB/球）组织成层次树，不绑定固定空间网格。适合**动态 + 不均匀分布**（如碰撞检测），更新时调整包围盒层次。
- **均匀网格 / 九宫格**：把空间切成固定大小格子，对象按位置归入格子。查询某点附近只看相邻几格。**简单、cache 友好、查询 O(1) 均摊**——游戏 AOI 最常用。

**AOI（Area of Interest，兴趣区域）**：服务端只把玩家"视野内"的其他实体广播给他，而非全服。两种经典实现：
- **九宫格（网格法）**：地图切成格子，玩家维护"我周围 3×3（或 5×5）格子"，移动时计算新旧视野差集，只广播进出视野的事件。实现简单、查询快，缺点是格子大小固定、对象密集时单格过载。
- **十字链表**：对象按 x 坐标和 y 坐标分别维护两条有序链表，查询视野 = 沿两条链表各取一段求交。更灵活（视野半径可变），但实现复杂、移动时维护两条链表有开销。

### 8. 海量数据：Top-K / 外部排序 / 布隆 / 一致性哈希

数据量超过内存时的工程手段：

- **Top-K**：从海量数据找最大的 K 个。用大小 K 的**最小堆**流式处理：每个元素与堆顶比，比堆顶大则替换。O(n log K)，内存只占 K。比全排序 O(n log n) 快且省内存。
- **外部排序**：数据放不下内存时，分块读入排序后写入临时文件，再**多路归并**。经典应用于排行榜全量重算、日志分析。
- **布隆过滤器（Bloom Filter）**：位数组 + k 个哈希。插入：把 k 个哈希位置 1；查询：所有 k 位都为 1 才"可能在"，否则"一定不在"。**有假阳性、无假阴性**，空间极省。游戏场景：缓存穿透防护（先布隆过滤不存在的 key）、去重（消息/奖励领过与否的初筛）。
- **一致性哈希**：把节点和 key 都映射到哈希环上，key 顺时针找最近的节点。加减节点只影响相邻一段 key，**迁移量小**。但节点少时分布不均，需引入**虚拟节点**（每个物理节点映射多个虚拟点）让分布均匀。游戏场景：分服/分片、玩家路由到游戏服、分布式缓存路由。

### 9. A\* 寻路前置

A\* 是游戏寻路的标配（第 10 章详讲），这里讲前置：它本质是**带启发式的图搜索**。

- **图搜索框架**：Dijkstra（无启发、保证最短、慢）、BFS（无权图）、A\*（带启发、保证最短、快）。
- **g/h/f**：g = 起点到当前已走代价，h = 当前到终点的**估计**代价（启发函数），f = g + h。每步取 f 最小的扩展。
- **启发函数 h 的要求**：
  - **admissible（可采纳）**：h 绝不高估真实代价 → 保证 A\* 找到最优解。
  - **consistent/monotonic（一致）**：h 满足三角不等式 → 节点只需扩展一次、更高效。
  - 常用：曼哈顿距离（4 向网格）、对角线距离（8 向）、欧几里得距离。
- **开放表用堆**：取 f 最小的节点 = 最小堆的堆顶，O(log n)。
- h = 0 时 A\* 退化为 Dijkstra；h 估计得越准，扩展的节点越少、越快。

## 面试题

### 【进阶】原理辨析 · 并查集的近 O(1)

> 并查集的路径压缩 + 按秩合并为什么能做到近乎 O(1)？游戏里有哪些应用？

**参考思路**：单用一种优化，复杂度是 O(log n)；两者配合后，单次操作均摊 **O(α(n))**——α 是反阿克曼函数，增长极慢，对任何实际 n ≤ 4，工程上视为常数。路径压缩让 `find` 后树变扁（后续查询 O(1)），按秩合并控制树高，二者叠加使整体几乎扁平。游戏应用：连通区域/地图区块归属判定、组队与帮派合并（动态连通性）、社交关系连通分量。比每次 BFS/DFS 增量维护高效得多。

**考点解析**：α(n) 的含义、两大优化的协同、动态连通性场景。资深要能讲清"为什么均摊近常数"。

**常见误区**：只知一种优化；以为复杂度是 O(log n)（那是单优化的）；忽略按秩合并导致树退化为链。

**追问方向**：只做路径压缩不做按秩合并，复杂度还是 O(α) 吗？（单独路径压缩均摊 O(log n)，二者配合才到 α；实际中路径压缩往往已足够好。）

### 【专家】深挖追问 · 排行榜：堆 vs 跳表 vs 红黑树

> 实时排行榜（按分数排名、频繁更新分数、按名次范围查、查某玩家名次），用堆、跳表还是红黑树？Redis ZSET 为什么用跳表？

**参考思路**：
- **堆**：只能高效取最值，**不能高效按名次范围查、不能高效查某玩家名次**（堆是无序数组）。淘汰。
- **红黑树（std::map）**：O(log n) 有序、能范围查，但并发不友好（再平衡大范围改结构）、实现复杂、节点分散 cache 不友好。
- **跳表**：O(log n) 有序、范围查 O(log n + k)、实现简单、**并发友好（局部加锁）**。还能顺手配一个哈希表 O(1) 查"某玩家当前分数"，再在跳表里定位其名次。
- Redis ZSET = 跳表（有序、范围）+ 哈希表（member→score 的 O(1) 查），正是这个组合。选跳表而非红黑树，因实现简单、范围操作友好、并发与内存表现更平衡。

**考点解析**：三者的访问模式适配性、排行榜的真实需求（名次范围 + 单点分数）、ZSET 的双结构设计。资深要按"查询需求"反推结构。

**常见误区**：用堆做排行榜（查不了名次）；以为红黑树一定最优；忽略"查某玩家名次"这个需求。

**追问方向**：千万级玩家、分数频繁变动，排行榜怎么扛？（分片排行榜、只精确算前列+其余近似、定时快照而非实时全算。）

### 【专家】系统设计 · 定时器模块：最小堆 vs 时间轮

> 设计一个服务端定时器模块（百万级定时任务，每 tick 检查到期）。最小堆和时间轮（hashed wheel）怎么选？

**参考思路**：
- **最小堆**：按到期时间堆排。每 tick 看堆顶是否到期，到期则弹出。**插入/删除 O(log n)**，查到期 O(1)（看堆顶）。优点：到期判断极快；缺点：插入/删除有 log n 开销，且只能高效取"最早到期"，批量到期时要逐个弹。
- **时间轮（hashed wheel timer）**：把时间分成槽（如每毫秒一槽，轮转一周 1 秒），任务按到期时间挂到对应槽。每 tick 推进当前槽，处理该槽全部任务。**插入/删除 O(1)**，到期处理 O(该槽任务数)。多层时间轮处理超长定时（秒针轮+分针轮+时针轮，像钟表）。
- **取舍**：任务量极大且插入/删除频繁 → **时间轮**（O(1) 插删，Linux 内核、Netty 都用它）；任务量小或到期判断是瓶颈 → 最小堆。游戏服务端定时器任务海量（buff、技能 cd、心跳、活动），**时间轮更主流**。

**考点解析**：两种结构的复杂度特征、海量定时任务的选型。资深要能按"插删频率 vs 到期判断"权衡。

**常见误区**：只会最小堆，忽略时间轮的 O(1) 优势；不知道多层时间轮处理超长定时。

**追问方向**：时间轮上一个 1 小时后的任务怎么放？（挂到高层轮，逐层降级到低层轮——时钟级联。）

### 【进阶】原理辨析 · 线段树与 lazy 标记

> 线段树为什么需要 lazy 标记？点更新和区间更新的复杂度分别是什么？给一个游戏场景。

**参考思路**：线段树把区间组织成二叉树，每个节点维护子区间聚合。**点更新**：改一个叶子、沿路径更新祖先，O(log n)。**区间更新**（如"把 [l,r] 全体 +v"）：若逐点更新是 O(n log n)；用 **lazy 标记**——把更新挂到覆盖该区间的最高节点上，**延迟下推**到子节点，使区间更新也 O(log n)；查询时再沿途下推 lazy。复杂度：点更新/区间更新/区间查询都 O(log n)。游戏场景：范围 buff（区域内全体玩家加减属性）、战斗区间伤害结算、按等级段统计。

**考点解析**：lazy 标记的作用（延迟下推把区间更新降到 O(log n)）、何时下推。资深要能讲清"不 lazy 会退化到 O(n)"。

**常见误区**：区间更新不用 lazy 导致 O(n)；下推 lazy 的时机错（查询/更新前要先 pushdown）。

**追问方向**：树状数组（BIT）能做区间更新+区间查询吗？（能：区间更新+单点查询用一个差分 BIT；区间更新+区间查询需两个 BIT，分别维护 Δ[i] 与 i·Δ[i]，前缀和组合出区间值；公式推导不如线段树直观，故 BIT 更适合点更新+前缀查询。）

### 【进阶】原理辨析 · 敏感词：trie vs AC 自动机 vs 哈希

> 聊天敏感词过滤，文本里匹配一个敏感词词库（十万级）。trie、AC 自动机、哈希各适用什么？

**参考思路**：
- **哈希**：只能精确匹配单个词，不能处理"文本里是否含某敏感词的子串/变体"。词库大、要全位置匹配时低效。
- **trie**：把词库建成前缀树，对文本每个位置做前缀匹配。能高效判断"是否以敏感词为前缀"，但每个文本起点都要重新匹配，复杂度 O(文本长 × 最长词长)。
- **AC 自动机**：trie + 失败指针（类似 KMP 的 next 数组推广到多模式）。**一次扫描文本即可匹配所有模式串，O(文本长 + 匹配数)**，是敏感词过滤的标准方案。词库超大时用双数组 trie 压缩内存。
游戏里聊天/昵称/公告过滤用 AC 自动机居多；要处理变体（谐音、拆字、星号）则需配合正则/规则引擎。

**考点解析**：多模式串匹配的演进（trie → AC）、复杂度优势。资深要知道"为什么哈希不行"（不能做子串/多位置匹配）。

**常见误区**：用一堆 `strstr`/哈希逐词扫（O(词数×文本长)，慢）；忽略 AC 自动机的一次扫描优势。

**追问方向**：词库经常更新，AC 自动机重建开销大怎么办？（增量构建失败指针，或双 buffer——新词库构建好再原子切换。）

### 【专家】系统设计 · AOI：九宫格 vs 十字链表

> 设计服务端 AOI（只广播玩家视野内的实体）。九宫格法和十字链表法各自的原理与开销？怎么选？

**参考思路**：
- **九宫格（网格法）**：地图切成固定大小格子，每个实体按位置归入一格。玩家视野 = 周围 3×3（或 5×5）格子。移动时计算"旧视野格子集合 → 新视野格子集合"的差集，只对进/出视野的实体广播 enter/leave。**查询 O(视野格子数 + 格内对象数)，简单、cache 友好**；缺点：格子大小固定，对象极密集时单格过载、极稀疏时一格太大。
- **十字链表**：实体按 x 和 y 各维护一条有序链表。视野查询 = 沿 x 链取 [x-r,x+r] 段、沿 y 链取 [y-r,y+r] 段，求交。**视野半径可变、分布自适应**；缺点：移动时要维护两条链表的有序性（O(视野内) 的调整）、实现复杂。
- **选择**：地图规则、对象分布均匀、视野半径固定 → 九宫格（简单高效，主流 MMO 用它）；视野半径多变、分布极不均 → 十字链表或四叉树。实践中九宫格 + 合理格子大小能覆盖绝大多数场景。

**考点解析**：AOI 的"增量广播"思想（只发进出视野的差集）、两种实现的开销模型。资深要主动讲"为什么不能每次全量广播全服"（带宽与 CPU 爆炸）。

**常见误区**：每次移动把视野内全部实体重新广播（应只广播差集）；格子大小拍脑袋（太大查询慢、太小跨格多）。

**追问方向**：对象极密集（千人同屏一格）怎么办？（格子内再用空间结构细分，或动态分裂格子；服务端做视野裁剪/限流。）

### 【专家】深挖追问 · 空间划分：四叉树/八叉树/BVH 选型

> 2D 用四叉树、3D 用八叉树，碰撞检测常用 BVH。它们的本质区别是什么？静态场景和动态场景怎么选？

**参考思路**：
- **四叉树/八叉树**：按固定空间**均匀细分**（每块切 4/8 份），结构绑定空间网格。适合对象分布相对均匀的场景；动态场景下对象移动要更新所属叶子，稀疏区域会过度细分或退化。
- **BVH**：按**对象**的包围盒组织层次树（不绑定固定网格），节点是子对象的合并包围盒。查询时用包围盒相交测试剪枝。**对不均匀分布和动态场景更友好**（碰撞检测主流），代价是对象移动后要更新/重平衡 BVH（refit 或重建）。
- **静态场景**（地图、建筑）：可预计算并烘焙，四叉树/八叉树或 BVH 都行，建一次即可。
- **动态场景**（大量移动实体）：BVH 的 refit（只更新包围盒不重建结构）更高效；四叉树频繁插删开销大。游戏碰撞检测（物理引擎）几乎都用 BVH（或其变种 SBVH/DOP 树）。

**考点解析**：空间绑定（四/八叉树）vs 对象绑定（BVH）的根本差异、静/动态选型。资深要能讲清"为什么物理引擎用 BVH"。

**常见误区**：动态场景硬用四叉树（插删慢）；以为 BVH 不用维护（移动对象要 refit）。

**追问方向**：BVH 在对象剧烈移动后退化（包围盒重叠多、查询变慢）怎么办？（周期性重建（rebuild）或启发式旋转（rotations/refit），平衡重建成本与查询效率。）

### 【进阶】原理辨析 · 一致性哈希与虚拟节点

> 一致性哈希解决什么问题？为什么需要虚拟节点？给游戏里的应用。

**参考思路**：普通 `hash(key) % N` 在节点数 N 变化时几乎所有 key 都要迁移。**一致性哈希**把节点和 key 都映射到哈希环，key 顺时针找最近节点；加减节点只影响相邻一段 key 的归属，**迁移量 ~1/N**。但节点少时环上分布不均（某节点负载远高），引入**虚拟节点**：每个物理节点映射到环上多个虚拟点（如 150 个），虚拟点越多分布越均匀。游戏应用：玩家路由到游戏服（分服/分片）、分布式缓存（Redis Cluster 的 hash slot 是类似思想）、跨服数据分片。

**考点解析**：一致性哈希降低迁移量、虚拟节点解决分布不均。资深要能讲清"为什么 %N 不行"和"虚拟节点的作用"。

**常见误区**：忘了虚拟节点导致负载不均；以为一致性哈希零迁移（只是迁移量小）。

**追问方向**：Redis Cluster 为什么用 16384 个 hash slot 而不是一致性哈希环？（slot 是固定划分、迁移以 slot 为单位更可控、节点间 gossip 同步 slot 表；思想类似但实现不同。）

### 【进阶】手撕代码 · 海量数据 Top-K

> 10 亿个 64 位整数，找最大的 100 个。内存只有几百 MB。怎么做？

**参考思路**：用**大小为 100 的最小堆**流式处理：遍历每个数，若比堆顶大则替换堆顶并下沉。一遍扫描后堆里就是最大的 100 个。时间 O(n log K)、空间 O(K)。**关键**：用最小堆而非最大堆——最小堆的堆顶是当前 K 个里最小的"门槛"，新数大于门槛才入选。若数据放不下内存，先分块（每块读入排序/取 Top-K 写临时文件），再对各块的 Top-K 做**多路归并**取最终 Top-K（外部排序思想）。

**考点解析**：最小堆做 Top-K（不是最大堆）、流式 O(n log K)、外部归并处理超内存。资深要主动问"数据放得下内存吗"并给外部方案。

**常见误区**：用最大堆（堆顶是最大，没法当门槛淘汰）；全排序 O(n log n)；数据超内存时不分块。

**追问方向**：如果是"出现频率最高的 K 个"（不是最大的 K 个）？（先哈希分片到多机/多文件，各片用哈希计数再小顶堆合并——MapReduce 思想。）

### 【专家】深挖追问 · A\* 的启发式与最优性

> A\* 的启发函数 h 满足什么条件才能保证找到最优解？h=0 时退化成什么？开放表为什么用堆？

**参考思路**：
- **admissible（可采纳）**：h 绝不高估真实最短代价 → A\* 保证找到最优解。直观：若 h 高估，算法可能过早锁定一条非最优路径。
- **consistent（一致）**：对任意相邻节点 u→v，h(u) ≤ cost(u,v) + h(v)（三角不等式）→ 每个节点最多被扩展一次（关闭后不再 reopen），更高效。一致的 h 一定 admissible。
- 常用 h：曼哈顿距离（4 向网格，admissible 若只许四向移动）、对角线距离（8 向）、欧几里得（不低估直线距离，admissible）。
- **h=0**：A\* 退化为 **Dijkstra**（无启发、保证最优但慢，扩展更多节点）。h 越接近真实代价，扩展节点越少、越快；但 h 绝不能高估。
- **开放表用最小堆**：每步取 f=g+h 最小的节点扩展 = 最小堆堆顶，O(log n) 取出。

**考点解析**：admissible/consistent 的定义与作用、h=0 退化、堆的作用。资深要能讲清"h 高估会怎样"（可能非最优）。

**常见误区**：h 随便设导致非最优；以为 h 越大越快（高估会丢失最优）；开放表用线性结构（取最小 O(n)）。

**追问方向**：要更快但可接受次优解怎么办？（加权 A\*：h 乘一个 >1 权重，扩展更少节点但可能非最优——空间/时间换精度。）

### 【进阶】权衡 · 布隆过滤器

> 布隆过滤器的原理？假阳性、假阴性各是什么？游戏里用在哪？能不能删除元素？

**参考思路**：位数组（m 位）+ k 个哈希函数。插入：把元素经 k 个哈希得到的 k 个位置全置 1。查询：若 k 个位置全为 1 → "可能在"（**假阳性**：别的元素可能也把这些位置置 1 了）；若有任一位为 0 → "一定不在"（**无假阴性**：置过 1 的不会变 0）。假阳性率随元素数增多而上升，靠调大 m、调 k 控制。**不能删除**：把位置回 0 会误伤其他共享该位的元素；要删除得用计数布隆（Counting Bloom，每位用计数器）或布谷鸟过滤器。游戏场景：缓存穿透防护（查 DB 前先布隆过滤不存在的 key）、领奖/去重初筛、恶意账号初筛。

**考点解析**：假阳性（有）vs 假阴性（无）、不能删的原因、典型用途。资深要能讲清"为什么省空间"（多位共享、允许假阳性）。

**常见误区**：以为布隆能精确判断存在；尝试直接删除位；忽略假阳性率随数据量上升。

**追问方向**：假阳性率怎么算/控制？（与 m、k、插入元素数 n 有关；给定 n 和目标假阳性率，可算最优 m、k。）

> **本章小结**：游戏服务端的数据结构与算法，主线是"**结构服务于访问模式**"。先想清楚访问是批量遍历、按 key 查、范围查、最值还是空间邻近，再在并查集/堆/跳表/线段树/trie、空间划分（四叉树/八叉树/BVH/AOI）、海量处理（Top-K/外部排序/布隆/一致性哈希）里选型。复杂度只是下限，**常数、cache 友好、与游戏访问模式的契合度**才是实战决胜点——这也正是后续寻路、同步、性能优化章节反复要用的基础。
