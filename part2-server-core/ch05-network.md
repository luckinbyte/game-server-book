# 第5章 网络编程深度

> 网络是游戏服务端的命脉——玩家的一切交互都走网络。资深面试里的网络题不在"三次握手背几遍"，而在 **epoll 的内核机制、ET/LT 的本质、Reactor 架构、协议设计与序列化、连接管理与弱网**。这些是网络面试反复考察、且区分中高级的核心。本章把它们串成体系。

## 原理体系

### 1. TCP/UDP 在内核里是怎么回事

- **TCP** 是面向连接的**可靠字节流**：三次握手建连、状态机（ESTABLISHED / TIME_WAIT / CLOSE_WAIT…）、用**序列号 + 确认 + 超时重传**保证可靠、用**滑动窗口**做流量控制（收方告诉发方能收多少）、用**拥塞控制**（慢启动、拥塞避免、BBR）应对网络拥塞。关键认知：TCP 给你的是**无边界字节流**，应用层的"一条消息"边界要自己定（见粘包）。
- **UDP** 是**无连接的不可靠数据报**：发出去就不管，没有重传/拥塞/顺序保证，但延迟低、开销小。强实时游戏（FPS/MOBA 的战斗帧）常自建可靠层跑在 UDP 上（KCP、QUIC 思路），以低延迟换可控的丢包。

游戏典型组合：**TCP 传可靠控制流**（登录、交易、聊天、跨服），**UDP 传高频战斗同步**（位置、技能，丢一两个无所谓）。这是后续「同步模型（帧同步/状态同步）选型」与「弱网优化」的网络基础（详见第 16 章）——注意帧/状态同步并不直接绑定某一种传输协议：帧同步对可靠性要求高，常走可靠 UDP 或 TCP；状态同步既可走 TCP 也可走 UDP，具体按业务取舍。

### 2. IO 多路复用：select / poll / epoll

一个线程要同时处理上万连接，不能一个连接一个线程阻塞读。**IO 多路复用**让一个线程同时监视多个 fd 的就绪状态。

- **select**：位图传 fd 集合，每次调用都要把全部 fd 从用户态拷到内核态、内核线性扫描全部 fd 判断就绪。限制：fd 上限（FD_SETSIZE 通常 1024）、O(n) 扫描、每次重复传集合。
- **poll**：用链表/数组代替位图，去掉了 1024 限制，但仍是 O(n) 扫描、每次拷贝。
- **epoll**：内核维护一个**红黑树**存监视的 fd（增删改 O(log n)，不用每次重传），就绪的 fd 通过**就绪链表**直接给出——`epoll_wait` 只返回就绪的，**O(就绪数)**。且利用内核事件回调机制，fd 就绪时内核主动把它挂到就绪链表，无需线性扫描。这就是 epoll 在万级连接下远快于 select/poll 的根本原因。

### 3. epoll 的两种触发模式：LT vs ET

- **LT（水平触发，默认）**：只要 fd 的读缓冲区**还有数据可读**，`epoll_wait` 就会持续通知。可以不一次读完，下次还会通知。编程简单、不易漏数据。
- **ET（边沿触发）**：只在 fd **从不可读变为可读**时通知**一次**，之后即使还有数据也不再通知，直到下次状态变化。要求：**必须用非阻塞 IO + 循环读到返回 EAGAIN/EWOULDBLOCK**，否则残留数据永远读不出来 → 连接"卡死"。文件描述符必须设 `O_NONBLOCK`。

ET 的优势：减少 `epoll_wait` 的唤醒次数（每批数据只通知一次），吞吐更高；劣势：编程复杂、易错（漏读、事件丢失）。高性能服务（nginx、Muduo）多用 ET 或 LT + 一次读尽。

### 4. Reactor 模式与 Muduo

**Reactor** 是事件驱动网络框架的核心模式：主线程 `epoll_wait` 等事件 → 事件就绪 → 分发给对应回调（读、写、接受连接）处理。把"等 IO"和"处理 IO"解耦。

**主从 Reactor（Main-Sub Reactor）**：
- **Main Reactor** 专门 `accept` 新连接。
- 新连接的 fd 派发给某个 **Sub Reactor**（多个，每核一个）。
- Sub Reactor 各自跑一个 epoll 循环，处理派发到自己这的连接的读写事件。

**Muduo 的 "one loop per thread"**：每个线程一个事件循环（一个 epoll），连接固定归属某个线程，避免跨线程锁。线程间用**任务队列 + 唤醒 fd（eventfd/self-pipe）**投递跨线程任务。这是 C++ 游戏服务端网络层的经典结构。

### 5. SO_REUSEPORT 与惊群

`SO_REUSEPORT` 允许多个 socket 绑定**同一 IP:port**，内核把进来的连接**哈希分发**到这些 socket 上。意义：多个 worker 线程/进程各自 `accept` 同一端口，内核做负载均衡，避免单 accept 瓶颈与**惊群（thundering herd）**——旧模型下多进程 `accept` 同一监听 fd，一个连接到来会唤醒所有阻塞的 accept，但只有一个成功，其余白醒。

REUSEPORT 让每个 worker 独占自己的连接队列，扩展性更好（nginx 1.9+ 用它做多 worker）。

### 6. 粘包/拆包与协议设计

TCP 是**字节流**，应用层发的两条消息可能被合并成一段到达（粘包），或一条被拆成多段（拆包）。所以接收方必须**自行组帧**。常见组帧方式：

- **长度前缀**（最常用）：消息头里写明 body 长度，接收方按长度切分。
- **分隔符**：消息间用特殊字节分隔（如 `\r\n`），body 不能含分隔符或需转义。
- **定长消息**：每条固定长度，简单但浪费。

协议设计要点：**版本号**（向前兼容）、**消息 ID/类型**（路由）、**长度**、可选**校验和/加密**。Body 用序列化格式编码。

**序列化选型**：
- **Protobuf**：二进制、紧凑、字段编号机制天然向前兼容、生态成熟。服务端配置/通信主流。
- **FlatBuffers**：**零拷贝**——反序列化不需解析，直接按偏移读字段，超低延迟，适合高频消息（游戏战斗包）。代价：schema 灵活性略低、体积控制不如 proto。
- **JSON**：可读、跨语言、调试方便，但体积大、解析慢，多用于外部 API/工具，少用于内部高频链路。

### 7. 零拷贝：sendfile / splice / mmap

减少数据在内核态/用户态间的拷贝：
- **sendfile**：把文件内容直接从内核页缓存拷到 socket 缓冲区，**不经用户态**。适合"从磁盘读文件发到网络"（静态资源、补丁分发）。
- **splice**：在两个 fd 之间（如管道 ↔ socket）用内核缓冲区移动数据，零用户态拷贝。
- **mmap**：把文件映射到进程地址空间，读写文件像读写内存，避免 read/write 的用户态拷贝。

游戏里的大文件分发（更新包）、日志写入常用零拷贝。注意零拷贝主要省 CPU（拷贝）和内存带宽，不改变网络本身的延迟。

### 8. 连接管理：TIME_WAIT / RST / Keepalive

- **TIME_WAIT**：主动关闭方进入的持续 2MSL 的状态，用途是确保最后的 ACK 到达对方、防止旧连接的延迟报文干扰新连接。**注意时长在 Linux 上固定为 60 秒**（内核常量 `TCP_TIMEWAIT_LEN`，MSL 硬编码为 30s，2MSL=60s，**不可经 sysctl 调整**；教科书的"2MSL=60-120s/4 分钟"是把 RFC 建议的 MSL=2 分钟与各实现混为一谈，Linux 实际取 30s）。**短连接高频建连**会让服务端/客户端堆积大量 TIME_WAIT，耗尽端口或内存。对策：用**长连接**（连接复用）、`SO_REUSEADDR`（快速重 bind）、调内核 `tcp_max_tw_buckets`（上限水位，非时长）、必要时 `tcp_tw_reuse`——注意 `tcp_tw_reuse` **不缩短 TIME_WAIT 时长**，而是允许新连接复用仍处于 TIME_WAIT 的四元组做出向连接，是治标。
- **RST**：异常重置连接（对端不存在、半关闭写、队列满）。服务端 `accept` 队列满时新连接被 RST。
- **Keepalive**：TCP 自带的空闲探测（默认 2 小时太长，游戏要自己加**应用层心跳**，几十秒一次，超时判定连接断开）。

### 9. 弱网与拥塞控制（概览，详见第 16 章）

弱网（高 RTT、高丢包、抖动）下 TCP 的拥塞控制（默认 CUBIC 的退避）会让吞吐骤降、延迟飙升。游戏战斗同步常用 **UDP + 自建可靠层（KCP/QUIC 思路）**：快速重传、前向纠错（FEC）、不退避或少退避，以可控丢包换低延迟。BBR 拥塞控制（按带宽与 RTT 建模而非丢包退避）在弱网下吞吐更稳。细节见第 16 章。

## 面试题

### 【专家】深挖追问 · epoll ET 模式为什么必须循环读到 EAGAIN

> epoll ET 模式下，处理读事件时为什么要用非阻塞 IO + 循环 read 直到返回 EAGAIN？不这么做会怎样？

**参考思路**：ET 只在状态从"不可读→可读"时通知一次。假设一次事件到了但 buffer 有 8KB 数据，你只读了 4KB 就返回，剩余 4KB 还在 buffer——但 ET 不会再通知（状态没变化）。这 4KB 就"卡"在内核 buffer 里，连接看起来活着却永远读不到，且对方可能因此阻塞写（滑动窗口满）。所以必须：fd 设 `O_NONBLOCK`，读到 EAGAIN 才说明本轮清空，下次新数据来才会再次触发 ET。LT 模式没这问题（还有数据就一直通知）。

**考点解析**：ET 的"一次性通知"语义、非阻塞+循环读的必要性、漏读导致的连接卡死。资深要能讲清"为什么 ET 高吞吐但易错"。

**常见误区**：ET 用阻塞读（read 阻塞拖死事件循环）；ET 不循环读（漏数据）；忘记设非阻塞。

**追问方向**：
1. ET 模式下写事件怎么处理？（同样循环写直到 EAGAIN，写不完要注册 EPOLLOUT、等可写再续写。）
2. ET 模式下 accept 为什么要循环 accept 到 EAGAIN？（可能多个连接同时就绪，只 accept 一个会漏，其余在队列里得不到处理。）

### 【进阶】原理辨析 · select/poll/epoll 为什么 epoll 快

> select、poll、epoll 的区别？为什么 epoll 在万级连接下远快于前两者？

**参考思路**：select/poll 每次调用都要把全部关心的 fd 从用户态拷到内核、内核**线性扫描全部 fd** 判断就绪，O(n) 且与连接数成正比；select 还有 1024 上限。epoll 在内核用**红黑树**维护关注的 fd（增删 O(log n)，不用每次重传），fd 就绪时内核**事件回调**主动把它挂进**就绪链表**，`epoll_wait` 只拷出就绪链表——O(就绪数)，与总连接数无关。所以万级连接中只有少量就绪时，epoll 远快。

**考点解析**：O(n) 全扫描 vs O(就绪数) 回调驱动；epoll 的红黑树+就绪链表双结构。资深要能讲清"快在哪"。

**常见误区**：以为 epoll 是 select 的"大号版"；忽略内核回调机制；不知道 LT/ET 还会影响行为。

**追问方向**：连接数很少但都活跃时，epoll 还比 select 快吗？（差距缩小——就绪数≈总数时 epoll 也要处理全部，优势在"少量就绪+大量空闲"的场景，正是服务端的常态。）

### 【专家】系统设计 · 主从 Reactor 与 one loop per thread

> 设计一个高并发服务端网络框架。主从 Reactor 是怎么分工的？Muduo 的 one loop per thread 为什么这样设计？

**参考思路**：**主从 Reactor**——Main Reactor 只负责 `accept` 新连接（监听 fd 的读事件=新连接到来），accept 到的连接 fd 按某种策略（轮询/哈希）派发给某个 Sub Reactor；多个 Sub Reactor 各跑一个 epoll 事件循环，处理自己名下连接的读写。这样 accept 不与 IO 处理抢资源、连接分散到多核并行处理。**Muduo one loop per thread**：每个线程一个 EventLoop（一个 epoll），连接一旦归属某 loop 就固定在其线程处理，**避免跨线程共享数据加锁**；线程间需要交互时，把任务投递到目标 loop 的任务队列，并通过 eventfd/self-pipe 唤醒它执行——保证"每个连接的数据只在它自己的线程访问"。

**考点解析**：Reactor 的事件驱动思想、主从分工、one loop per thread 的无锁化设计。资深要能讲清"为什么连接固定到线程能避免锁"。

**常见误区**：连接数据跨线程共享还加锁（违背 one loop 设计）；accept 与 IO 在同一线程（accept 慢会拖累 IO）。

**追问方向**：业务逻辑（DB 查询、计算）很慢，放在 Sub Reactor 的 IO 线程里会怎样？（阻塞事件循环，拖慢该线程所有连接——慢逻辑要用线程池或异步，不阻塞 IO 线程。）

### 【专家】深挖追问 · 跨线程/跨核转移 fd（fd migration）

> 主从 Reactor 里，Main Reactor accept 到一个新连接后要把它交给某个 Sub Reactor 处理。这个 fd 怎么从 Main Reactor 的 epoll "搬"到目标 Sub Reactor 的 epoll？常见的错误做法是什么？

**参考思路**：fd 在 epoll 中的归属是按「(epfd, fd) + 关联的事件回调/数据」绑定的，不是文件表项的固有属性。正确的转移流程：① Main Reactor 先对自己 epfd 做 `EPOLL_CTL_DEL` 把这个 fd 摘掉；② 通过目标 Sub Reactor EventLoop 的任务队列投递一个"把该 fd `EPOLL_CTL_ADD` 进目标 epfd、并绑定目标 loop 的回调/连接对象"的任务，由**目标线程自己**执行 add（epoll 的 `EPOLL_CTL_ADD/MOD/DEL` 应由持有该 epfd 的线程来做，避免并发操作同一 epfd）。这样事件回调、连接上下文、所属线程三者一致——这就是 one loop per thread 落地最关键的约定。注意 `dup(fd)` 复制出的新 fd 是**另一个**文件描述符（指向同一 file），把它 add 到目标 epfd 并不等于转移了原 fd 的归属，且两边都会收到事件造成混乱；`EPOLL_CTL_MOD` 也只是改原 epfd 上的事件掩码，不会跨 epfd 迁移。

**考点解析**：epoll 归属语义、跨 epfd 转移的正确三步（DEL → 投递任务 → 目标线程 ADD）、为什么必须由目标线程操作自己的 epfd。资深要能讲清 dup fd / EPOLL_CTL_MOD 为什么不等于转移所有权。

**常见误区**：只 `dup` 一个 fd 加到目标 epfd 就以为转移了（原 fd 还在原 epfd，双触发）；直接在 Main 线程对目标 epfd 做 `EPOLL_CTL_ADD`（跨线程操作同一 epfd，需自行加锁，违背 one loop 思路）；忘了先从原 epfd DEL，两个 epfd 同时监听同一 fd。

**追问方向**：为什么 epoll 操作最好由持有 epfd 的那个线程自己做？（epoll 内核对同一 epfd 的 ctl/wait 并发保护有限，外部线程操作需额外同步，把 ctl 收敛到 owner 线程天然串行化、无锁。）转移过程中若恰好有就绪事件到达会怎样？（DEL 前已入就绪链表的事件仍会被原 loop 取到一次，回调里要能容忍"连接正在迁移"的中间态。）

### 【进阶】权衡 · SO_REUSEPORT 与惊群

> SO_REUSEPORT 解决什么问题？什么是惊群？

**参考思路**：旧模型下多个 worker 进程/线程 `accept` 同一个监听 fd，一个新连接到来时内核会**唤醒所有**阻塞在 accept 上的 worker（惊群），但只有一个 accept 成功，其余白醒（多余上下文切换）。`SO_REUSEPORT` 让多个 socket 绑定同一端口，内核**只把连接派发给一个** socket（按哈希/轮询），每个 worker 独占自己的连接队列，无惊群、扩展性好（nginx 多 worker 用它）。也支持进程级热升级（新旧进程同时 bind）。

**考点解析**：惊群的成因与代价、REUSEPORT 的内核级负载均衡。资深要知道惊群是 accept 多 worker 的经典问题。

**常见误区**：以为多线程 accept 同一 fd 没问题（有惊群）；混淆 REUSEPORT 和 REUSEADDR。

**追问方向**：epoll 在多线程共享一个 epfd 时有没有类似惊群？（有——多线程 wait 同一 epfd，一个事件唤醒多个，但事件只能处理一次；现代内核有 EPOLLEXCLUSIVE 缓解。）

### 【专家】原理辨析 · TCP 粘包与组帧

> TCP 为什么会"粘包"？怎么在应用层解决？

**参考思路**：TCP 是**字节流**，没有"消息边界"——发送方写的两条消息可能被合并进一个 TCP 段（粘包），或一条被拆成多个段（拆包），这由发送/接收缓冲区、MSS、Nagle 等决定，是 TCP 的正常行为而非 bug。解决在应用层**组帧**：最常用**长度前缀**（消息头写 body 字节数，接收方先读头拿长度、再读这么多 body，不足则缓存等齐）；或分隔符、定长。接收侧维护一个"已收字节 buffer + 解析游标"，够一帧就切出一帧交给上层。

**考点解析**：TCP 流语义、应用层组帧的必要性、长度前缀法。资深要能讲清"粘包是应用层概念，TCP 本身无包"。

**常见误区**：以为 TCP 有 bug；以为一次 send 对应一次 recv；用定长但 body 变长导致浪费。

**追问方向**：长度前缀本身怎么读（头也可能"粘/拆"）？（先按"读够头长度"再读 body，头不够先缓存；用状态机解析。）

### 【进阶】权衡 · Protobuf vs FlatBuffers vs JSON

> 内部高频通信、跨语言、需要向前兼容，序列化格式怎么选？

**参考思路**：
- **Protobuf**：二进制紧凑、字段编号机制天然**向前兼容**（加字段旧端忽略、删字段保留号）、跨语言、生态成熟。服务端内部通信与配置的主流。代价：需编译 schema、反序列化要解析。
- **FlatBuffers**：**零拷贝**——序列化结果是可直接按偏移读的内存布局，反序列化零成本，超低延迟，适合极高频消息（战斗同步包）。代价：schema 灵活性低、字段对齐占用、修改结构不如 proto 兼容性强。
- **JSON**：可读、调试友好、跨语言零依赖，但体积大、解析慢。多用于外部 API、配置、工具，少用于内部高频链路。
选型：内部高频 → proto；极致低延迟（每包都要反序列化）→ flatbuffers；对外/可读 → JSON。

**考点解析**：三者的性能/兼容/可读性权衡、向前兼容机制、零拷贝的价值。资深要能按场景选型。

**常见误区**：全用 JSON（高频链路慢）；忽略向前兼容（schema 变更打破老客户端）；以为零拷贝万能（它省反序列化，不省网络）。

**追问方向**：protobuf 加字段、删字段、改字段类型分别对兼容性影响？（加：兼容；删：旧端仍发、新端忽略即可，但别复用编号；改类型：通常不兼容。）

### 【专家】故障复盘 · 大量 TIME_WAIT

> 服务端监控发现 TIME_WAIT 状态连接数持续飙升到数万。什么原因？有什么危害？怎么处理？

**参考思路**：原因——**短连接高频建连**（每次请求建一个 TCP、用完主动关闭，主动关闭方进 TIME_WAIT，Linux 上固定持续 60s = 2×30s MSL），典型于 HTTP 短连接、或服务端主动关连接的客户端池。危害：① 耗尽**临时端口**（客户端侧，端口范围约几万）导致无法建新连接；② 占内存（每条 TIME_WAIT 一份内核结构）；③ 占内核计数（超 `tcp_max_tw_buckets` 内核告警/丢弃）。处理：① **改长连接/连接复用**（HTTP Keep-Alive、连接池）——治本；② `SO_REUSEADDR` 让服务端快速重新 bind；③ 调内核参数（`tcp_max_tw_buckets` 控制水位而非时长、必要时 `tcp_tw_reuse` 允许新连接复用 TIME_WAIT 四元组做出向连接——它**不缩短** TIME_WAIT 时长，是治标；勿用 `tcp_tw_recycle`——已在 4.12 移除， NAT 下会丢包）；④ 让客户端主动关（把 TIME_WAIT 留在客户端）。

**考点解析**：TIME_WAIT 的成因（主动关闭方、2MSL）、危害（端口/内存）、治本（长连接）vs 治标（调参）。资深要能区分端口耗尽（客户端）与内存压力（服务端）。

**常见误区**：上来就调 `tcp_tw_reuse` 而不改长连接（治标）；用已移除的 `tcp_tw_recycle`（NAT 丢包）；不知道端口耗尽发生在客户端侧。

**追问方向**：为什么 TIME_WAIT 要持续 2MSL？（确保最后的 ACK 到达对方；若丢，对方重传 FIN，本端还能响应；同时让旧连接的延迟报文在网络中消亡，不干扰同四元组的新连接。）

### 【进阶】原理辨析 · 零拷贝 sendfile/splice/mmap

> sendfile、splice、mmap 各解决什么？和普通 read+write 比省了什么？

**参考思路**：普通 `read(file)+write(sock)` 要 4 次上下文切换、4 次拷贝（磁盘→内核页缓存→用户 buffer→内核 socket buffer→网卡，其中页缓存→用户→socket 那两次是冗余的用户态往返）。**sendfile**：直接内核态把页缓存数据送到 socket buffer，省掉"拷到用户态再拷回"的两次，少 2 次上下文切换。**splice**：用内核管道在两个 fd 间移动数据，零用户态拷贝。**mmap**：文件映射进进程地址空间，读文件像读内存，省 read 的那次拷贝（但写网络仍需拷到 socket buffer）。零拷贝主要**省 CPU 与内存带宽**，不改变网络延迟。游戏里：补丁/资源分发（sendfile 大文件）、日志落盘（splice/mmap）受益。

**考点解析**：用户态/内核态拷贝的开销、三种零拷贝的原理与适用。资深要能画出数据流并指出省了哪次拷贝。

**常见误区**：以为零拷贝降低网络延迟（它省 CPU/带宽）；混淆 sendfile（文件→socket）与 splice（任意 fd 间）。

**追问方向**：sendfile 能不能用于"内存里的数据发给 socket"？（不能，sendfile 源是文件 fd；内存数据用 splice+vmsplice 或直接 write。）

### 【专家】故障复盘 · 连接数/句柄耗尽

> 服务运行一段时间后 `accept` 失败、新玩家连不上，`ESTABLISHED` 连接数或进程句柄数很高。怎么排查？

**参考思路**：分层排查：
1. **进程句柄（fd）上限**：`ulimit -n` / `/proc/<pid>/limits` 看软上限，`ls /proc/<pid>/fd | wc -l` 看实际占用。超限则 accept/_socket 失败。原因：连接泄漏（accept 了没 close）、文件/日志 fd 泄漏、fd 没复用。提升 `ulimit`（临时）/`/etc/security/limits.conf`（持久）+ 排泄漏。
2. **ESTABLISHED 连接堆积**：连接建立但业务不处理/不关，堆积。用 `ss -s` / `netstat` 看连接分布，定位是哪类连接滞留。
3. **端口耗尽**（客户端侧）：`ss` 看本地端口范围，TIME_WAIT 占满。
4. **accept 队列满**：`ss -lnt` 看 Recv-Q（accept 队列积压），服务端处理不过来 → 内核 RST 新连接。
修复：提升 fd 上限是治标，**排泄漏**是治本（连接生命周期管理、fd 配对 open/close、用 RAII 管理连接）。

**考点解析**：fd 上限、连接泄漏、accept 队列、端口耗尽四个层面。资深要能从"连不上"一路定位到具体根因。

**常见误区**：只提 ulimit 不排泄漏（fd 还会再涨满）；混淆 fd 上限与端口耗尽（前者进程级、后者通常客户端出向连接）。

**追问方向**：怎么快速定位是哪类 fd 泄漏？（`ls -l /proc/<pid>/fd` 看 fd 指向，统计 socket vs file vs pipe；或用 lsof。）

### 【进阶】原理辨析 · TCP_NODELAY 与 Nagle

> Nagle 算法是什么？为什么游戏服务端通常要关掉（设 TCP_NODELAY）？

**参考思路**：Nagle 算法为减少小包——发送方若有未确认的小数据，就攒着等"要么攒够 MSS、要么收到上一个包的 ACK"才发，避免网络上充斥小包。但游戏指令（移动、按键）是小包、要求**低延迟**，Nagle 会把小指令攒着延迟发出，手感变差。所以游戏连接设 `TCP_NODELAY` 关闭 Nagle，让小包立即发出。代价是网络上小包增多（但对游戏低延迟更重要）。同理 `TCP delayed ACK`（接收方攒 ACK）也会增加延迟，强实时场景一并考虑。

**考点解析**：Nagle 的初衷（减包）与游戏的低延迟诉求冲突；为什么游戏要 NODELAY。资深要能讲清"延迟 vs 包数"的权衡。

**常见误区**：不知道 Nagle 默认开；以为 NODELAY 有额外开销（它只是关掉攒包）。

**追问方向**：关了 Nagle 后，频繁发极小包会不会有"小包风暴"？（会，但游戏指令频率有上限、且包小；若极高频率，可考虑批包合并——但合并不能增加太多延迟。）

### 【专家】权衡 · 单机百万连接（C1M/C10K→C1M）演进

> 从 select 到支撑单机百万连接，关键演进是什么？

**参考思路**：
1. **IO 模型**：select（1024 上限、O(n)）→ epoll（O(就绪数)、红黑树管理万级 fd）。
2. **多核扩展**：单线程 epoll → 主从 Reactor + REUSEPORT 多 worker，连接哈希分散到多核。
3. **线程模型**：一连接一线程（万级就爆栈/调度爆）→ Reactor 事件驱动 + 线程池 / 协程（少量线程跑海量连接）。
4. **资源**：fd 上限提升（ulimit、`fs.file-max`）、内存（每连接的 buffer/上下文要省，用共享 buffer、SLAB）、端口范围（出向连接才受）。
5. **连接保活**：百万连接的心跳与超时管理要用高效结构（时间轮）。
6. **进一步**：内核态加速（XDP/DPDK 绕过内核协议栈）支撑极致。
关键：连接数上去了，**活跃连接数**和**每连接开销**才是瓶颈——百万长连接里大多空闲（IM、推送），真正难的是百万活跃。

**考点解析**：C1M（单机百万）的多维瓶颈（IO 模型/多核/线程/资源/心跳）与对应手段。资深要能分层拆解，并知道从 C1M 再上到 C10M（千万）需要内核协议栈 bypass（XDP/DPDK）+ 每连接内存压到 ~1KB 量级，是另一个数量级的工程。

**常见误区**：以为换 epoll 就能百万（还要多核+资源+心跳管理）；忽略"活跃连接"才是真考验。

**追问方向**：百万长连接里怎么高效做心跳超时？（时间轮 + 批量检测，避免对每连接单独 timer。）

---

> **本章小结**：网络编程的主线是"**IO 多路复用（epoll + ET/LT）→ Reactor 架构（主从 + one loop per thread）→ 协议与序列化 → 连接管理 → 弱网对策**"。epoll 的内核机制与 ET 的边沿语义、Reactor 的事件驱动、粘包组帧、TIME_WAIT/句柄这些是服务端网络的基本功；序列化选型与弱网优化则是连接"可靠控制流"与"低延迟战斗"的桥梁——后者在第 16 章深入。
