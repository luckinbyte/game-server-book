# 第6章 并发与多线程深度

> 多核是性能的来源，也是 bug 的来源。资深服务端工程师对并发的理解，不在"会用 mutex"，而在**同步原语的代价与适用、无锁编程的正确性（CAS + memory order）、线程模型的选择、以及死锁/优先级反转/ABA 这些深水区**。本章把这些串成体系——它们是并发面试的高频核心。

## 原理体系

### 1. 并发的本质：并行、并发与代价

- **并发（concurrency）**：多个任务在同一个时间段内推进（交替或并行）。
- **并行（parallelism）**：多个任务在同一时刻真正同时执行（多核）。
- 并发用多线程/多进程/协程实现；并行需要多核硬件支撑。

多线程的代价：**上下文切换**（内核态切换、cache/TLB 失效，~µs 级）、**同步开销**（锁、原子）、**可观测性差**（数据竞争难复现）。所以不是线程越多越好——线程数应匹配核数与任务类型（CPU 密集 ≈ 核数，IO 密集可远多于核数配合 IO 多路复用）。

### 2. 同步原语：互斥锁 / 自旋锁 / 读写锁 / 条件变量

- **互斥锁（mutex）**：获取不到就**睡眠**（让出 CPU、进内核等待队列），被唤醒再试。适合**临界区较长**或**锁竞争激烈**——睡眠期间不占 CPU。代价：上下文切换开销（睡眠/唤醒各一次内核态）。
- **自旋锁（spinlock）**：获取不到就**忙等**（循环 CAS 测），不睡眠。适合**临界区极短**且**不希望切换开销**——避免睡眠/唤醒的 µs 级代价。代价：忙等白烧 CPU；在**单核**上自旋可能死锁（持锁线程没机会运行）、多核高竞争下浪费 CPU。用户态自旋要设上限（防止永久自旋），通常"先自旋几次再退化为睡眠"（自适应锁，Linux 内核 mutex 的做法）。
- **读写锁（RWLock/shared_mutex）**：允许多读单写（读共享、写独占）。适合**读远多于写**。陷阱：写者饥饿（读者源源不断时写者永远拿不到）、读者间 cache line 竞争（计数器 false sharing）。高读场景的现代替代是 **RCU** 或 copy-on-write。
- **条件变量（condition_variable）**：用于"等待某条件成立"。必须**配合 mutex + while 循环**使用——`lock; while(!cond) cv.wait(lock); ...`。wait 原子地"释放锁 + 睡眠"，被 signal 唤醒后重新加锁再检查条件。
- **信号量（semaphore）**：计数同步，适合"限流 N 个并发"（如连接池大小）。

### 3. 无锁编程：CAS、原子操作与 memory_order

无锁不是"没有锁"，是**不使用操作系统级别的互斥**，靠**原子指令**（CAS/LL-SC、fetch-add 等）实现同步。

- **CAS（Compare-And-Swap）**：原子地"若位置处的值==期望则写新值，返回成功；否则返回失败"。是无锁算法的基石（`std::atomic::compare_exchange_*`）。
- **ABA 问题**：线程 1 读到 A，线程 2 把 A→B→A，线程 1 的 CAS 看到"还是 A"就成功——但中间已变过，逻辑可能错。解法：加**版本号/tag**（CAS 的值里含版本，每次改版本+1），或用 hazard pointer/代纪。
- **memory_order**（呼应第 1 章）：无锁代码正确性的基石。CAS 默认 `seq_cst`（最安全、最贵）；高性能场景用 `acquire/release` 配对传递可见性；纯计数用 `relaxed`。错用 memory_order 是无锁 bug 的头号来源。

### 4. 无锁数据结构

- **SPSC 环形队列（单生产者单消费者）**：经典无锁结构。生产者写 `buf[head]` 后 `head.store(release)`；消费者 `tail.load(acquire)` 后读 `buf[tail]`。head/tail 各只被一个线程写，用 acquire/release 保证"数据写入"对另一端可见，避免读到未初始化数据。这是高性能消息传递的标配（DPDK、跨线程消息队列）。
- **无锁栈/队列（MPMC）**：用 CAS 链表实现 push/pop，要处理 ABA（tag 指针：把版本号和指针打包成一个 64/128 位原子值一起 CAS）。
- **节点内存回收**：无锁结构里"pop 出去的节点何时能释放"是难题——别的线程可能还持有指针。解法：hazard pointer（发布"我正在访问这个指针"）、epoch-based reclamation（隔几轮确认无引用再释放）、或退化为引用计数。

无锁不是银弹：实现极难正确、调试困难、高竞争下 CAS 重试风暴反而慢。**工程上优先用锁（简单正确），仅热点路径且 profile 证实锁是瓶颈才上无锁。**

### 5. 线程池与任务调度

线程池避免"每任务建线程"的开销。设计要素：
- **核心线程数**：CPU 密集 ≈ 核数（多了反而抢核+切换）；IO 密集可更高（配合阻塞等待）。
- **任务队列**：生产者 push、worker pop。多 worker 下队列本身是竞争点（用无锁队列或每 worker 独立队列 + work stealing）。
- **拒绝/背压策略**：队列满时——阻塞生产者、丢任务、或扩容。游戏消息常"丢 + 告警"防雪崩。
- **优雅关闭**：停池时等待在途任务完成。
- **优先级/延迟任务**：用优先队列（最小堆）或时间轮。

游戏服务端常见：**IO 线程（Reactor）只做收发**，业务逻辑丢给**逻辑线程池**（或固定到"逻辑线程"串行处理同一玩家的操作，避免数据竞争）。

### 6. 协程 / 纤程

协程是**用户态轻量级并发单元**，切换不进内核（~ns 级），可在单线程内成千上万并发。
- **有栈协程**（goroutine、Lua coroutine、Boost.Coroutine/fiber）：每个协程有独立栈，挂起时保存栈/寄存器。
- **无栈协程**（C++20 coroutine、Python async/await、JS async）：编译器把协程转成状态机，挂起时把局部状态保存在堆上的协程帧（coroutine frame）里，无独立协程栈。

协程适合 **IO 密集、海量连接**（每连接一协程，IO 时挂起让出，不用线程）。局限：协作式（不主动让出就阻塞，除非运行时抢占，如 Go）；CPU 密集计算用协程无优势（还是要靠多核多线程）；与 C 互操作/调试更复杂。Go 的 goroutine + GMP 是"协程 + 多核并行 + 运行时抢占"的成熟方案（见第 3 章）。

### 7. 死锁、活锁、优先级反转

- **死锁**：四个必要条件——互斥、持有并等待、不可剥夺、循环等待。预防：**锁层次（lock ordering，总按固定顺序获取多把锁）**、避免持锁时回调/等待、用 `try_lock` + 超时回退、尽量缩小临界区、用一把锁代替多把。
- **活锁**：线程不断改变状态却无法推进（如都互相让、又互相抢，反复）。罕见但要识别。
- **优先级反转**：高优先级线程等待低优先级线程持有的锁，而中间优先级线程抢占低优先级线程 → 高优先级被间接"压低"。经典解法：**优先级继承**（低优先级持锁期间临时提升到等它的最高优先级线程的级别）。Mars Pathfinder 探测器就因这个翻车过。

工程铁律：**临界区尽量短、持锁时不做耗时操作（IO、回调、长计算）、明确锁层次、能无锁（消息/单线程串行）就别用锁。**

## 面试题

### 【专家】深挖追问 · 自旋锁 vs 互斥锁

> 什么时候用自旋锁、什么时候用互斥锁？自旋锁有哪些陷阱？

**参考思路**：
- **临界区极短（几十条指令）且竞争不激烈** → 自旋锁，省睡眠/唤醒的 µs 级切换开销。
- **临界区长或竞争激烈** → 互斥锁（睡眠），自旋会白烧 CPU。
- 陷阱：① **单核上自旋可能死锁**——持锁线程被抢占，自旋线程占着唯一的核忙等，持锁线程永远没机会运行；② 高竞争下自旋 → cache line ping-pong + CPU 浪费；③ 用户态纯自旋无上限会饿死。实践多用**自适应锁**（先自旋几次、拿不到再睡眠），Linux 内核 mutex 即如此。

**考点解析**：切换开销 vs 忙等代价的权衡、单核死锁、自适应锁。资深要能讲清"自旋不是更快"的条件。

**常见误区**：以为自旋锁总是更快；用户态无限自旋；单核环境用自旋。

**追问方向**：为什么内核态常用自旋而用户态慎用？（内核临界区极短且可能在中断/不可睡眠上下文；用户态临界区长度不可控、自旋浪费用户 CPU。）

### 【进阶】原理辨析 · 读写锁的陷阱

> 读写锁适合什么场景？有什么常见陷阱？

**参考思路**：读写锁允许多读者并发、写者独占，适合**读远多于写**的场景（配置、缓存、路由表）。陷阱：① **写者饥饿**——读者源源不断时写者永远拿不到锁（标准 RWLock 无写优先），数据迟迟更新不了；② 读者间的内部计数器竞争（false sharing）；③ 比 mutex 复杂、开销更大（要维护读者计数与写状态），**读写比不高时反而比 mutex 慢**。现代替代：读极多写极少时用 **RCU（Read-Copy-Update，读完全无锁、写时复制并择机回收旧版）**或 copy-on-write（写时整体复制一份不可变的，原子换指针，读端零同步）。

**考点解析**：读写锁的适用前提（读≫写）、写饥饿、RCU/COW 替代。资深要能判断"该不该用读写锁"。

**常见误区**：读写比不高也用 RWLock（更慢）；忽略写饥饿；不知道 COW/RCU 这类读端零开销方案。

**追问方向**：写很少、读极多且要低延迟读，COW 怎么做？（写时复制整个结构→原子换指针→旧版等读端退出后回收，读端只读指针、零锁。难点在旧版的安全回收。）

### 【专家】手撕代码 · 无锁 SPSC 环形队列

> 实现一个单生产者单消费者的无锁环形队列，并说明每处用什么 memory_order。

**参考思路**：
```cpp
template<class T, size_t N>
struct SpscQueue {
    alignas(64) std::atomic<size_t> head{0};   // 生产者写
    alignas(64) std::atomic<size_t> tail{0};   // 消费者写
    alignas(64) T buf[N];
    bool push(const T& v) {
        size_t h = head.load(std::memory_order_relaxed);
        size_t next = (h + 1) % N;
        if (next == tail.load(std::memory_order_acquire)) return false; // 满
        buf[h] = v;                              // 先写数据
        head.store(next, std::memory_order_release); // 再发布 head（release 保证数据对消费者可见）
        return true;
    }
    bool pop(T& out) {
        size_t t = tail.load(std::memory_order_relaxed);
        if (t == head.load(std::memory_order_acquire)) return false; // 空
        out = buf[t];                             // 先读数据
        tail.store((t + 1) % N, std::memory_order_release); // 再推进 tail
        return true;
    }
};
```
关键：head 只生产者写、tail 只消费者写（无竞争），靠 **release（写端）/acquire（读端）配对**保证"数据写入"在"索引发布"之前对另一端可见；`alignas(64)` 避免 head/tail false sharing。不用 seq_cst——acquire/release 足够且更便宜。

**考点解析**：SPSC 的"各写一个索引"无竞争设计、release/acquire 配对传递可见性、false sharing 对齐。资深要能讲清每处 order 的理由。

**常见误区**：全用 relaxed（消费者可能看到新 head 却读到未初始化数据）；head/tail 同一 cache line（false sharing）；用 seq_cst（不必要地贵）。

**追问方向**：扩展到多生产者多消费者（MPMC）会引入什么问题？（head/tail 多线程写 → 要 CAS + 处理 ABA + 节点回收，复杂度激增。）

### 【专家】深挖追问 · 死锁的必要条件与避免

> 死锁的四个必要条件是什么？工程上怎么避免？持锁回调为什么危险？

**参考思路**：四条件——① 互斥、② 持有并等待（拿了一把还想要另一把）、③ 不可剥夺（不能强行抢锁）、④ 循环等待。打破任一即可避免。工程手段：**锁层次（lock ordering）**——全局规定多锁的获取顺序，所有代码都按此顺序，打破循环等待；缩小临界区、用一把锁代替多把；用 `try_lock` + 超时回退；避免持锁时回调（回调可能反向调回本模块、再次尝试获取已持有的锁 → 自死锁，或调到未知代码里又取别的锁破坏层次）；避免持锁时做 IO/睡眠。**持锁回调危险**：被回调的代码不可控，可能重入或触发锁层次违反，是死锁/重入的高发源。

**考点解析**：四条件、锁层次打破循环等待、持锁回调的重入风险。资深要主动提出"持锁时不回调"。

**常见误区**：只知道加锁不知道锁层次；持锁时调用未知回调；多锁无序获取。

**追问方向**：怎么检测已发生的死锁？（运行时锁依赖图检测——记录每个线程持锁与等锁关系，发现环即死锁；或用死锁检测库/超时告警。）

### 【进阶】故障复盘 · 优先级反转

> 什么是优先级反转？怎么解决？

**参考思路**：场景——低优先级线程 L 持有锁，高优先级线程 H 等该锁；此时中优先级线程 M 就绪，抢占 L（因为 M>L）→ L 没机会运行、释放锁 → H 被 L 间接拖住，且 M 在跑，看起来像"H 比 M 慢"，严重时 H 长期饿死。经典案例：Mars Pathfinder 探测车因优先级反转反复重启。解法：**优先级继承**——H 等待 L 的锁时，把 L 的优先级临时提升到 H 的级别，让 L 能尽快跑完临界区释放锁，再恢复 L 原优先级。POSIX mutex 支持 `PTHREAD_PRIO_INHERIT`。

**考点解析**：优先级反转的链式机理、优先级继承解法。资深要知道这个经典并发坑。

**常见误区**：没听过优先级反转；以为高优先级一定先跑完；不知道优先级继承机制。

**追问方向**：普通用户态服务端（非实时调度）会遇到优先级反转吗？（用户态线程优先级由调度器管理，一般 SCHED_OTHER 不严格优先级，但锁导致的"间接阻塞高优先级任务"现象仍存在——本质是锁竞争调度延迟。）

### 【专家】系统设计 · 线程池设计

> 设计一个通用线程池。核心线程数怎么定？任务队列怎么设计？CPU 密集和 IO 密集区别？

**参考思路**：
- **核心线程数**：CPU 密集型 ≈ 核数（N），多了反而抢核+切换开销，甚至更慢；IO 密集型可远多于核数（线程在阻塞等 IO，CPU 空闲），经验值 `N × (1 + 等待/计算)`，或配合 IO 多路复用减少线程数。
- **任务队列**：单队列多 worker → 队列锁是竞争点；优化为**每 worker 独立队列 + work stealing**（自己队列空就去别人队列偷），减少竞争、提升 cache 局部性。
- **拒绝/背压**：队列满时——阻塞生产者、丢任务（+告警）、或动态扩容到上限。游戏消息队列常"丢+告警"防雪崩。
- **优雅关闭**：停止接受新任务、等在途完成。
- **延迟/周期任务**：最小堆或时间轮。
游戏服务端典型：IO 线程（Reactor）只收发，逻辑解包后投递到逻辑线程池；或按玩家/实体分片到固定逻辑线程串行处理（避免同玩家操作的数据竞争）。

**考点解析**：线程数与任务类型的关系、队列竞争与 work stealing、背压、IO 与逻辑分离。资深要能按任务特征定参数。

**常见误区**：线程数开越多越好（CPU 密集型会变慢）；任务队列无背压（OOM 或雪崩）；IO 和逻辑混在同一线程（互相阻塞）。

**追问方向**：怎么把"同一玩家的操作"串行化避免数据竞争，又不损失多核？（按玩家 id 分片到固定 worker，同一玩家总在同一 worker 串行处理，不同玩家并行。）

### 【进阶】原理辨析 · 条件变量为什么必须 while 循环

> 条件变量的 wait 为什么要放在 `while(!cond)` 循环里？什么是 spurious wakeup？

**参考思路**：`cv.wait(lock)` 可能在**没有 signal** 的情况下自行返回——这叫**虚假唤醒（spurious wakeup）**，POSIX 明确允许（实现上为简化信号处理/多处理器竞争）。所以被唤醒后**不能假设条件已成立**，必须重新检查 `cond`：用 `while(!cond) cv.wait(lock);`（或直接用 `cv.wait(lock, [&]{return cond;})` 这个带谓词的重载，它内部就是 while 循环）。另外，即使没有虚假唤醒，多个等待者被一次 `notify_all` 唤醒后只有一个能推进，其余必须重新等待——也要求 while 重新检查。还必须配合 mutex：wait 原子地"释放锁 + 阻塞"，唤醒后重新加锁。

**考点解析**：虚假唤醒、while 重新检查的必要性、wait 与锁的原子配合。资深要能讲清"为什么不能 if"。

**常见误区**：用 `if(!cond) cv.wait()`（虚假唤醒或竞态下越过条件）；wait 前不加锁；signal 和 wait 用了不同 mutex。

**追问方向**：notify_one 和 notify_all 怎么选？（notify_one 只唤醒一个等待者，适合一次只满足一个等待者的场景（如生产者放入一个任务），开销最小；notify_all 唤醒所有等待者，适合条件对多个等待者同时成立的广播事件（如关闭信号），但会带来惊群（thundering herd）——被唤醒者竞争同一把锁、多数立即重新阻塞。）

### 【专家】深挖追问 · 并发结构里的 false sharing

> 多线程各自频繁更新一个共享数组里的相邻元素，为什么慢？怎么避免？（呼应第 2 章）

**参考思路**：相邻元素落在同一 cache line，多核各自写自己的元素却因 **false sharing**（伪共享）让该 line 在核间反复 invalidate/迁移，写操作串行化，比单线程还慢。避免：让并发写的元素**各占一条 cache line**——`alignas(64)` 或显式 padding（每个计数器后塞 64B 填充）。C++17 用 `std::hardware_destructive_interference_size`。这是无锁结构、per-thread 计数器、统计聚合的高频性能坑。

**考点解析**：false sharing 机理、cache line 对齐修复。资深要在写并发结构时主动警惕。

**常见误区**：只看逻辑无关就以为无竞争；不知道 cache line；per-thread 计数器紧挨着放。

**追问方向**：怎么定位 false sharing？（perf c2c；或多线程 scaling 反常——核数加性能反降。）

### 【进阶】权衡 · 协程 vs 线程

> 什么时候该用协程？协程相对线程的优势和局限？

**参考思路**：
- **优势**：协程用户态切换（~ns，对比线程 µs）、栈小（KB 级）、可海量（十万百万级）；单线程内协程是协作式无锁（同时只跑一个，临界区天然安全）。适合 **IO 密集 + 海量连接**（每连接一协程，IO 时挂起）。
- **局限**：① 协作式——不主动 yield 就阻塞整线程（除非运行时抢占，如 Go）；② CPU 密集无优势（还是要多核多线程并行）；③ 一个协程的栈崩了可能影响所在线程；④ 与 C 互操作、调试更复杂。
- 线程适合 CPU 密集、需要真正并行、或调用阻塞式库（协程遇阻塞 IO 库会阻塞整个线程）。
现代选择：IO 密集海量并发 → 协程（goroutine/asio coroutine）；CPU 密集/系统级 → 线程；混合 → 线程做 CPU + 协程做 IO。

**考点解析**：协程的轻量与协作式本质、适用（IO 密集）与局限（CPU/阻塞库）。资深要能按任务类型选并发模型。

**常见误区**：以为协程总比线程好；在协程里调用阻塞 IO 库（阻塞整个线程）；忽略协程的协作式阻塞风险。

**追问方向**：C++20 协程和 Go goroutine 的关键区别？（C++20 协程是无栈协程+需自己写 promise/awaitable，无运行时调度器——要嵌入框架如 asio；goroutine 有 GMP 运行时调度+抢占，开箱即用。）

### 【专家】原理辨析 · ABA 问题

> 什么是 ABA 问题？在无锁栈里怎么发生？怎么解决？

**参考思路**：线程 1 读到值 A 准备 CAS；期间线程 2 把 A 改成 B 再改回 A；线程 1 的 CAS 看到"还是 A"就成功——但中间已变化，逻辑可能错。无锁栈 pop：`do { n=head; next=n->next; } while(!head.compare_exchange(n,next));`——若 n 被 pop 出去又 push 回来（A→B→A），CAS 仍成功，但 `next` 可能指向已释放/已改变的节点。解决：① **tag/版本号指针**——把版本和指针打包成一个原子值，每次改版本+1，CAS 一起比较版本+指针；② **hazard pointer / epoch reclamation**——保证 pop 出的节点在别的线程安全之前不被释放。实践中 128 位 DCAS（双字 CAS，装指针+版本）常见。

**考点解析**：ABA 的成因、tag 指针解法、节点回收难题。资深要能讲清"为什么值相同不代表没变"。

**常见误区**：以为 CAS 值相同就安全；忽略节点回收与 ABA 的关联；用 64 位指针 CAS 装不下版本号（要 128 位或折中）。

**追问方向**：为什么 ABA 在 GC 语言（Java/Go）里相对少？（GC 保证对象不被回收，指针相同即同一存活对象，但逻辑层 ABA 仍可能；C/C++ 无 GC，ABA 常伴随 use-after-free。）

### 【进阶】权衡 · 高读低写：读写锁、COW 还是 RCU

> 一个被大量线程读、偶尔写的全局结构（如路由表、配置），用什么同步？读写锁、copy-on-write、RCU 各怎么选？

**参考思路**：
- **读写锁**：实现简单，但读端仍要原子操作读者计数（有开销），且写饥饿风险；写稍频繁时退化。
- **copy-on-write（COW）**：写时整体复制一份不可变副本→原子换指针；读端只读指针、**零同步、零等待**。适合写极少、读极多、结构不太大。难点：旧版的回收（要等所有在用读端退出，用 epoch/hazard）。
- **RCU（Read-Copy-Update）**：读端完全无锁（甚至无原子）；写端复制修改后，等"所有读者都退出旧版"再回收（grace period）。Linux 内核高频用，用户态有 liburcu。读极重的终极方案，但回收时机复杂、调试难。
选型：读多写少且结构小 → COW（最简单、读零开销）；读极重、对延迟敏感、有库支持 → RCU；读写都不少或简单场景 → 读写锁或直接 mutex。

**考点解析**：三者读端开销（读写锁有计数/RCU 与 COW 读零开销）、写的代价、回收难点。资深要能按"读写比 + 读延迟要求"选型。

**常见误区**：读极重还用读写锁（计数开销）；COW 不回收旧版（内存泄漏）；忽略"读零开销"对热点路径的价值。

**追问方向**：COW 的旧版何时安全释放？（等所有"读指针时"的读端都退出读临界区——用 epoch 计数或引用计数，无法立即释放是 COW 的主要复杂度。）

> **本章小结**：并发的核心心法是"**能用单线程串行（消息驱动）就别共享；必须共享时优先锁、锁要短且有序；仅热点瓶颈经 profile 证实后才上无锁**"。同步原语的代价（自旋 vs 睡眠、读写锁的写饥饿）、无锁的正确性（CAS + acquire/release + ABA）、线程/协程模型的选型、死锁与优先级反转这些深水区，是区分中高级的关键——它们也是后续架构、性能、同步章节的基础。
