# 第7章 数据库与存储

> 游戏服务端的数据层不是"会写 SQL"就行——它要回答：玩家档案存 MySQL 还是 MongoDB？热数据怎么用 Redis 加速？分库分表的分片键怎么定？缓存和 DB 不一致怎么办？分布式锁怎么才正确？这些问题决定了服务的承载与稳定性，是面试中区分中高级的高频核心。

## 原理体系

### 1. MySQL InnoDB：索引、事务与 MVCC

**B+ 树索引**：InnoDB 用 B+ 树（非 B 树、非哈希）做索引。B+ 树的特点：只有叶子节点存数据、叶子间用链表串起（范围查询高效）、非叶子节点只存键（扇出大、树矮、IO 少）。**聚簇索引（clustered）**：叶子节点存**整行数据**，按主键组织——一张表只有一个，就是主键索引。**二级索引（secondary）**：叶子节点存主键值而非整行。通过二级索引查到主键后，若需要的列不在索引里，要**回表**（拿主键去聚簇索引查整行）——这是索引设计的核心成本点。**覆盖索引**：要查的列都在二级索引里，不用回表，最优。

**事务与 ACID**：原子性（undo log 回滚）、持久性（redo log 崩溃恢复）、隔离性（锁 + MVCC）、一致性（前三者保证）。

**隔离级别与 MVCC**：
- **RU（读未提交）**：能读到未提交数据（脏读）。
- **RC（读已提交）**：只读到已提交数据，但同一事务内两次读可能不同（不可重复读）。
- **RR（可重复读）**：同一事务内多次读结果一致（InnoDB 默认）。
- **Serializable（串行化）**：最强，加锁串行。

InnoDB 用 **MVCC（多版本并发控制）**实现 RC/RR 的"非阻塞读"：每行有多个版本（undo 链），事务根据其**读视图（read view）**决定看到哪个版本。RC 每次 SELECT 都建新 read view（所以看到最新已提交）；RR 在事务首次读时建 read view 并复用（所以可重复）。MVCC 让读不加锁、读写不互斥，是高并发读的关键。

### 2. MySQL 锁：行锁、间隙锁、临键锁

InnoDB 默认以**行级锁**为主（区别于 MyISAM 的表锁），锁粒度比"行"更细（细到记录/间隙/临键）；但也存在意向锁（IS/IX）、AUTO-INC 锁、外键约束加锁、显式 `LOCK TABLES`/DDL 等表级锁。主要锁类型：
- **记录锁（Record Lock）**：锁住某一行。
- **间隙锁（Gap Lock）**：锁住两行之间的**间隙**，防止别的事务往这里插入（防幻读）。
- **临键锁（Next-Key Lock）**= 记录锁 + 它前面的间隙锁，锁住"一个记录及其左开右闭区间"。

RR 隔离级别下，范围查询会用 next-key lock，**防止幻读**（别的事务插不进查询范围）。这是 RR 比 RC 更强的体现，代价是范围操作加锁范围大、并发降低。RC 下普通业务范围查询不再加间隙锁（间隙锁主要出现在 RR），所以 RC 并发更高但有幻读；严格说 RC 下外键约束检查、duplicate-key 检查等少数场景仍会产生间隙锁。

**死锁**：InnoDB 会自动检测死锁并回滚代价小的事务（`innodb_deadlock_detect`）。业务上要避免长事务、固定加锁顺序。

### 3. 慢查询与执行计划

用 `EXPLAIN` 看执行计划，关注：
- **type**：访问类型，从好到差：`const` > `eq_ref` > `ref` > `range` > `index`（扫整棵索引树）> `ALL`（全表扫描）。`ALL` 通常要优化。
- **key**：实际用的索引（NULL = 没走索引）。
- **rows**：估算扫描行数。
- **Extra**：`Using index`（覆盖索引，好）、`Using filesort`/`Using temporary`（差，需排序/临时表）。

索引失效的常见场景：函数操作列（`WHERE func(col)`）、隐式类型转换、`LIKE '%xxx'`（前缀通配）、`OR` 中部分列无索引、违反最左前缀（联合索引没用上前导列）、`!=`/`NOT IN`（往往全扫）。

### 4. 分库分表

单库单表到瓶颈（千万级行、写压力、单机存储）时拆分：
- **垂直分库**：按业务拆（用户库、战斗库、社交库到不同实例）。
- **垂直分表**：把宽表拆成多个窄表（热列与冷列分开）。
- **水平分表（sharding）**：按某规则把数据分散到多个表/库。**分片键（shard key）**选择是核心——玩家 id 最常见，让同一玩家的数据落在同一分片。

难点：**跨分片查询/分页/聚合**（如"全服排行榜"要汇总所有分片）、**分布式事务**（跨分片写）、**扩容迁移**（一致性哈希缓解）。游戏典型：按玩家 id 分片玩家档案；排行榜、跨服数据另用专门方案（Redis ZSET、汇总表）。

### 5. MongoDB：文档模型与分片

MongoDB 是**文档数据库**（BSON），schema 灵活（字段可变），适合**结构不固定、嵌套深、迭代快**的数据——如玩家背包（道具组合多变）、活动配置、日志。

- **分片（sharding）**：按 shard key 分散数据到多个 shard，mongos 路由。shard key 选择决定分布均匀度与查询是否要广播。
- **副本集（replica set）**：主从复制 + 自动故障转移。
- **聚合管道（aggregation pipeline）**：`$match`/`$group`/`$sort` 等流水线处理，适合分析型查询。

何时选 MongoDB 而非 MySQL：schema 频繁变、嵌套对象多、读写模式偏 KV/文档、不想为 schema 迁移头疼。何时坚持 MySQL：强事务、复杂关联（join）、成熟稳定要求高。游戏里常见 MySQL 存核心账务 + MongoDB 存背包/日志的混合。

### 6. Redis：数据结构、持久化与集群

Redis 是**内存 KV**，单线程模型（命令串行执行，无锁；6.0 后网络 IO 多线程，命令执行仍单线程），极快。核心是丰富的**数据结构**：
- **string**：缓存、计数器。
- **hash**：对象存储（玩家档案的字段级读写）。
- **list**：消息队列、最近访问。
- **set/zset**：集合 / **有序集合（跳表）**——排行榜标配。
- **stream/hyperloglog/bitmap**：流、基数统计、位统计。

**持久化**：
- **RDB**：周期性全量快照（fork 子进程 dump）。恢复快、文件小；缺点：崩溃丢最近一段。
- **AOF**：记录每条写命令（可每秒/fsync）。更安全；缺点：文件大、恢复慢。
- **混合（4.0+）**：AOF 前面是 RDB 全量、后面增量命令，兼顾。生产主流。

**高可用**：
- **主从复制**：读写分离、备份。
- **哨兵（Sentinel）**：监控主、主挂自动选从提升，实现自动故障转移（单实例主从的场景）。
- **Cluster**：分片集群（16384 个 slot 分散到多主多从），横向扩展 + 高可用。大规模用 Cluster。

### 7. 缓存问题：穿透、击穿、雪崩

缓存三大经典故障：
- **穿透（penetration）**：查**根本不存在**的数据，每次都穿到 DB（恶意攻击或 bug）。解法：**布隆过滤器**前置拦截不存在的 key、或缓存 null 值（短过期）。
- **击穿（breakdown）**：**某个热点 key** 突然过期，瞬间海量请求打到 DB。解法：热点 key **永不过期** + 异步刷新、或**互斥锁**（只让一个请求回源 DB、其余等待）。
- **雪崩（avalanche）**：**大量 key 同时过期**或 Redis 宕机，请求全打到 DB。解法：过期时间**加随机抖动**避免同时失效、多级缓存、Redis 高可用（哨兵/Cluster）、**限流降级**兜底。

### 8. 缓存与 DB 一致性

更新数据时缓存怎么同步？常见**Cache-Aside**：
- **读**：先查缓存，miss 则查 DB 并回填。
- **写**：**先更新 DB，再删除缓存**（不是更新缓存——更新缓存有并发覆盖问题，且写多读少时浪费）。

为什么删而不是更新？并发下"更新缓存"易出现 A、B 两个写先后到、缓存被旧值覆盖的竞态；删缓存让下次读自然回源最新值。仍有极小窗口的不一致（读 miss 后回填旧值），可用**延迟双删**（更新DB后删缓存、延迟一段时间再删一次）缓解。强一致场景要加分布式锁或接受最终一致。**记住：缓存与 DB 的强一致几乎不可能，工程上追求"最终一致 + 短暂不一致可接受"。**

### 9. 分布式锁

用 Redis 实现分布式锁：`SET key value NX PX timeout`（原子地"不存在则设置 + 过期"）。value 用唯一标识，释放时用 Lua 脚本"判 value 相等才删"（避免误删别人的锁）。过期时间要覆盖业务执行；业务超时要考虑**锁续期**（watchdog）。

**Redlock**（作者提的多节点版）：向 N 个独立 Redis 实例加锁，多数成功才算成功。但有争议（时钟漂移、GC pause 导致持锁者误判），生产慎用。游戏服务端分布式锁更常用**单 Redis + 业务幂等**或**基于 etcd/zk 的强一致锁**。

## 面试题

### 【专家】深挖追问 · InnoDB 的 B+树与索引

> InnoDB 为什么用 B+ 树而不是 B 树或哈希？聚簇索引和二级索引的区别？什么是回表和覆盖索引？

**参考思路**：B+ 树相比 B 树：数据只存叶子、叶子用链表串起 → **范围查询高效**（遍历链表）；非叶子只存键 → 扇出大、树矮（3-4 层就能撑亿级行）→ IO 次数少。哈希索引 O(1) 但不支持范围/排序，不适合通用 DB。**聚簇索引**：叶子存整行，按主键组织，一张表一个。**二级索引**：叶子存主键值。通过二级索引查非索引列要**回表**（二次查聚簇索引）。**覆盖索引**：查询所需列全在二级索引里，不用回表，最优。

**考点解析**：B+ 树的结构优势（范围、扇出）、聚簇 vs 二级、回表成本。资深要能据此设计索引（尽量覆盖、避免回表）。

**常见误区**：以为索引越多越好（写放大、占空间）；不知道二级索引要回表；混淆聚簇与主键（主键即聚簇，但聚簇是概念）。

**追问方向**：联合索引的"最左前缀"是什么？为什么 `WHERE b=?` 用不上 `(a,b)` 联合索引？（B+ 树按 a 再按 b 排，跳过 a 无法二分定位 b。）InnoDB 还有哪些影响索引/写性能的关键机制？（change buffer 缓存二级索引非唯一的变更、延迟合并到磁盘，提升随机写；buffer pool 的 LRU 分 young/old 区防全表扫描冲刷、可预热；adaptive hash index 对热点页自动建哈希索引；doublewrite buffer 防页撕裂。）

### 【进阶】原理辨析 · 隔离级别与 MVCC

> 四种隔离级别分别解决什么问题？InnoDB 的 RR 如何用 MVCC 避免不可重复读？

**参考思路**：RU（脏读）/ RC（不可重复读）/ RR（幻读，InnoDB 默认）/ Serializable（串行）。MVCC 给每行维护多个版本（undo 链），事务按**读视图 read view** 决定看到哪个版本。RR 在事务**首次**读时建 read view 并复用整个事务，所以多次读同一行都看到同一版本（可重复）；RC 每次 SELECT 都建新 read view，所以能看到别的事务新提交的（不可重复）。MVCC 让读不加锁、不阻塞写，是高并发读的关键。

**考点解析**：各级别解决的异常、read view 的建立时机（RC 每读 vs RR 首次读）。资深要能讲清 RR 怎么做到可重复。

**常见误区**：以为 RR 完全没有幻读（标准 RR 有，InnoDB 用 next-key lock 在当前读场景额外防幻读）；混淆快照读（MVCC）与当前读（加锁）。

**追问方向**：RR 下 `SELECT ... FOR UPDATE` 还能防幻读吗？（能——当前读会用 next-key lock 锁住范围，阻止插入。普通 SELECT 是快照读，靠 MVCC。）read view 的可见性判定算法是怎样的？（read view 记录生成时的活跃事务数组 `m_ids`、最小活跃事务 id `up_limit_id`（= min(m_ids)）、下一个将分配的事务 id `down_limit_id`（= max(m_ids)+1）。对某行版本的 `trx_id`：① < up_limit_id → 该版本在 read view 生成前已提交，可见；② ≥ down_limit_id → 在 read view 之后才开启，不可见；③ 落在 [up_limit_id, down_limit_id) 且不在 m_ids 中 → 已提交，可见；④ 在 m_ids 中 → 仍未提交，不可见，沿 undo 链找更早版本再判。这是 MVCC 真正的深挖点。）

### 【专家】深挖追问 · InnoDB 的行锁/间隙锁/临键锁

> 行锁、间隙锁、临键锁分别锁什么？RR 怎么防幻读？RC 为什么并发更高？

**参考思路**：记录锁锁单行；间隙锁锁两行之间的间隙（防插入）；临键锁 = 记录锁 + 前间隙（锁一个左开右闭区间）。**RR** 下范围查询用 next-key lock 锁住查询范围及间隙，别的事务插不进 → **防幻读**，代价是锁范围大、并发降。**RC** 下普通业务范围查询不再加间隙锁，只锁命中的行，并发更高，但范围查询时别的事务能插入新行（幻读）；严格说 RC 下外键约束检查、duplicate-key 检查等少数场景仍会产生间隙锁。游戏业务里，若能接受幻读、追求高并发，可考虑降到 RC。

**考点解析**：三种锁的范围、RR 防幻读的代价（锁范围大）、RC 的并发优势。资深要能权衡隔离级别。

**常见误区**：以为 RR 完全没锁代价（范围锁降低并发）；以为间隙锁只在 RR（严格说 RC 下外键/duplicate-key 检查仍会产生间隙锁，但普通范围查询不再加 next-key lock）；用 RC 时忽略幻读风险。

**追问方向**：什么场景下间隙锁会造成意外的锁冲突？（RR 下两个事务范围更新不相交的数据却因间隙重叠互锁——业务上要明确查询条件、必要时降 RC。）

### 【进阶】故障复盘 · 慢查询定位

> 接口越来越慢，怀疑 SQL 慢查询。怎么排查？常见的索引失效有哪些？

**参考思路**：开慢查询日志抓慢 SQL → `EXPLAIN` 看执行计划：type 是否 ALL（全表扫）、key 是否 NULL（没走索引）、rows 是否巨大、Extra 是否 Using filesort/temporary。常见索引失效：① 对索引列做函数/运算（`WHERE YEAR(t)`）；② 隐式类型转换（字符串列传数字）；③ `LIKE '%xx'`（前缀通配）；④ `OR` 部分列无索引；⑤ 联合索引违反最左前缀；⑥ `!=`/`NOT IN` 往往放弃索引。修复：加合适索引、改写查询、避免失效写法。注意索引不是越多越好（写放大）。

**考点解析**：EXPLAIN 的关键字段、索引失效的典型场景。资深要能从慢日志到执行计划到优化形成闭环。

**常见误区**：只看有没有索引不看是否生效；建一堆索引不管写放大；忽略 EXPLAIN 的 rows 估算。

**追问方向**：为什么 `WHERE col + 1 = 5` 不走索引但 `WHERE col = 4` 走？（前者对索引列做运算，B+ 树无法按变换后的值定位。）

### 【专家】系统设计 · 玩家数据分库分表

> 千万级玩家、单库扛不住，怎么分库分表？分片键怎么选？跨分片的排行榜/分页怎么办？

**参考思路**：按**玩家 id** 水平分片（玩家 id 取模或一致性哈希路由到分片），保证同一玩家数据在同一分片（事务、查询局部化）。分片数预留扩容余量（如一开始 16 分片，扩容时翻倍 + 数据迁移，一致性哈希可减少迁移）。**跨分片难题**：① **全服排行榜**——不能扫全部分片，改用 Redis ZSET 维护全服排名（玩家分数变更时同步）；② **跨分页**——`LIMIT offset` 跨分片无法直接做，用游标分页（按 id/时间游标）或汇总表；③ **跨分片事务**——避免，或用最终一致（消息+对账）。运维：分片路由中间件（自研 proxy 或 ShardingSphere 的 Sharding-JDBC/Proxy；MyCAT 社区已停滞维护，仅作历史提及）。

**考点解析**：分片键选择（玩家 id 的局部性）、跨分片查询的替代方案、扩容迁移。资深要主动指出"排行榜/跨服查询不能靠扫分片"。

**常见误区**：分片键选错导致热点（如按时间分片，最新分片爆）；跨分片扫全表做排行榜（慢且压垮库）；不留扩容余量。

**追问方向**：玩家 id 分片下，"查某个公会所有成员"（成员跨分片）怎么办？（建公会→成员的反向索引表/汇总，或公会数据独立分片。）跨分片事务（如跨服交易、合服）怎么处理？（避免优先；实在要跨则用 2PC/TCC/Saga/本地消息表+对账兜底，按一致性强度与吞吐取舍，游戏跨服交易多用最终一致 + 业务幂等。）MySQL 主库高可用有哪些形态、缓存怎么跟着 DB 刷新？（MGR 组复制基于 Paxos 强一致、MHA 监听主库故障自动切从、Orchestrator 编排拓扑；用 canal 订阅 binlog 异步刷新/失效缓存，形成"DB → binlog → canal → 缓存/对账"链路。）

### 【进阶】权衡 · MongoDB vs MySQL

> 什么数据适合存 MongoDB？玩家背包为什么常用文档库？

**参考思路**：MongoDB 优势在 **schema 灵活**（字段可变、嵌套深）、迭代快、读写偏文档。玩家背包：道具种类/数量/镶嵌/强化属性组合多变、嵌套结构复杂、schema 频繁演进——存 MySQL 要频繁改表/加列、join 麻烦；存 MongoDB 一个文档表示一个背包、改 schema 不影响旧数据、读写整体高效。其他适合：活动配置、运营日志、灵活属性。坚持 MySQL：强事务（账务、交易）、复杂 join、极高稳定性要求。游戏典型混合：**MySQL 存账务/核心关系数据 + MongoDB 存背包/日志/灵活数据**。

**考点解析**：文档库的灵活 schema 优势、何时该用、何时不该。资深要能按数据特征（结构稳定 vs 灵活多变）选型。

**常见误区**：所有数据塞 MongoDB（事务/join 弱）；玩家背包存 MySQL 改 schema 痛苦；忽略 MongoDB 的事务限制。

**追问方向**：MongoDB 的事务支持如何？（4.0+ 支持多文档事务，但性能弱于 MySQL，强事务场景仍选关系库。）读写一致性如何控制？（write concern `w:1/majority`、read concern `local/majority/linearizable`、read preference 控制从哪个节点读；WiredTiger 用 MVCC + snapshot isolation，{w:majority} + {read:majority} 才能读到不回滚的持久值。）选 shard key 有哪些坑？（不可变、决定数据分布与是否广播查询；选错导致 jumbo chunk、热点分片。）索引类型？（compound/text/geo/TTLS 等，按查询模式建。）

### 【进阶】深挖追问 · Redis 持久化与高可用

> RDB 和 AOF 各自的优缺点？混合持久化是什么？主从、哨兵、Cluster 怎么选？

**参考思路**：RDB（快照）恢复快、文件小、fork 开销大、崩溃丢最近一段；AOF（追加命令）更安全（最多丢 1 秒）、文件大、恢复慢；混合（4.0+）= AOF 文件 = RDB 全量 + 增量命令，兼顾恢复速度与安全性，生产主流。高可用：**主从**（读写分离、备份，主挂要手动）；**哨兵 Sentinel**（监控 + 自动故障转移，适合单分片主从）；**Cluster**（slot 分片到多主多从，横向扩展 + 自动转移，大数据量/高吞吐必选）。选型：数据量小、单分片够 → 主从+哨兵；数据量大、要扩展 → Cluster。资深可进一步深挖：① RDB/AOF 的 `fork` 子进程依赖操作系统的 COW（copy-on-write），大内存实例 fork 本身耗时长且写多时物理内存可能翻倍，是单机实例上限的关键约束；② 主从复制为异步，断连重连后通过 **psync2**（replid + offset）做部分重同步，避免每次全量；③ Cluster 故障检测基于 gossip 协议，节点间互报 `PFAIL`（主观下线），过半数标记后升级为 `FAIL`（客观下线）并触发从节点选举；④ 脑裂（网络分区下旧主仍接受写）需配合 `min-slaves-to-write` 类参数，否则分区恢复时旧主数据会被丢弃。

**考点解析**：两种持久化的权衡、混合持久化、三种高可用形态的适用规模。资深要能按数据量与可用性要求选型，并触及 fork COW、psync2 部分重同步、Cluster gossip 故障检测等底层细节。

**常见误区**：只用 RDB（崩溃丢数据）；AOF 不重写（文件膨胀）；该用 Cluster 时还在单机哨兵；忽略大内存实例 fork COW 的内存翻倍风险。

**追问方向**：Redis 主从复制是同步还是异步？全量同步怎么发生？（异步复制（默认），可能丢数据；全量同步 = 主 bgsave 生成 RDB 发给从 + 缓存期间增量命令补发。）

### 【进阶】故障复盘 · 缓存穿透/击穿/雪崩

> 三者区别？分别怎么防？

**参考思路**：
- **穿透**：查不存在的数据穿到 DB。防：布隆过滤器前置（拦截不存在的 key）、缓存 null（短过期）。
- **击穿**：单热点 key 过期瞬间被打。防：热点 key 永不过期 + 异步后台刷新、或互斥回源（只一个请求查 DB 其余等）。
- **雪崩**：大量 key 同时过期 / Redis 宕机全压 DB。防：过期时间加随机抖动、多级缓存、Redis 高可用、限流降级兜底。
三者核心区别：穿透是"查不存在"、击穿是"单热点失效"、雪崩是"批量失效/整体宕"。面试要能精确区分并各给解法。

**考点解析**：三者成因的精确区分、各自解法。资深要能说清"穿透 vs 击穿 vs 雪崩"的不同，并能结合游戏场景复盘真实案例。

**常见误区**：三者混为一谈；解法张冠李戴（用布隆防雪崩）；忽略限流降级这个兜底。

**追问方向**：热点 key 怎么识别？（监控 key 访问 QPS、Redis 的 LFU 计数、或业务侧预判——排行榜榜首、热门活动。）游戏场景追问：开服瞬间批量预热的 key 同时失效、全服公告/活动发放打到一个 key 形成 hot-key（解法：本地缓存 + 多副本 key 打散，如 `rank:1:{0..N}` 分片）、布隆过滤器容量与误判率的工程权衡（n 与 p 决定 bit 数和 hash 数，误判会放行少量穿透）。

### 【专家】深挖追问 · 缓存与 DB 一致性

> 更新数据时，先更新 DB 再删缓存，还是先删缓存再更新 DB？为什么不更新缓存？延迟双删解决什么？

**参考思路**：主流是**先更新 DB 再删缓存**。为什么不更新缓存：① 并发下两个写先后到、缓存被旧值覆盖（竞态）；② 写多读少时频繁更新缓存浪费。删缓存让下次读自然回源最新值。**延迟双删**：解决"先删缓存再更新 DB"或极端时序下，读 miss 回填旧值的窗口——更新 DB 后先删一次、延迟一段（覆盖读回填窗口）再删一次。强一致几乎做不到，工程追求**最终一致 + 短暂不一致可接受**；要更强则加分布式锁或用 binlog 订阅（canal）异步刷新缓存。

**考点解析**：删 vs 更新的理由、延迟双删、最终一致的现实。资深要能讲清"为什么强一致不现实"。

**常见误区**：更新缓存（并发竞态）；以为删缓存就一致了（仍有短暂窗口）；强求强一致忽略成本。

**追问方向**：先删缓存再更新 DB 有什么问题？（删了缓存后、更新 DB 前，另一请求读 miss 回源旧 DB 值并回填，缓存又变旧。延迟双删缓解。）

### 【专家】系统设计 · Redis 分布式锁

> 用 Redis 实现分布式锁怎么做？有什么陷阱？Redlock 为什么有争议？

**参考思路**：基础版：`SET lock value NX PX timeout`（原子加锁 + 过期），value 用**唯一标识**（如 UUID+线程），释放用 Lua 脚本"判 value 相等才删"（防误删别人的锁）。陷阱：① 业务执行超时、锁自动过期、别人加锁 → 误删（用 value 校验+Lua 防误删）；② 过期时间难定，要**看门狗续期**（业务未完成周期续）；③ 单点故障（Redis 主从异步复制，主挂从晋升可能丢锁）。**Redlock**：向 N 个独立实例加锁、多数成功才算成功，试图解决单点。争议：时钟漂移、GC/进程暂停导致持锁者误判锁仍持有，正确性证明有漏洞（Martin Kleppmann 质疑）。生产实践中，**不强一致**的锁用单 Redis 足够（配合业务幂等）；**强一致**用 etcd/zk（基于 Raft/ZAB）。

**考点解析**：加锁的原子性、释放的 value 校验、续期、单点问题、Redlock 争议。资深要能指出每一步的陷阱。

**常见误区**：`SETNX` + `EXPIRE` 两步非原子（崩溃丢过期 → 死锁）；释放锁不校验 value（误删）；以为 Redis 锁强一致。

**追问方向**：为什么释放锁必须用 Lua 而不能"GET 判断 + DEL"？（GET 和 DEL 之间可能被别人改，非原子；Lua 在 Redis 单线程内原子执行。）

### 【进阶】权衡 · 玩家档案存哪里

> 玩家的账号信息、档案、背包、关系、热数据（在线状态/分数），分别适合存 MySQL、MongoDB 还是 Redis？

**参考思路**：按数据特征选：
- **账号/认证/账务**（强一致、强事务）→ **MySQL**。
- **玩家档案/背包**（灵活 schema、嵌套、频繁演进）→ **MongoDB**（或 MySQL JSON 字段，量大用 Mongo）。
- **关系链/社交**（图状、关联查询）→ 关系库或图数据库，简单场景 MySQL。
- **热数据**（在线状态、实时分数、会话）→ **Redis**（低延迟、高频读写）。
- **排行榜**→ Redis ZSET。
- **日志**→ MongoDB / 专用日志系统（ES）。
混合架构是常态：MySQL 兜底一致、MongoDB 存灵活数据、Redis 加速热路径。关键是**按访问模式与一致性要求分层**，而非一种库打天下。

**考点解析**：按数据特征（一致性/schema/访问频率）分层选型。资深要能给出有依据的混合方案。

**常见误区**：全塞一种库；把热数据放 MySQL（慢）；把强事务数据放 Redis（不一致风险）。

**追问方向**：玩家上线时怎么把档案从 DB 加载到内存/Redis 热起来？（按需加载 + 缓存回填 + 下线时脏写回 DB；要防丢（写 DB 成功再清缓存）。）读写分离下主从延迟导致读到旧值（如充值到账延迟）怎么办？（成因：异步复制 + 从库 binlog apply 滞后；解法：对延迟敏感的读强制走主（写后短时间内的读、或会话级粘性）、半同步复制至少等一个从库 ack、关键路径不读写分离。）Redis 大 key / 热 key 怎么办？（大 key：`redis-cli --bigkeys` / `MEMORY USAGE` 发现、拆成小 hash、删除用 `UNLINK` 异步避免阻塞主线程；热 key：本地缓存兜底、多副本 key 打散到不同节点。）

---

> **本章小结**：数据层的主线是"**按数据特征分层选型 + 用缓存加速 + 管好一致性与高可用**"。MySQL 的索引/事务/MVCC/分片、MongoDB 的灵活文档、Redis 的结构与缓存三板斧（穿透/击穿/雪崩）和分布式锁，是服务端数据层的核心。记住两条心法：**强一致用关系库、灵活/热数据用文档/KV**；**缓存与 DB 追求最终一致，不追求不可能的强一致**。
