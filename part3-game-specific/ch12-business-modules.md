# 第12章 核心业务模块

> 框架与底层是地基，业务模块是房子。登录、背包、交易、匹配、排行榜、活动、商城、跨服、聊天——这些是玩家每天接触的系统，也是面试系统设计题的主战场。本章按模块梳理核心设计点与高频陷阱，培养"给需求→出方案→讲清权衡"的能力。

## 原理体系

### 1. 登录与网关

- **登录流程**：客户端带账号凭据 → 鉴权服务校验（账号密码/token/OAuth）→ 签发**会话令牌（token/ticket）**→ 客户端凭令牌连游戏服。常见拆分：**登录服**（鉴权、发 token）与**网关（gateway）**（维持长连接、路由到逻辑服）分离。
- **网关职责**：维持海量客户端长连接、解包/加密、按玩家路由到对应逻辑服（或跨服）、做限流/防刷。网关无状态或轻状态，方便水平扩展。
- **防刷**：登录限流（IP/账号频率）、验证码、设备指纹、异常登录检测（异地）。

### 2. 背包与道具系统

背包是高频且易错系统。设计要点：
- **格子 vs 容量**：固定格子数（可扩容）+ 每格叠堆上限。或无格子的"容量/重量"模型。
- **叠堆（stack）**：可叠道具（消耗品）合并占一格，不可叠（装备）独占一格。
- **事务性**：增删改道具必须**原子**（尤其涉及交易、合成、掉落），不能"扣了材料没给产物"。通常用 DB 事务 + 操作日志。
- **唯一性/绑定**：装备绑定（拾取/装备后不可交易）、唯一道具（每人只能有一个）。
- **排序/分类/查找**：道具多时要高效查询（按类型、id）。

### 3. 战斗与数值系统

- **数值配置驱动**：伤害公式、属性、技能效果应**数据驱动**（配置表），策划改数值不改代码、可热更。
- **战斗结算**：服务端权威算伤害/命中（见第 9、10 章）；客户端做表现。
- **数值平衡**：DPS、属性曲线、成长公式要可分析、可回溯。

### 4. 匹配系统

- **匹配目标**：把实力相近的玩家配对，保证公平 + 等待时间合理。
- **评分**：ELO/MMR（根据胜负动态调整的实力分）。
- **匹配池**：按段位/模式分池，扩窗匹配（开始严格、超时逐步放宽范围，平衡公平与等待）。
- **组队**：队伍平均分 + 队伍人数权重。

### 5. 排行榜

- **实时性**：分数变化即时反映排名。
- **规模**：千万级玩家，要高效更新与查询。
- **实现**：Redis **ZSET**（跳表）天然适合——`ZADD` 更新分数、`ZREVRANGE` 取前 N、`ZREVRANK` 查某玩家名次，都 O(log n)。千万级用 ZSET + 分段/分片。
- **实时 vs 快照**：前列实时精确，尾部可定时快照近似。

### 6. 活动与任务

- **限时活动**：开启/结束时间精确，开启瞬间有**流量洪峰**（大量玩家同时涌入）。
- **任务系统**：条件触发（杀怪/收集/到达）、进度追踪、奖励发放（注意防重复领取/防刷）。
- **配置化**：活动/任务配置表驱动，运营可动态开/关、调奖励，不重启。

### 7. 商城、交易与经济系统

- **交易**：玩家间/玩家与系统。核心是**原子性与防超卖/防回档**（见下文题）。
- **经济系统**：货币的**产出与消耗平衡**——产出（打怪/任务/活动）与消耗（强化/购买/修理）要匹配，否则通货膨胀（货币贬值）或紧缩。要有数据监控产出消耗比、可调节水龙头（产出）与下水道（消耗）。
- **商城**：直购、限购、抽奖（注意法规与概率公示）。

### 8. 跨服

- **跨服战场/副本**：玩家从本服"迁移"到跨服进程，结束后回本服。核心是**数据一致性**——跨服期间的战斗结果要正确同步回本服，玩家状态不能丢/冲突。
- **跨服匹配/排行**：全服范围，需汇总各服数据。

### 9. 聊天系统

- **频道**：世界/公会/私聊/队伍/附近。世界频道是**广播放大器**（一人发言全服收），要控成本（限频、分线路由）。
- **敏感词**：过滤（AC 自动机，见第 4 章）+ 变体处理。
- **百万在线广播**：不能一人发全员收，要分线路由（按线路/分片聚合）、必要时丢弃非关键消息。

### 10. GM 后台与运营工具

- **GM 指令**：封号、发奖、改数值、踢人、查日志——必须有**审计日志**（谁、何时、做了什么），防滥用。
- **运营工具**：开服/合服、活动配置、数据统计、客服查询。要与游戏服解耦（HTTP 后台 + 内部 RPC）。

## 面试题

### 【专家】系统设计 · 背包系统

> 设计一个背包系统：支持扩容、叠堆、增删改查。怎么保证道具操作的事务性？

**参考思路**：数据模型——按玩家存道具列表（id/数量/绑定/唯一标识/位置）。叠堆：可叠道具记数量、合并占格；不可叠每件独占一格（带实例 id）。扩容：格子数存玩家表，扩容道具消耗后加格子。**事务性**是核心：增删改（尤其合成/交易/掉落涉及多道具）必须在**一个 DB 事务**里完成——要么全成要么全失败，配合**操作日志/流水**用于审计与对账。注意：操作前校验（格满？材料够？）、操作原子化、并发安全（同玩家操作串行化，避免竞态，见第 6 章"按玩家分片串行"）。唯一道具/绑定要在操作中校验。资深常用两手段：① **操作日志（oplog）+ 单调递增 op 序号**——每条道具变更记 op，客户端带 op 序号做 delta 对账与断线重放（客户端报"我已到 op=k"，服务端只回 k 之后的变更），避免重连后全量同步；② **版本号/乐观锁**——背包带版本号，提交时 `WHERE version=?` CAS，与串行化/悲观锁相比并发更高、适合冲突稀疏场景，冲突时重试。

**考点解析**：叠堆/格子模型、DB 事务保证原子性、并发串行化。资深要主动讲"道具操作要事务、要串行化"。

**常见误区**：分多条 SQL 无事务（中途失败数据错乱）；同玩家操作不串行（竞态刷道具）；忘记唯一性/绑定校验。

**追问方向**：玩家背包有 1000 格道具，怎么高效同步给客户端？（只发变化 delta；初次全量后增量；按页/分类懒加载。）

### 【专家】系统设计 · 交易系统防超卖与防回档

> 设计玩家间交易。怎么保证不超卖、不回档、原子完成？

**参考思路**：交易是典型"多方资源原子转移"问题。核心：① **预检 + 锁定**——双方确认后，把要交易的道具/货币**锁定**（标记"交易中"，不可再动）。② **原子提交**——扣 A 给 B、扣 B 给 A 在**一个分布式/本地事务**里完成。③ **防超卖**——锁定 + 原子扣减，避免同一道具被多次交易。④ **防回档**——DB 提交成功前不让客户端认为成功；提交后写**流水日志**，崩溃恢复时按日志对账。⑤ **双方确认 + 超时取消**——任一取消/超时则解锁回滚。跨服交易还要分布式事务（两阶段/最终一致 + 对账）。游戏交易常用"**交易锁 + 单玩家串行 + 事务 + 流水**"组合。

**考点解析**：锁定防超卖、事务原子性、流水防回档、双方确认/超时。资深要能讲清"为什么不能直接扣"（并发竞态）。

**常见误区**：先扣 A 再给 B（中途失败，A 没了 B 没收到）；无锁导致同一道具多交易；无流水，崩溃后无法恢复。

**追问方向**：交易过程中一方掉线，怎么处理？（超时自动取消 + 解锁回滚；已锁定的资源不能因掉线丢失——靠服务端权威状态，不依赖客户端。）

### 【专家】系统设计 · 匹配系统

> 设计一个匹配系统（如 5v5）。怎么保证公平 + 等待时间合理？

**参考思路**：① **实力分**：用 ELO/MMR，胜负动态调整（赢了加分、输了扣，按对手实力加权）。② **匹配池**：按模式/段位分池，待匹配玩家进池。③ **扩窗策略**：进池时严格按 MMR 范围找对手；**超时逐步放宽范围**（如每 10s 放宽 100 分），平衡公平（窄窗）与等待（宽窗）。④ **组队**：取队伍平均 MMR + 人数权重（5 人队匹配 5 人队优先）。⑤ **十人凑齐**：从池里选 MMR 接近的凑成对局。⑥ **防连胜/连败保护**：避免高手连续碾压新手。⑦ **区域/延迟路由**：同区服/低延迟优先匹配，超时再跨区放宽——这是公平（实力）与手感（延迟）的权衡，跨区对局延迟高影响体验。⑧ **角色位补位**：分位置（坦克/输出/辅助）匹配，先按位补满、位冲突时让位或拓宽等待，平衡"队伍位型合理"与"等待时长"。监控：匹配等待时长分位、对局实力差分布、跨区比例、补位比例，调扩窗与路由参数。

**考点解析**：MMR/ELO、扩窗平衡公平与等待、组队权重。资深要能讲清"等待久了放宽范围"的工程权衡。

**常见误区**：永远严格匹配（等待过长）；组队不按人数（不公平）；忽略等待时长监控。

**追问方向**：深夜玩家少，匹配池空，怎么避免无限等待？（扩窗到全局、补机器人（AI）凑数、或提示玩家改时段——按产品定，但要保证有出口。）

### 【专家】系统设计 · 千万级排行榜

> 千万玩家、分数频繁变动、要实时查名次与前 N。怎么设计？

**参考思路**：**Redis ZSET** 是核心——分数变动用 `ZADD`（O(log n)）、查前 N 用 `ZREVRANGE`（O(log n + N)）、查某玩家名次用 `ZREVRANK`（O(log n)）。千万级单 ZSET 内存与性能可能吃紧，优化：① **分段/分片**——按段位或区间分到多个 ZSET，全局排名靠合并或单独维护。② **只精确前列**——前列（前 1000/1%）实时精确，尾部用**定时快照近似**（每隔几分钟重算或估算）。③ **分数聚合**——玩家分数变化先在内存累加、周期性批量 ZADD，减少 Redis 写。④ **查自己名次**——可缓存或用近似。⑤ **更现代的分桶近似**——把分数域按区间分桶，桶内只存计数（或桶内 ZSET 近似），Redis 7+ 可用 `ZRANGEBYSCORE` 取区间玩家做桶内近似排名；对比"全量单 ZSET"与"分桶近似"，后者用更少内存换尾部精度下降（桶越粗内存越省、名次越糊），按"前列精确、尾部近似"选桶宽。本质：**精确只给前列 + 全量用近似**，平衡实时性与成本。

**考点解析**：ZSET 适合排行榜、大规模的分段/近似策略。资深要能讲清"不必全量实时精确"。

**常见误区**：千万级单 ZSET 硬扛（内存/慢）；全量实时（成本爆）；查询不缓存。

**追问方向**：玩家问"我排第几"，但他在尾部（百万名外），怎么答得快？（近似估算——按分数段估算名次区间，或返回"在 xx% 之外"，不必精确。）

### 【进阶】故障复盘 · 活动开启流量洪峰

> 限时活动整点开启，瞬间几十万玩家涌入，服务扛不住。怎么应对？

**参考思路**：① **预热**——活动开启前预热缓存、预分配资源、提前加载活动数据。② **削峰填谷**——客户端**错峰**进入（按账号/区服错开几秒到几十秒）、或排队（先到先得，超出排队）。③ **限流降级**——网关层限流（令牌桶/漏桶），超量请求排队或拒绝 + 友好提示；非核心功能降级（如关闭部分表现）。④ **弹性扩容**——活动前预扩容逻辑服/跨服副本进程。⑤ **异步化**——领奖/报名等非即时操作异步处理 + 排队。⑥ **监控告警**——实时监控 QPS/延迟，过载自动降级。本质：**洪峰不可避免，但可削平**（错峰/排队/限流）+ **资源提前备好**（预热/扩容）。

**考点解析**：预热、错峰/排队、限流降级、扩容。资深要能讲清"洪峰靠削峰而非硬扛"。

**常见误区**：等点开再扩容（来不及）；无限流（被冲垮）；核心非核心一视同仁（全降级或全不降）。

**追问方向**：活动奖励是限量的（先到先得），怎么防超发？（原子扣减库存（Redis DECR/ Lua）+ 库存预扣 + 失败回退；不要"查库存>0 再发"两步非原子。）

### 【专家】权衡 · 经济系统防通胀

> 游戏里货币越打越多、越来越不值钱（通胀）。怎么设计经济平衡？

**参考思路**：把游戏经济看作**水龙头（产出）与下水道（消耗）**的平衡。产出：打怪掉钱、任务奖励、活动、卖出道具给系统。消耗：购买（道具/服务）、强化、修理、税费、消耗品。防通胀：① **监控产出消耗比**——数据化追踪每种货币的产出/消耗，比值偏离则调。② **可调水龙头/下水道**——产出上限（每日/每周额度）、增加高价值消耗品（坐骑、外观、强化）吸金。③ **货币沉淀**——长期目标消耗（养成线）让玩家愿意花。④ **稀缺资源**——核心资源限量产出（绑定/限次），避免无限刷。⑤ **交易税费/绑定**——玩家间交易抽税、绑定道具防炒作。⑥ **数据驱动调参**——运营按数据动态调产出消耗，而非拍脑袋。本质：**没有下水道的产出必然通胀**。

**考点解析**：水龙头/下水道模型、产出消耗平衡、可调手段。资深要从系统角度讲清"通胀是产出>消耗的必然结果"。

**常见误区**：只加产出不加消耗（必然通胀）；不可监控（无法调）；忽略玩家间炒作（绑定/税费缺失）。

**追问方向**：玩家间自由交易会不会加剧通胀？（不一定——玩家间交易不产生/销毁货币（只是转移），真正影响通胀的是"系统产出"与"系统回收"。但炒作会推高物价，需税费/绑定调节。）

### 【专家】系统设计 · 跨服战场

> 设计跨服战场：玩家从各服进入同一战场，结束后回本服。数据一致性怎么保证？

**参考思路**：流程：① 本服收到跨服匹配成功 → 把玩家**状态快照**（等级/装备/背包）发给跨服进程，本服标记玩家"跨服中"（避免重复操作）。② 跨服进程加载玩家快照，跑战场（战斗、结算）。③ 战场结束，跨服进程把**结果**（胜负、奖励、消耗、可能的成长）发回本服。④ 本服**原子应用结果**（发奖、扣消耗、更新数据），解除"跨服中"标记。一致性要点：① 玩家"跨服中"期间本服不接受会冲突的操作（或排队）。② 结果传递**可靠**（消息队列 + 确认 + 重试，避免丢结果导致玩家白打）。③ **幂等**——本服应用结果要幂等（重复消息不重复发奖），用唯一战斗 id 去重。④ 崩溃恢复——跨服进程崩了要有持久化战场状态 + 恢复机制，或判定异常结束按规则补偿。核心：**本服是玩家数据的最终归属，跨服只是临时借出，结果可靠回流 + 幂等应用**。

**考点解析**：快照借出、结果可靠回流、幂等应用、跨服中状态保护。资深要能讲清"跨服不能丢玩家进度"。

**常见误区**：跨服结果丢了（玩家白打）；不幂等（重复发奖）；玩家跨服中本服还允许冲突操作。

**追问方向**：跨服战场进行中本服重启，玩家状态怎么办？（本服持久化"跨服中"标记 + 玩家所属战场 id，重启后按标记等待跨服结果或主动查询，不误判玩家离线。）

### 【进阶】原理辨析 · 掉落与保底

> 怪物掉落的"概率"怎么设计？什么是 PRD（伪随机分布）？为什么要有保底？

**参考思路**：纯随机（每次独立概率 p）会让玩家体验方差极大——有人一刷就出、有人刷百次不出（愤怒退坑）。**PRD（Pseudo Random Distribution）**：开始概率较低，**每次没出下次提升**，出到则重置——平滑运气方差，让"期望次数"稳定（Dota 暴击、很多抽卡用此）。本质是每次以 `C·n` 的概率判定（`n` 为连续未命中次数、`C` 为按目标期望率反推的常数），通过 `C` 校准使长期实际命中率≈目标公示率。**保底**：累计 N 次必出（如"十连必出 SR""99 次必出"），给玩家确定性下限，防极端坏运。服务器要记录每个玩家的"累计计数"，掉落判定服务端权威（防客户端篡改）。设计上要平衡"惊喜感"（随机）与"可控体验"（保底/PRD）。

**考点解析**：纯随机的方差问题、PRD 平滑、保底兜底、服务端权威计数。资深要能讲清"为什么纯随机对体验不好"。

**常见误区**：纯随机导致玩家暴怒；客户端算掉落（篡改）；保底计数不持久（刷退重置或重连重置，被刷）。

**追问方向**：抽卡要公示概率（法规），PRD/保底怎么公示？（公示基础概率与保底规则；PRD 的递增机制要透明，避免"实际概率≠公示"的合规风险。）

### 【专家】系统设计 · 登录与网关

> 设计高并发的登录与网关。鉴权、路由、防刷各怎么做？

**参考思路**：① **登录服**：账号密码校验（加盐哈希存密码）、签发**短期 token/ticket**。可加 OAuth/第三方登录。登录服无状态、可水平扩展。② **网关**：客户端拿 token 连网关 → 网关校验 token（向登录服/缓存验）→ 建立长连接 → 按玩家路由到对应逻辑服（按玩家 id 分片或负载均衡）。网关维持海量长连接（epoll + REUSEPORT + 协程，见第 5 章），无状态/轻状态、易扩展。③ **防刷**：登录限流（IP/账号/设备频率）、验证码、设备指纹、异常检测（异地/批量注册）、封禁黑名单。④ **安全**：传输加密（TLS/自研加密）、token 防重放（nonce + 过期）、防中间人。

**考点解析**：登录服与网关分离、token 鉴权、长连接网关扩展、防刷。资深要能讲清"为什么登录和网关分开"。

**常见误区**：网关做重逻辑（应只路由）；token 不过期/不防重放；无限流被撞库。

**追问方向**：玩家连了网关但逻辑服还没分配/在迁移，怎么处理？（网关先维持连接 + 排队/重试，逻辑服就绪后绑定；或网关做轻缓存过渡，不让玩家断线。）

### 【进阶】故障复盘 · 玩家数据回档

> 玩家充了值/打了装备，服务重启后发现数据没了（回档）。怎么防？

**参考思路**：回档 = 数据"看似成功但实际没持久化"，常见于：① 内存改了但**还没落 DB**就崩了；② 写 DB 用了缓存/异步，崩溃时未刷盘；③ 事务没真正提交。防范：① **关键操作立即持久化**——充值、购买、稀有掉落等"高价值操作"改完内存立刻同步落 DB（不要攒批），或用**WAL（预写日志）**先写日志再改内存（崩溃后按日志重放）。② **事务确认**——DB 事务返回成功后才认为成功、才回客户端成功。③ **双写校验**——关键数据写两处（DB + 日志/备份），定期对账。④ **崩溃恢复**——启动时按 WAL/日志重放未完成操作。⑤ **充值回调幂等**——支付平台可能重复回调，按订单号去重，避免重复发货或回档误判。核心：**高价值数据不能只活在内存，必须有可靠的持久化路径**。

**考点解析**：回档成因（内存未落盘/事务未提交/异步未刷）、WAL/立即持久化/事务确认。资深要能讲清"哪些数据必须立即落盘"。

**常见误区**：所有数据攒批异步落盘（高价值数据也丢）；事务没等确认就回客户端成功；支付回调不幂等。

**追问方向**：内存数据周期性落盘（如每 5 分钟），这 5 分钟内的操作崩了怎么办？（WAL 兜底——关键操作先写日志，崩溃后重放这 5 分钟；或高频/高价值操作即时落盘。）

### 【专家】权衡 · 数值配置化

> 策划要频繁改技能伤害、怪物属性、掉率，不能每次改都改代码发版。怎么设计数值系统？

**参考思路**：**数据驱动（配置化）**——把所有数值（属性、公式系数、技能效果、掉率、成长曲线）抽到**配置表/数据**（Excel/JSON/protobuf/自研编辑器导出），代码只读配置执行逻辑。要点：① **配置 schema** 严格（类型/范围/引用完整性校验），编辑器/导出器校验后下发。② **热更**——配置变更后服务端**热加载**（不重启），生效到运行时。③ **版本与灰度**——配置带版本，可灰度（部分服先上）、可回滚。④ **策划自助**——可视化编辑器，策划自助改、导出、下发，工程师不介入日常调参。⑤ **代码与配置解耦**——逻辑写"读配置执行"，新增技能/属性只改配置不改代码（尽量）。代价：配置 schema 设计要前瞻、配置错误会影响线上（需校验+灰度）。

**考点解析**：数据驱动、热加载、版本/灰度/回滚、策划自助。资深要能讲清"为什么数值不能写死在代码"。

**常见误区**：数值硬编码（改一次发一次版）；配置无校验（错值上线）；不可热更/不可回滚。

**追问方向**：配置热更时，已经在跑的战斗用旧配置还是新配置？（通常已开始的战斗用旧配置到结束、新战斗用新配置——避免中途切换造成不一致；要明确边界。）

### 【进阶】系统设计 · 聊天系统

> 设计聊天系统：世界频道、私聊、公会、敏感词过滤。百万在线怎么扛世界广播？

**参考思路**：① **频道模型**：世界/公会/队伍/私聊/附近，每条消息带频道与目标。② **世界广播放大器**——一人发言、全服接收，带宽与 CPU 是放大问题。优化：**分线路由**——把玩家分到多条"世界频道"线路（按区服/分片），发言只广播到本线路，避免单次广播全服；或**聚合**（多条消息合并下发）；**限频**（每人发言间隔、防刷屏）。③ **敏感词**：AC 自动机过滤（见第 4 章）+ 变体处理（谐音/拆字）+ 人工审核兜底。④ **私聊**：按玩家 id 路由，存离线消息（对方不在线时）。⑤ **存储**：聊天记录可选存（审计/举报），热数据在内存、冷数据落库。核心：**世界频道是放大器，必须靠分线/限频/聚合控制，不能裸广播**。

**考点解析**：频道模型、世界广播的放大问题与分线/限频解法、敏感词。资深要能讲清"世界广播的成本与控制"。

**常见误区**：世界频道裸广播全服（爆带宽）；无限频（刷屏）；敏感词用简单 substring（漏变体）。

**追问方向**：玩家举报某条聊天违规，怎么追溯？（聊天记录存证（带发送者/时间/内容）+ 举报链路；记录按法规与隐私策略定期清理。）

### 【专家】系统设计 · 拍卖行（交易所）

> 设计一个全服拍卖行：玩家挂单出售、按条件搜索、价格撮合、成交结算。高并发搜索与撮合怎么扛？怎么防刷/防洗钱？

**参考思路**：① **挂单**：卖家挂单（道具/数量/单价/一口价或竞价）→ 服务端**冻结道具**（标记"上架中"、从背包移出）→ 入库挂单表。② **搜索索引**：百万级在架商品不能裸扫库——按"道具 id + 品质/等级"建**搜索索引**（Elasticsearch 或自研倒排/分桶），支持按价格/属性排序、分页；热品类索引常驻内存。③ **价格撮合**：两种模式——**竞价/一口价**（买家出价，到时最高价成交或直接一口价买断）或**订单簿撮合**（买卖挂单按价格优先、时间优先匹配，类似交易所）。撮合要**原子**（冻结款、扣买家钱、加买家道具、上架卖家所得、解冻卖单）在一个事务，配合**流水**对账。④ **成交结算**：扣买家货币（先冻结）、给买家道具、卖家所得进"待提取/邮件"（含税费）；全程幂等（按订单号/撮合 id 去重）。⑤ **防刷/防洗钱**：挂单限频、异常低价监控（同一道具远低于市价、双方关联账号互转——典型洗钱/小号搬运）、税费/最低价限制、大额交易审计日志、与登录/交易锁联动防并发薅。⑥ **性能**：搜索读多写少，索引与撮合分离；撮合是写热点，按品类/分片串行化或单写主对账。核心：**搜索靠索引、撮合靠原子事务+订单簿、防洗靠异常监控+审计**。

**考点解析**：搜索索引、价格撮合（一口价 vs 订单簿）、冻结/原子结算、防洗钱审计。资深要能讲清"搜索是读放大、撮合是写热点，要分开优化"。

**常见误区**：百万挂单裸扫库（搜索慢）；撮合非原子（一方扣款一方没拿到货）；无异常监控（小号洗钱、低价搬运）；卖家道具未冻结就上架（一物多卖）。

**追问方向**：卖家挂单后道具被冻结，这时游戏服要合服或卖家被封号，挂单怎么处理？（合服前下架回流/迁移挂单；封号时挂单按规则失效或退回——必须有清理流程，不能让冻结道具卡死。）

---

> **本章小结**：业务模块的核心心法是"**事务保证一致性（道具/交易/跨服）、数据驱动配置化（数值/活动）、放大器要削峰（世界广播/活动洪峰）、权威放服务端（掉落/结算）、高价值数据即时持久化（防回档）**"。系统设计题没有唯一答案，关键是讲清**需求拆解 → 方案 → 权衡 → 风险**这条链路——这正是第五部分系统设计题集要专项训练的能力。
