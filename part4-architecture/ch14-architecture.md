# 第14章 服务端架构设计

> 架构决定了系统的天花板——单体能扛多少、能不能水平扩展、一个模块出问题会不会拖垮全局、从百人服到万人服怎么演进。资深工程师要能从需求倒推架构、讲清每层的职责与边界、并预判扩展瓶颈。本章讲清游戏服务端的分层、进程模型、有状态服务的扩展、架构演进路径。

## 原理体系

### 1. 架构演进：单体 → 分层 → 分布式

- **单体（monolith）**：所有逻辑在一个进程里。简单、本地调用快、易开发调试；天花板低（单机算力/内存上限）、一处崩溃全崩、无法局部扩展。适合 Demo/小规模。
- **分层（layered）**：在单体内按职责分层（网络/逻辑/数据），结构清晰但仍单进程。
- **多进程/分布式**：把不同职责拆到不同进程/机器，独立扩展、故障隔离。代价：跨进程通信开销、一致性复杂、运维复杂。

游戏服务端典型演进：**单进程单体（开发期）→ 单进程分层（上线）→ 多进程（网关/逻辑/战斗/DB 分离）→ 分布式（跨服、微服务化、数据分片）**。每一步解决一个瓶颈（性能/扩展/容错），也引入新复杂度。**不要一上来就分布式**——按实际瓶颈驱动演进。

### 2. 进程与线程模型

- **单进程多线程**：一个进程内多线程跑不同逻辑（IO 线程 + 逻辑线程 + DB 线程）。共享内存、通信快；但锁复杂、一崩全崩。适合中等规模、逻辑紧密耦合的场景。
- **多进程**：不同职责拆成独立进程（网关进程、逻辑进程、战斗进程），进程间靠 IPC/RPC/消息通信。故障隔离（一个进程崩不影响其他）、独立扩展；但通信有序列化开销、状态共享难。游戏服务端主流是**多进程**（崩溃隔离 + 独立扩展）。
- **Actor（如 skynet）**：在一个进程里用 actor 模型实现"逻辑多线程"（每 actor 单线程无锁、actor 间消息）。介于单进程多线程与多进程之间——共享进程内存但 actor 间逻辑隔离。

游戏常见：**多进程骨架（网关/逻辑/DB/跨服分离）+ 单进程内多线程或 actor 并发**。

### 3. 有状态 vs 无状态服务

- **无状态服务**：不持有跨请求的状态（如 HTTP API、网关路由）。任何实例都能处理任何请求，**水平扩展简单**（加机器 + 负载均衡）、故障转移容易（请求重试到另一实例）。
- **有状态服务**：持有会话/玩家状态（如游戏逻辑服持有玩家在线状态）。**水平扩展难**——某玩家的请求必须路由到持有他状态的实例（粘性路由 / 一致性哈希分片）；故障转移复杂（状态要迁移或恢复）。

游戏逻辑服**天然有状态**（玩家在线、实时战斗），这是游戏架构区别于普通 Web 的关键难点。扩展有状态服务的手段：**按玩家 id 分片**（一致性哈希把玩家路由到固定实例）、**状态外置**（把状态放 Redis/共享内存，逻辑服尽量无状态化）、**会话迁移**（实例故障时把玩家会话迁到其他实例）。

### 4. 典型分层：网关 / 逻辑 / 战斗 / DB / 跨服

- **网关（gateway）**：维持客户端长连接、加解密、限流、按玩家路由到逻辑服。无状态/轻状态、易扩展。
- **逻辑服（logic）**：处理玩家业务（背包、社交、任务）。有状态（玩家在线状态）。按玩家分片。
- **战斗服（battle）**：跑战斗模拟（同步、物理、AI）。CPU 密集、按对局分配、对局结束即释放。常独立进程（隔离 + 资源调度）。
- **DB 服/数据层**：持久化、缓存。可能是 MySQL + Redis + MongoDB 混合。
- **跨服（cross-server）**：跨服战场/匹配/排行，聚合各服数据。
- **后台/运营服**：GM、配置下发、统计。

层间通过 **RPC/消息** 通信，依赖单向（上层调下层）。关键：**战斗服独立**（隔离崩溃、CPU 调度）、**逻辑服按玩家分片**（有状态扩展）、**网关无状态**（易扩展、故障转移）。

### 5. 服务间通信：RPC vs 消息队列

- **RPC（同步/异步调用）**：服务 A 直接调服务 B 的接口，等结果（或异步）。适合**请求-响应**、低延迟、调用关系明确的场景（逻辑服调 DB 服、跨服调用）。游戏内部通信主流。
- **消息队列（异步解耦）**：服务 A 发消息到队列、服务 B 订阅处理。适合**解耦、削峰、广播**（活动事件广播、跨服异步通知、日志）。游戏里用于异步通知、事件广播，少用于核心同步链路（延迟敏感）。

游戏内部主链路用 RPC（低延迟、强交互），异步/广播/解耦用消息总线/事件。

### 6. 数据驱动与配置化

架构要支持**数据驱动**：数值/活动/规则配置化、热更、灰度（见第 12、13 章）。这要求架构层面把"逻辑"与"数据/配置"分离——逻辑代码稳定、配置可变，运营/策划自助改配置不重启。这是现代游戏服务端架构的标配。

### 7. 可扩展性设计

设计时预留扩展空间：
- **无状态部分**尽量水平扩展（网关、匹配、后台）。
- **有状态部分**按玩家/区服**分片**（一致性哈希），分片数预留扩容余量。
- **战斗/计算密集**部分独立进程/线程池，按需弹性调度。
- **避免单点**——任何单实例故障不应导致全局不可用（主备/多活/降级）。
- **数据层**分库分表 + 读写分离 + 缓存分层。
- **预留接口与协议版本**——协议带版本号、向前兼容，避免协议锁死。

## 面试题

### 【专家】系统设计 · 整体架构分层

> 从零设计一个 MMO 服务端架构。网关/逻辑/战斗/DB 怎么分层？各自职责？

**参考思路**：
- **网关**：维持海量客户端长连接、加解密/限流、按玩家路由到逻辑服。无状态、易水平扩展。
- **逻辑服**：玩家在线业务（背包/社交/任务/聊天），持有玩家会话状态，**按玩家 id 分片**（一致性哈希路由）。
- **战斗服**：跑战斗（同步/物理/AI/结算），**独立进程**——CPU 密集需隔离、按对局分配、对局结束释放。崩溃不影响逻辑服。
- **DB/数据层**：MySQL（账务/关系/强一致）+ Redis（热数据/缓存/排行榜），分库分表；部分场景用 MongoDB/KV 存灵活结构化数据。
- **跨服**：跨服战场/匹配/排行，聚合各服。
- **后台**：GM/配置下发/统计，HTTP + 内部 RPC，与游戏服解耦。
层间 RPC 通信，依赖单向。关键决策：战斗独立（隔离+调度）、逻辑按玩家分片（有状态扩展）、网关无状态（易扩展）。

**考点解析**：分层职责、有状态分片、战斗独立。资深要能讲清"为什么这么分层"与每层扩展方式。

**常见误区**：战斗与逻辑混进程（崩溃连坐、CPU 抢占）；逻辑服不分片（单点）；网关做重逻辑。

**追问方向**：玩家从主城（逻辑服）进入副本（战斗服），流程怎么走？（逻辑服申请战斗服资源→战斗服加载玩家快照→玩家"迁移"到战斗服→结束回流逻辑服，见第 12 章跨服。）

### 【专家】权衡 · 有状态服务的水平扩展

> 游戏逻辑服天然有状态，怎么水平扩展？

**参考思路**：有状态服务扩展的三大手段：① **按玩家分片**——一致性哈希（配虚拟节点均衡分布）把玩家路由到固定逻辑服实例，某玩家请求总到持有他状态的实例（粘性）。扩容时新增实例、迁移部分玩家（一致性哈希减少迁移，虚拟节点避免分片实例少时数据倾斜）。② **状态外置**——把状态从进程内存挪到 **Redis/共享内存**，逻辑服尽量无状态化，任何实例都能处理任何玩家（查询 Redis 拿状态）。代价：每次请求多一次 Redis 查询。③ **会话迁移**——实例故障时把该实例上的玩家会话迁到其他实例（从 Redis/DB 重建状态）。游戏常用：**热数据（在线会话）外置 Redis + 按玩家分片路由 + 故障会话迁移**。本质：**减少进程内状态、状态可重建/可迁移**。

**考点解析**：分片、状态外置、会话迁移三手段。资深要能讲清"有状态扩展靠减少进程内状态"。

**常见误区**：有状态服务直接加机器（请求路由错、状态丢失）；不外置状态（故障不可恢复）；分片键选错（热点）。

**追问方向**：玩家热数据外置 Redis，每请求查 Redis 会不会太慢？（热会话可缓存在逻辑服本地内存 + Redis 兜底；或用长连接绑定实例（粘性），状态留实例内存，Redis 仅持久化/恢复用。）

### 【专家】权衡 · 单体 vs 微服务

> 游戏适合微服务化吗？拆分边界在哪？

**参考思路**：Web 的微服务（每业务一个独立服务、HTTP/gRPC 通信）**不适合直接套到游戏核心**——游戏内部通信**低延迟、强实时、高频**，微服务的网络/RPC 开销与分布式事务复杂度会拖垮核心。但游戏可**按"粗粒度边界"拆**：网关/逻辑/战斗/DB/跨服/后台这些大块拆成独立进程/服务（已经是"游戏版微服务"），而不是把背包/任务/聊天各拆一个细粒度服务（过细、调用爆炸）。判据：**拆分边界应在"延迟容忍度高、故障可隔离、独立扩展需求强"的地方**——战斗服独立（CPU 隔离+调度）、跨服独立（聚合）、后台独立（解耦）。核心逻辑（玩家内业务）保持聚合（一个逻辑服内），靠模块化而非微服务解耦。

**考点解析**：微服务的代价（延迟/事务）、游戏按粗粒度边界拆、核心保持聚合。资深要能区分"游戏版微服务"与"Web 微服务"。

**常见误区**：盲目微服务化（背包/任务各一服务，调用爆炸）；完全单体（无法扩展/隔离）；不区分核心与非核心。

**追问方向**：什么情况下值得把某业务拆成独立服务？（独立扩展需求强、故障隔离需求高、团队 ownership 清晰、延迟容忍——如匹配服、排行服、聊天服。）

### 【专家】深挖追问 · 架构演进路径

> 项目从单服到分布式，架构怎么一步步演进？每步解决什么问题？

**参考思路**：
1. **单进程单体**：开发期，所有逻辑一进程。简单，天花板低。
2. **单进程分层 + 状态外置（Redis/DB）**：上线初期，单机能扛。解决：结构清晰、数据持久化。
3. **网关与逻辑分离（多进程）**：单机扛不住连接/IO。解决：连接处理与逻辑解耦、网关独立扩展。
4. **战斗服独立**：战斗 CPU 吃满拖累逻辑。解决：CPU 隔离、按对局调度。
5. **逻辑服分片（按玩家）**：单逻辑服扛不住玩家数。解决：有状态水平扩展。
6. **数据层分库分表 + 读写分离 + 缓存**：单 DB 扛不住。解决：数据扩展。
7. **跨服/全服聚合**：多服互动需求（跨服战场/排行）。解决：跨服数据一致性。
8. **多机房/多活**：单机房容灾。解决：可用性/容灾。
每步**由实际瓶颈驱动**（连接/CPU/玩家数/数据/容灾），不提前过度设计。演进的核心是**把瓶颈点独立出来、可扩展、可隔离**。

**考点解析**：演进的"瓶颈驱动"逻辑、每步解决的问题。资深要能讲清"为什么这么演进、不跳步"。

**常见误区**：一上来就分布式（过度设计、复杂度爆炸）；不演进（扛不住就崩）；跳步（没解决单点就上多活）。

**追问方向**：演进到分片后，玩家跨分片操作（如交易）怎么办？（分布式事务/最终一致 + 对账，见第 15 章；或把相关玩家路由到同分片。）

### 【进阶】系统设计 · RPC vs 消息队列

> 服务间通信用 RPC 还是消息队列？怎么选？

**参考思路**：
- **RPC**：直接调、（通常）等结果，**请求-响应**模型。适合低延迟、强交互、调用关系明确的核心链路（逻辑服↔DB服、逻辑服↔战斗服、跨服调用）。游戏内部主链路主流。
- **消息队列/事件总线**：发布-订阅、异步解耦、削峰、广播。适合**非即时、解耦、一对多**（活动事件广播、跨服异步通知、日志采集、运营推送）。游戏里用于异步通知与事件广播。
判据：**要即时响应的核心链路用 RPC；可异步、要解耦/广播的用消息**。同一个系统两者共存——核心 RPC + 外围消息。游戏核心链路几乎全 RPC（延迟敏感），消息用于边缘异步。

**考点解析**：RPC（同步/低延迟/请求响应）vs 消息（异步/解耦/广播）。资深要按延迟与交互模式选。

**常见误区**：核心链路用消息（延迟大）；广播/解耦用 RPC（一对多难、耦合）；非此即彼。

**追问方向**：RPC 调用下游服务超时，怎么处理？（超时 + 重试（幂等前提下）+ 熔断（下游异常时快速失败）+ 降级，见第 15 章。）

### 【专家】权衡 · 战斗服独立

> 为什么战斗逻辑要拆到独立进程/服，而不在逻辑服里跑？

**参考思路**：① **CPU 隔离**：战斗是 CPU 密集（物理/同步/AI），跑在逻辑服会抢核、拖累其他玩家业务；独立进程让战斗的 CPU 消耗不影响全局。② **故障隔离**：战斗服崩（物理 bug、内存问题）只影响该对局，不连累逻辑服/全服玩家。③ **资源调度**：战斗对局按需分配、结束即释放，独立进程便于弹性调度（开新进程扛高峰、空闲回收）。④ **独立扩展**：战斗负载与逻辑负载不同步，独立后可按各自瓶颈扩展。代价：跨进程通信开销（玩家状态在逻辑服、战斗在战斗服，需快照借出/回流）。整体收益（隔离 + 调度）远大于通信代价。

**考点解析**：CPU 隔离、故障隔离、弹性调度、独立扩展。资深要能讲清"为什么战斗值得拆"。

**常见误区**：战斗与逻辑混进程（崩溃连坐、CPU 抢占）；战斗服不按对局释放（资源泄漏）；忽略状态借出/回流的复杂性。

**追问方向**：战斗服按对局分配，高峰期战斗服不够，怎么办？（弹性扩容（开新进程/容器）、排队进入、或降级（简化物理）；监控战斗服负载主动扩。）

### 【专家】原理辨析 · 单进程多线程 vs 多进程

> 单进程多线程和多进程各适合什么？游戏怎么选？

**参考思路**：
- **单进程多线程**：共享内存、线程间通信快（直接访问）；但锁复杂、一崩全崩、调试难（数据竞争）。适合**逻辑紧密耦合、通信极频繁、规模不大**的场景。
- **多进程**：故障隔离（一崩不全崩）、独立扩展、可用不同语言/版本；但跨进程通信有序列化开销、状态共享难、运维复杂。适合**需要隔离/独立扩展/故障容错**的场景。
游戏主流**多进程**（隔离 + 扩展 + 容错）——网关/逻辑/战斗/DB 各进程，进程内再用多线程或 actor 并发。单进程多线程多用于单进程内的并发（如逻辑服内多线程/actor），而非整个服务端。判据：**要隔离/扩展 → 多进程；要紧密共享 → 单进程多线程**。

**考点解析**：共享内存（快但锁复杂、连坐）vs 进程隔离（安全但通信贵）。资深要能按隔离/扩展需求选。

**常见误区**：全单进程多线程（崩全崩、难扩展）；全多进程（紧密逻辑通信开销大）；不区分场景。

**追问方向**：多进程间共享大数据（如全局配置/大表）怎么办？（共享内存 mmap + 只读；或独立数据服务 + 缓存；避免每进程拷贝一份。）——进一步深挖：actor 模型（如 skynet）与线程模型在 GC 压力、锁竞争、可调试性上的具体差异？（actor 每 actor 单线程无锁，但消息驱动模型下 GC 独立于其他 actor、调试需 trace 消息流；多线程共享内存需细控锁粒度、警惕伪共享/NUMA 跨节点访问开销。）

### 【专家】系统设计 · 跨服架构

> 跨服战场/匹配怎么架构？跨服进程与单服什么关系？

**参考思路**：跨服进程是**独立于单服**的全局层：① **跨服匹配服**——接收各单服玩家的匹配请求，全局配对。② **跨服战场服**——跑跨服战斗，玩家从单服"借出"到跨服（状态快照传过去）、结束回流（结果传回单服）。③ **跨服数据/排行**——聚合各服。关系：单服是玩家数据的归属，跨服只是**临时借出玩家**参与全局活动，结束回流。架构上跨服是**横向独立层**（独立进程、独立扩缩容），单服与跨服通过可靠消息/RPC 交互，**结果必须可靠回流 + 幂等应用**（见第 12 章）。跨服要解决：玩家借出的状态一致性、跨服战斗的同步、结果回流的可靠性。

**考点解析**：跨服作为独立横向层、单服是数据归属、借出/回流模型。资深要能讲清"跨服不能丢玩家进度"。

**常见误区**：跨服直接改单服数据（一致性乱）；结果回流不可靠（玩家白打）；跨服与单服耦合（扩展难）。

**追问方向**：跨服战场进行中跨服进程重启，怎么办？（持久化战场状态 + 恢复，或判定异常结束按规则补偿；玩家会话保持不断线——见第 12 章。）

### 【进阶】故障复盘 · 架构耦合拖垮全局

> 某次线上：一个非核心模块（如签到）卡住，导致全服响应变慢。架构上怎么避免？

**参考思路**：根因是**架构耦合**——非核心模块与核心链路共享资源（同线程/进程/连接池），一个卡住拖累全部。防范：① **资源隔离**——不同模块用独立线程池/连接池/进程，避免争抢。② **故障隔离**——非核心模块异常不影响核心（熔断、降级、超时）。③ **依赖单向 + 弱依赖**——核心不依赖非核心（签到挂了不能影响战斗）。④ **超时 + 熔断**——任何下游调用有超时与熔断，不无限等待。⑤ **异步解耦**——非核心操作（签到/统计）异步化，不阻塞主链路。本质：**核心链路只依赖核心，非核心故障要被隔离**。

**考点解析**：资源/故障隔离、弱依赖、超时熔断。资深要能讲清"为什么签到卡住不能拖垮战斗"。

**常见误区**：所有模块共享线程池/连接池（争抢）；核心强依赖非核心；无超时（一个慢拖全局）。

**追问方向**：怎么定位"哪个模块是瓶颈/卡点"？（全链路追踪看各环节耗时、监控各线程池/连接池水位、慢调用日志。）

### 【专家】权衡 · 玩家数据组织：按玩家聚合还是按功能拆

> 玩家数据按"玩家聚合"还是按"功能"组织？比如背包数据放背包服还是玩家档案？

**参考思路**：
- **按玩家聚合**：一个玩家的所有数据（档案/背包/社交/战斗）聚合在一起（同一逻辑服/同一存储分区）。优点：**玩家内操作局部化、事务简单、查询高效**（拿一个玩家拿全）。缺点：单玩家数据量大、不同功能的访问模式不同（背包高频小写、档案低频）混在一起。
- **按功能拆**：背包数据放背包服务/库、社交放社交服务。优点：各功能独立扩展、访问模式匹配存储。缺点：**跨功能操作（交易涉及背包+货币）要分布式事务**、查一个玩家要汇总多处。
游戏实践：**玩家内强相关数据（档案/背包/货币）按玩家聚合**（同一逻辑服 + 同一存储分区，本地事务保证一致性）；**跨玩家/全局数据（社交关系/排行/公会）按功能拆**（独立服务）。判据：**强一致 + 同玩家局部 → 聚合；独立扩展 + 跨玩家 → 拆**。

**考点解析**：聚合（一致+局部）vs 拆分（扩展+访问匹配）的权衡、按一致性边界定。资深要能划分聚合边界。

**常见误区**：全按玩家聚合（背包/排行混、扩展难）；全按功能拆（交易要分布式事务、复杂）；不按一致性边界划分。

**追问方向**：交易涉及双方背包+货币，怎么保证一致？（把同一交易涉及的玩家路由到同一逻辑服分片，本地事务搞定；跨分片才上分布式事务。）

### 【进阶】系统设计 · 从百人服到万人服的可扩展架构

> 架构怎么设计才能从百人服平滑扩展到万人服？

**参考思路**：核心是**识别扩展瓶颈、逐层水平扩展**：① **连接层**——网关无状态，加网关实例 + 负载均衡扛连接。② **逻辑层**——逻辑服按玩家分片（一致性哈希），加实例 + 迁移玩家。③ **战斗层**——战斗服按对局分配 + 弹性扩缩容。④ **数据层**——分库分表（玩家 id 分片）+ 读写分离 + 缓存分层。⑤ **跨服/全局**——独立横向层，独立扩展。⑥ **无单点**——每层主备/多活，避免单实例瓶颈。⑦ **预留扩容余量**——分片数/连接数/数据分区留余量，扩容时翻倍迁移。关键设计原则：**有状态按玩家分片、无状态任意扩展、战斗独立调度、数据分片 + 缓存**。这样从百人到万人是"加机器 + 调分片"，而非重构。

**考点解析**：各层水平扩展手段、无单点、预留余量。资深要能讲清"扩展性是设计出来的、不是事后硬扛"。

**常见误区**：有状态不分片（单点天花板）；有单点（扩不动）；不留余量（扩容要大迁移）。

**追问方向**：万人同屏（同一区域万人），逻辑服分片也扛不住同区域，怎么办？（空间分片——同一区域拆到多进程协同 + AOI 裁剪同步 + 降级，见第 9、10 章。）

---

> **本章小结**：架构的主线是"**按瓶颈驱动演进（单体→分层→多进程→分布式），有状态按玩家分片、无状态任意扩展，核心与非核心隔离，战斗/跨服独立成层**"。记住三条铁律：**演进由实际瓶颈驱动，不提前过度设计**；**核心链路只依赖核心，非核心故障要被隔离**；**扩展性是设计出来的（分片+无单点+预留余量），不是事后硬扛**。架构能力是资深服务端工程师的标志。
