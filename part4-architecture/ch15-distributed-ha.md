# 第15章 分布式与高可用

> 分布式系统的本质是用多机换取性能与可用性，代价是**一致性、可用性、分区容错**的三角权衡（CAP）。游戏服务端做跨服、做容灾、做防雪崩，都要落地这套理论——共识算法、分布式事务、一致性哈希、限流熔断降级、脑裂。本章讲清这些，是资深架构岗的硬核考点。

## 原理体系

### 1. 一致性模型与 CAP

- **一致性（Consistency）**：强一致（线性一致：每个操作看起来在调用到返回之间某一瞬间原子完成，读总返回最新已提交写；对外呈现单一系统镜像）、最终一致（短时间内可能不一致，最终收敛）、因果一致等。
- **CAP 定理**：分布式系统在网络分区（P）时，只能在**一致性（C）**与**可用性（A）**间二选一。分区不可避免，所以实质是 CP（保一致牺牲可用）vs AP（保可用牺牲一致）。
- **游戏取舍**：游戏**大多选 AP**（最终一致）——玩家体验优先可用（不能因一致性问题卡服/拒绝服务），容忍短时不一致（如排行榜延迟几秒更新、跨服数据异步同步）。**账务/交易**等关键数据选 CP 或强一致（不能错账）。

### 2. 共识算法：Raft / Paxos

共识（consensus）= 让多个节点对**某个值/状态**达成一致，是分布式一致性的基石（用于选主、日志复制、配置同步）。
- **Paxos**：经典共识算法，正确性严格但难理解难实现。
- **Raft**：为"可理解性"设计的共识算法（etcd/Consul 用它）。核心：**选主（leader election）**——一个 leader 接受写请求、**复制日志**到 follower、多数派（quorum，过半）确认才算提交。leader 故障则重新选主。Raft 把共识拆成"选主 + 日志复制 + 安全性"三个清晰子问题。

游戏里共识用于：**选主**（主备切换时谁是主）、**强一致配置/元数据**（etcd/zk 存服务发现、锁、配置）。一般业务数据不直接跑 Raft（开销），而是用 etcd/zk 这类现成的强一致存储做协调。

### 3. 分布式事务

跨服务/跨库的写操作要保证原子性（全成或全失败）。方案：
- **2PC（两阶段提交）**：协调者先让所有参与者"准备"（锁定资源）、再"提交"。强一致但**阻塞**（协调者挂则参与者锁定卡住）、性能差。少用。
- **TCC（Try-Confirm-Cancel）**：业务层三阶段——Try（预留资源）、Confirm（确认）、Cancel（回滚）。需要业务为每个操作实现 try/cancel 接口，侵入大但性能好、最终一致。
- **Saga**：把长事务拆成一系列**可补偿的子事务**，失败时按反序补偿。适合长流程（订单、跨服结算）。
- **本地消息表 / 事务消息（RocketMQ）**：在本地事务里同时写业务数据 + 一条"消息"，本地事务保证两者原子；消息异步发出去触发下游，下游幂等消费。**最终一致**，游戏跨服最常用。

游戏实践：**核心跨服写用"本地消息表 + 幂等消费 + 对账"**（最终一致、简单可靠），强一致强事务场景才上 TCC/Saga。

### 4. 一致性哈希与分片负载均衡

分布式扩展靠分片，分片的路由靠**一致性哈希**（见第 4、7 章）：节点与 key 都映射到哈希环，key 顺时针找最近节点。加减节点只影响相邻一段 key（迁移少），配**虚拟节点**保证分布均匀。游戏用于：玩家路由到逻辑服分片、数据分库分表路由、分布式缓存。负载均衡的另两种：**轮询/最少连接**（无状态服务，任意实例均可）、**粘性/一致性哈希**（有状态，按 key 固定到实例）。

### 5. 容灾：主备 / 多活 / 异地

- **主备（master-slave）**：一主一备，主挂备顶。简单，但备平时不服务（资源浪费），切换有窗口。
- **双主/多主**：多主都可读写，冲突解决复杂。
- **同城多活**：同城多机房，延迟低，任一机房故障其他接管。
- **异地多活**：异地机房（距离远、延迟高），按地域分流 + 数据同步。最强容灾（机房级/城市级故障都能扛），代价是数据同步延迟与一致性问题。
- **数据复制**：主从复制（异步，主挂可能丢少量数据）、同步复制（强一致但慢）、多数派写入（Raft 思路）。

游戏容灾：核心服务**主备/同城多活**（故障自动转移），数据按 RPO（可丢数据量）/RTO（恢复时间）要求定复制策略。异地多活多用于超大规模/合规要求。

### 6. 限流、熔断、降级

保护系统不被流量打垮的三大手段：
- **限流（rate limiting）**：控制进入系统的请求速率。算法：**令牌桶**（匀速发令牌、允许突发）、**漏桶**（匀速流出、平滑）、**滑动窗口**（精确控流）。按维度：单机/集群、按 IP/账号/接口。
- **熔断（circuit breaker）**：下游服务异常率超阈值时"熔断"（直接快速失败，不再调用），过一段时间"半开"试探恢复。防止**雪崩**——下游慢导致上游线程堆积、连带拖垮。
- **降级（degradation）**：过载时关闭/简化非核心功能（如关闭排行榜实时更新、聊天限频），保住核心。要有预案与开关（配置化，运营/自动触发）。

三者配合：**限流防过载、熔断防雪崩、降级保核心**。

### 7. 脑裂（split-brain）

**脑裂**：集群节点间网络分区，导致两个子集各自认为对方挂了、**各自选出主**，出现"双主"，数据分叉冲突。避免：① **多数派（quorum）**——只有获得过半节点支持才能当主（Raft/Paxos 的核心），少数派无法选主，避免双主。② **fencing（隔离）**——新主上任前先 fence 旧主（强制其停服务，如 STONITH 关电源、租约过期），保证只有一个主能写。③ **租约（lease）**——主靠租约维持身份，租约过期自动失主。脑裂是分布式高可用的头号风险，必须靠多数派/fencing 兜底。

## 面试题

### 【专家】深挖追问 · CAP 与游戏取舍

> 讲讲 CAP。游戏服务端在 C 和 A 之间怎么取舍？给例子。

**参考思路**：CAP——分区（P）不可避免时，一致（C）与可用（A）二选一。游戏**大多选 AP（最终一致）**——玩家体验优先可用，不能因一致性问题拒绝服务/卡服，容忍短时不一致。例：排行榜延迟几秒更新、跨服数据异步同步、聊天消息最终到达。但**关键数据选 CP/强一致**——账务、交易、充值不能错账（宁可短暂不可用也要一致）。所以同一系统内**按数据敏感度分层**：账务/交易强一致、排行榜/社交最终一致。本质：**对一致性问题敏感的（钱）保 C，对可用性敏感的（体验）保 A**。

**考点解析**：CAP 的实质（分区时 C/A 二选一）、游戏按数据敏感度分层取舍。资深要能举例而非背定理。

**常见误区**：背 CAP 不懂落地；以为游戏必须强一致（多数最终一致即可）；一刀切选 C 或 A。

**追问方向**：跨服排行榜用最终一致，玩家会不会看到"上一秒我是第一、刷新变第三"？怎么缓解？（短窗口不一致是最终一致的代价；缓解靠缩短同步延迟、或给前列实时一致、尾部近似。）

### 【专家】权衡 · Raft 与共识

> Raft 怎么工作？游戏里共识用在哪？为什么一般不自己实现？

**参考思路**：Raft——选一个 **leader**，所有写请求经 leader、leader 把**日志复制**到 follower、**过半（quorum）确认**才算提交。leader 故障，follower 超时未收到心跳则触发**选主**（任期 term 递增、获过半票者当选）。Raft 把共识拆成"选主 + 日志复制 + 安全性"，比 Paxos 易理解易实现。游戏里共识用在哪：**选主**（主备切换）、**强一致元数据**（服务发现、配置、分布式锁）——通常用 etcd（Raft）/ZooKeeper（ZAB）这类现成强一致存储，而非自己实现。为什么不自实现：共识算法正确性极难（边界情况多）、实现易出致命 bug、有成熟现成的。判据：**业务需要强一致协调时用 etcd/zk，别自己造共识轮子**。

**考点解析**：Raft 的 leader+日志复制+quorum、选主机制、用 etcd/zk 而非自实现。资深要能讲清"共识难、用现成的"。

**常见误区**：想自己实现共识（踩坑）；以为 Raft 解决所有一致性问题（它解决共识/线性一致，业务最终一致另说）；混淆 Raft（共识）与分布式事务（跨服务原子写）。

**追问方向**：Raft 的 quorum 是过半，为什么？（过半保证任意两个多数派集合必有交集（一个已提交的日志必在多数派里），新 leader 必含已提交日志，保证一致性；这是多数派的核心数学性质。选举时比较候选日志的 lastTerm/lastIndex，落后者得不到多数票，从而保证已提交日志不丢。）

### 【专家】系统设计 · 分布式事务选型

> 跨服操作（如跨服交易、跨服发奖）要保证原子性。2PC/TCC/Saga/本地消息表怎么选？

**参考思路**：
- **2PC**：强一致但**阻塞**（协调者挂则参与者锁死）、性能差。游戏几乎不用（阻塞不能接受）。
- **TCC**：Try（预留）→Confirm/Cancel，业务侵入大（每操作实现 try/cancel）但性能好、最终一致。适合**短流程、高一致要求**（如扣减库存类）。
- **Saga**：拆成可补偿子事务链，失败反序补偿。适合**长流程**（订单、跨服结算）。
- **本地消息表/事务消息**：本地事务里同时写业务 + 消息（原子），消息异步触发下游、下游幂等消费。**最终一致、简单可靠**。游戏**跨服最常用**——简单、不阻塞、配合对账兜底。
选型：**默认本地消息表 + 幂等 + 对账**（覆盖 90% 跨服场景）；强一致短事务用 TCC；长流程用 Saga；2PC 基本不用。

**考点解析**：四种方案的特性与适用、游戏首选本地消息表。资深要能按场景选并说清代价。

**常见误区**：跨服用 2PC（阻塞）；不考虑幂等（消息重发导致重复处理）；无对账（最终一致可能漂移）。

**追问方向**：本地消息表方案，消息发出去但下游处理失败/没消费，怎么办？（消息表持久化 + 重试 + 死信告警；下游幂等保证重复消费无害；长时间未消费的对账介入。）

### 【专家】故障复盘 · 跨服数据不一致

> 玩家跨服战斗赢了、奖励却没到本服（或重复发了）。怎么排查与防范？

**参考思路**：根因多是跨服结果**回流丢失/重复**或**应用非幂等**。排查：① 看**消息链路**——跨服战斗服是否发了结果消息、本服是否收到、是否处理（消息队列/日志追溯）。② 看**幂等**——本服是否按唯一战斗 id 去重（重复消息重复发奖 = 非幂等）。防范：① **可靠消息**——结果回流走持久化消息队列 + 确认 + 重试，不丢。② **幂等应用**——本服按唯一战斗 id 去重，重复消息不重复发奖。③ **对账**——定期比对跨服战斗记录与本服发奖记录，发现缺失/多发的补偿。④ **可观测**——跨服结果回流成功率监控、异常告警。本质：**最终一致靠"可靠消息 + 幂等 + 对账"三件套**，不能靠"发一次就完事"。

**考点解析**：回流丢失/重复的根因、可靠消息+幂等+对账三件套。资深要能讲清"最终一致必须兜底"。

**常见误区**：跨服结果发一次不确认（丢就丢）；本服不幂等（重发重复发奖）；无对账（漂移无感知）。

**追问方向**：对账发现某玩家奖励多发了一份，怎么处理？（幂等键去重避免再发；已发的按业务定——能回收则回收（扣回）、不能则记录坏账 + 风控；根本是修幂等 bug。）

### 【进阶】原理辨析 · 限流算法

> 令牌桶、漏桶、滑动窗口限流各是什么？怎么选？

**参考思路**：
- **令牌桶**：匀速往桶里放令牌（容量上限），请求消耗令牌；桶空则拒绝。**允许突发**（桶满时一次性消费多个令牌），适合**容忍短时突发**的场景。
- **漏桶**：请求进桶、匀速漏出处理；超桶容量的拒绝。**平滑输出**（不管输入多突发，输出匀速），适合**严格限速**（保护下游）。
- **滑动窗口**：统计最近时间窗口内请求数，超阈值拒绝。精确控流，可按窗口细化。
游戏：入口限流常用令牌桶（容忍突发）、保护下游用漏桶（平滑）、按账号/IP 防刷用滑动窗口。集群限流要把计数放 Redis（原子计数）或用专门限流服务。

**考点解析**：三种算法的特性（突发 vs 平滑 vs 精确）。资深要能按需求选。

**常见误区**：用错算法（需平滑却用令牌桶突发）；单机限流无法应对集群；计数非原子（并发不准）。

**追问方向**：集群限流怎么实现？（计数放 Redis，每次请求原子 INCR + 判断；或用专门的限流服务统一判断；注意 Redis 故障时的降级策略。）

### 【专家】系统设计 · 熔断与降级

> 怎么设计熔断和降级，保护系统不被下游/流量拖垮？

**参考思路**：
- **熔断**：对每个下游调用维护状态（closed/open/half-open）。**closed**（正常）调下游、统计失败率；失败率超阈值 → **open**（熔断，直接快速失败，不再调下游，避免线程堆积）；过冷却时间 → **half-open**（放少量请求试探），成功则回 closed、失败则回 open。防**雪崩**——下游慢导致上游线程池耗尽、连带崩溃。
- **降级**：过载或异常时关闭/简化非核心功能。预案：排行榜降级为缓存/定时、聊天限频、非核心 RPC 直接返回默认、关闭表现功能。**配置化开关**（运营手动或自动触发），保住核心（登录/战斗/交易）。
设计要点：**每个下游调用都要有超时 + 熔断**；**核心链路不依赖非核心**（非核心降级不影响核心）；降级开关配置化、可热更；监控各调用成功率，自动触发熔断/降级。

**考点解析**：熔断三态、防雪崩、降级保核心、配置化。资深要能讲清"每个下游都要超时+熔断"。

**常见误区**：调用下游无超时（一个慢拖全局）；无熔断（雪崩）；降级写死不可配（无法应对突发）。

**追问方向**：熔断 half-open 时放多少请求试探？（少量——如 1 个或很小比例，既探测恢复又不过载；成功才逐步恢复流量。）

### 【专家】深挖追问 · 脑裂

> 什么是脑裂？怎么发生？怎么避免？

**参考思路**：脑裂——集群网络分区，两个子集互相看不到、各自认为对方挂了、**各自选出主**，出现双主，两边各自写入导致数据分叉冲突。发生：网络分区/网线断/交换机故障。避免：① **多数派（quorum）**——只有获**过半节点**支持才能当主，少数派无法选主，保证至多一个主（Raft/Paxos 的核心）。② **fencing（隔离）**——新主上任前先 fence 旧主（强制其停服务，如租约过期、STONITH 关电源、磁盘锁），保证旧主不能再写。③ **租约（lease）**——主靠带期限的租约维持身份，租约过期自动失主，分区时少数派侧的旧主租约过期即失效。脑裂是分布式头号风险，多数派 + fencing 是标准兜底。

**考点解析**：脑裂成因（分区+双主）、多数派防双主、fencing 隔离旧主。资深要能讲清"为什么多数派能防双主"。

**常见误区**：以为主备就不会脑裂（异步复制+分区仍可能双主）；不用多数派（双主）；不 fencing（旧主继续写）。

**追问方向**：主备数据库（如 MySQL 主从）切换时怎么防脑裂？（多数派/仲裁节点判断、fencing 旧主、或人工确认；纯主备无仲裁时切换要谨慎，靠工具（MHA/Orchestrator）做 fencing。）

### 【进阶】权衡 · 主备 vs 多活

> 游戏容灾用主备还是多活？各适合什么？

**参考思路**：
- **主备**：一主一备（或多备），主服务、备待命。主挂、备顶（自动或人工）。简单、资源省（备平时不服务）；切换有窗口（秒~分）、备可能数据略滞后（异步复制丢少量）、资源利用率低。
- **多活（同城/异地）**：多机房同时服务，流量分担，任一机房故障其他接管。可用性高、切换快（甚至无感）、资源利用率高；代价是**数据同步延迟 + 一致性问题**（多活的数据同步是难点）、架构复杂、成本高。
游戏：**核心服务主备/同城多活**（故障自动转移、RTO 短），按 RPO/RTO 要求定复制策略。异地多活用于超大规模或合规（机房级/城市级容灾）。多数项目从主备起步、按可用性要求升级到多活。判据：**按 RTO（恢复时间）/RPO（可丢数据）与成本权衡**。

**考点解析**：主备（简/省/有窗口）vs 多活（高可用/复杂/贵）。资深要能按 RTO/RPO 选。

**常见误区**：以为主备就高可用（切换窗口 + 数据滞后）；盲目上多活（成本/复杂度爆炸）；不明确 RTO/RPO 指标。

**追问方向**：多活的数据同步怎么做？（同步复制（强一致但慢）、异步复制（快但滞后）、或按业务分——核心强一致、非核心异步；异地多活常用"单元化"（按地域分单元、单元内自洽）。）

### 【专家】系统设计 · 全服排行的最终一致

> 全服排行榜跨多服数据，怎么做到最终一致且实时性可接受？

**参考思路**：① **各单服维护本地玩家分数**（玩家在单服的活动产出）。② **增量上报**——单服把分数变化异步上报给全服排行服务（消息/定期）。③ **全服排行服务**用 Redis ZSET 聚合，提供全服排名查询。④ **最终一致**——分数变化经异步链路有延迟（秒级），但最终收敛一致。⑤ **对账**——定期全量比对各服与全服排行，修正漂移。⑥ **实时性分级**——前列（前百）可强制近实时（关键变化立即上报），尾部容忍延迟。本质：**最终一致 = 增量异步同步 + 对账兜底**，配合实时性分级控制成本。

**考点解析**：增量异步同步、ZSET 聚合、对账兜底、实时性分级。资深要能设计最终一致的全局聚合。

**常见误区**：全服实时强一致（成本爆炸）；无对账（漂移）；所有数据同等实时（浪费）。

**追问方向**：异步上报消息丢了导致全服排行漏更新，怎么办？（可靠消息 + 重试；周期对账兜底修正；关键变化（登顶/破纪录）可靠传。）

### 【进阶】原理辨析 · 幂等性

> 为什么分布式系统必须幂等？怎么实现？

**参考思路**：分布式里**消息/请求可能重复**（网络重传、重试、at-least-once 投递、故障恢复重放）。如果处理不幂等（如"加 100 金币"重复执行两次就加了 200），数据就错。所以**所有可能重复的操作必须幂等**——重复执行结果与一次执行相同。实现：① **唯一业务 id 去重**——每操作带唯一 id，处理方记录已处理 id，重复的跳过（用 DB 唯一键/Redis SETNX/状态机判断）。② **状态机**——操作只在特定状态下生效（如"领奖"只在"未领"状态生效，重复请求发现已领则跳过）。③ **乐观锁/版本号**——带版本号，重复操作版本不匹配则跳过。游戏里：发奖、充值回调、跨服结果、消息消费都必须幂等。

**考点解析**：重复不可避免、幂等的必要性、去重/状态机/版本号实现。资深要主动强调"分布式必须幂等"。

**常见误区**：以为消息只发一次（at-least-once 常态）；用"加法"而非"设值/状态机"；去重无持久化（重启丢已处理记录）。

**追问方向**：唯一 id 去重，已处理 id 表越来越大怎么办？（带 TTL 清理旧 id；或用业务状态判断替代 id 表——如"订单已发货"状态本身即幂等标志。）

### 【专家】权衡 · 强一致 vs 最终一致

> 游戏数据里，交易/排行榜/聊天/背包各该强一致还是最终一致？

**参考思路**：按**数据敏感度与可用性需求**分层：
- **交易/账务/充值**：**强一致**——钱不能错账，宁可短时不可用也要一致（CP）。本地事务 + 关键操作即时持久化。
- **背包/玩家档案**：**强一致**（玩家自己的数据，不能丢/错）——本地事务保证，单玩家数据聚合同分片。
- **排行榜**：**最终一致**——延迟几秒更新可接受，用异步同步 + 对账。
- **聊天/世界广播**：**最终一致/可丢**——消息延迟或偶丢可接受，重在可用与低延迟。
- **跨服战斗结果**：**最终一致**（可靠回流 + 幂等 + 对账），不要求强一致。
判据：**错不起的（钱/玩家核心数据）强一致；错得起的（排行/聊天/跨服）最终一致**。强一致成本高（事务/阻塞/可用性牺牲），只用在必须的地方。

**考点解析**：按数据敏感度分层选一致级别。资深要能给每类数据定一致性级别并说清理由。

**常见误区**：全强一致（成本爆炸、可用性差）；全最终一致（账务出错）；不区分数据敏感度。

**追问方向**：充值要求强一致，但支付平台回调可能延迟/重复，怎么平衡？（回调幂等去重 + 订单状态机（待支付→已支付→已发货），强一致在状态机内保证；延迟回调靠对账补偿。）

### 【专家】原理辨析 · 分布式锁

> Redis 锁、Redlock、ZooKeeper 锁各怎么做？游戏里怎么选？锁过期/主从切换丢锁怎么防？

**参考思路**：
- **Redis 单实例锁**：`SET key value NX PX 过期时间`，value 存唯一标识，释放用 Lua 校验 value 再删（防误删他人锁）。**坑**：① 业务超时未续期，锁过期被别人抢，出现双写；② 主从异步复制，主挂从晋升时锁丢失（主上锁未同步到从）。
- **Redlock**（多 Redis 节点加锁、多数派成功才算锁）：想解决单实例主从丢锁。但有争议（Martin Kleppmann 指其依赖时钟同步、GC 停顿仍可能双持），**对正确性敏感场景不可靠**。
- **ZooKeeper/etcd 锁**：用临时顺序节点/租约，session 断开自动释放，一致性靠 ZAB/Raft。**比 Redis 强（CP，不会丢锁）**，但延迟略高。
- **fencing token**：锁释放后再加一个单调递增 token，下游存储拒绝旧 token 的写——彻底防"持锁者暂停后双写"。
游戏选型：**对一致性要求高（防双写关键）用 ZK/etcd 锁 + fencing**；性能优先、容忍偶发双写用 Redis 锁（务必设合理过期 + 看门狗续期）。**别用 Redlock 当强锁**。

**考点解析**：Redis 锁的两类坑、Redlock 争议、ZK 锁的 CP 保证、fencing token 的作用。资深要能按一致性需求选锁并说清代价。

**常见误区**：Redis 锁当强锁用（过期/主从切换丢锁）；释放锁不校验 value（误删他人锁）；无续期（长任务锁过期双写）；迷信 Redlock。

**追问方向**：业务执行时间超过锁过期，怎么避免双写？（看门狗定时续期；或根本缩短临界区；或用 fencing token 让旧持锁者写无效。）

### 【进阶】原理辨析 · 全局唯一 ID

> 全服要按唯一 id 去重（发奖/充值回调/跨服结果），这个 id 怎么生成？雪花算法时钟回拨怎么办？

**参考思路**：
- **UUID**：本地生成、无中心、不重复；但**长、无序**（作 DB 主键/索引差），不推荐作业务 id。
- **号段模式**：发号器批量从 DB 取一段 id 缓存到本地发放，用完再取。高性能、趋势递增；DB 挂则发不出（双 buffer 预取缓解）。
- **Snowflake（雪花）**：`时间戳 + 机器id + 序列号`，64 位，趋势递增、本地生成、性能高。**核心坑：时钟回拨**——机器时间往回拨，会生成重复或未来 id。应对：① 回拨小则**等待**（等追上）；② 回拨大则**报错拒绝**；③ 借用机器位（每机房多分配 worker 抵御）；④ 用 NTP 合理配置（禁大步回拨）。
游戏：**跨服结果/充值回调/发奖用 Snowflake 或号段模式**生成唯一 id，配合幂等去重闭环；机器 id 由 etcd/ZK 统一分配避免冲突。

**考点解析**：Snowflake 各段含义、时钟回拨的应对、号段 vs Snowflake 取舍。资深要能说清"唯一 id 从哪来"。

**常见误区**：用自增主键当全局 id（分库分表后冲突）；Snowflake 不处理时钟回拨（重复 id）；机器 id 硬编码（扩容冲突）。

**追问方向**：号段模式发号器宕机，怎么保证不重发不漏发？（双 buffer 预取下一段、宕机前已持久化步长，重启从持久化点续发；用 DB 事务保证取号原子。）

---

> **本章小结**：分布式与高可用的主线是"**按数据敏感度分层一致性（钱强一致、体验最终一致）+ 共识/事务保证关键一致 + 限流熔断降级保可用 + 多数派/fencing 防脑裂 + 最终一致靠幂等+对账兜底**"。记住三条铁律：**CAP 是分区时的硬权衡，不是选择题而是取舍题**；**分布式必须幂等，重复不可避免**；**最终一致必须配对账兜底，否则会漂移**。这套能力是资深架构岗的硬核。
