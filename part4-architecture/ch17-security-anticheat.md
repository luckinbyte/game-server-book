# 第17章 安全与反作弊

> 游戏服务端是攻击者的目标——作弊者想刷道具/作弊赢、工作室想刷金牟利、黑客想拖库。反作弊的根基是**服务端权威 + 客户端不可信**，配合协议安全、行为检测、漏洞加固。本章讲清游戏安全威胁模型与反作弊体系，是主程/架构岗的高频考点。

## 原理体系

### 1. 威胁模型

游戏安全的攻击面：
- **客户端篡改**：改本地数据/逻辑（加速、改伤害、改坐标）。
- **协议攻击**：抓包/重放/篡改/伪造协议。
- **服务端漏洞**：SQL 注入、越权、逻辑漏洞（刷道具/刷金币）。
- **自动化**：脚本/外挂/工作室批量操作。
- **信息窃取**：拖库、账号盗取。

防御心法：**客户端永远不可信，服务端是唯一权威**。所有影响真实结果（伤害/位置/掉落/经济）的判定必须在服务端，客户端只是表现。

### 2. 服务端权威（反作弊根基）

呼应第 9、10 章：服务端跑权威逻辑——伤害/命中/碰撞/位置/掉落/经济都在服务端算。客户端篡改本地数据（改坐标穿墙、改伤害秒杀）只是"自己看到的假画面"，不影响服务端维护的真实状态，其他玩家与最终结算以服务端为准。这是反作弊的**第一原则**。代价：服务端算力压力大。所以服务端用**简化模型**判定（AABB/射线/范围校验），不必照搬客户端完整物理。

### 3. 协议安全：加密、防重放、防篡改

- **加密**：传输加密（TLS 或自研对称加密 AES），防**窃听/抓包逆向**。注意：加密防窃听，**不防客户端自造数据**（客户端有密钥就能伪造合法加密包）——所以加密只是协议安全的一部分。
- **防重放**：每包带 **nonce/序号 + 时间戳**，服务端拒绝重复/过时包（防止抓到的包被重复提交刷操作）。
- **防篡改**：每包带 **MAC（消息认证码）/签名**，篡改内容则校验失败。
- **协议混淆/频繁变更**：增加逆向难度（但挡不住有决心的人，主要是抬高门槛）。

协议安全的现实：**只要客户端持有密钥，理论上客户端能伪造任何合法包**——所以协议安全主要是防窃听/防重放/防被动篡改/抬高逆向门槛，**真正的反作弊要靠服务端权威 + 行为检测**。

### 4. 常见作弊类型与检测

- **加速（speed hack）**：改本地时钟或移动速度，移动/攻击比别人快。检测：服务端按**服务端时间 + 速度上限**校验玩家位移——单位时间位移超过速度上限即判异常。靠服务端权威时间与位置，不信任客户端上报的"我走了这么远"。
- **穿墙/瞬移**：改坐标穿过障碍。检测：服务端跑碰撞判定，玩家移动路径穿墙即拒绝/纠正。
- **透视（wallhack）**：看到本不该看到的敌人位置。本质是**信息泄露**——客户端拿到了不该有的数据。防御：**服务端按 AOI 只发玩家视野内的实体**（见第 9 章），不该看到的不下发——客户端没数据就没法透视。
- **自动瞄准（aimbot）/脚本**：客户端辅助瞄准/自动操作。难直接防（看起来是"操作快"），靠**行为统计**（反应时间分布异常、操作精度异常、24 小时不间断）检测。
- **内存修改**：改客户端内存（改血量/改金币显示）。服务端权威下只影响本地显示，不影响真实；可加反调试/内存校验增加难度。

### 5. 数值校验

服务端对所有客户端影响的状态变更做**合理性校验**：
- **范围校验**：伤害/移动距离在合理范围内。
- **频率校验**：操作频率（攻击/移动）不超过上限。
- **状态校验**：操作前置条件满足（CD 到了？蓝量够？在合法位置？）。
- **资源校验**：消耗/获得的资源与规则一致。
校验失败则拒绝 + 记录（累计异常触发封禁）。校验要**服务端权威**，不能信客户端上报。

### 6. 风控与异常行为检测

针对脚本/工作室/批量作弊：
- **行为统计**：操作频率/时长/分布异常（24 小时无间断、毫秒级反应、轨迹完全一致）。
- **设备/账号指纹**：多账号同设备、批量注册特征。
- **经济异常**：异常的金币/道具流转（工作室刷金→集中→交易）。
- **机器学习**：训练模型识别异常行为模式。
- **人工审核 + 举报**：玩家举报 + 客服审核兜底。
风控是**统计 + 规则 + ML + 人工**的多层体系，误封与漏封要平衡（见下文题）。

### 7. 服务端漏洞加固

服务端自身的安全基本功：
- **SQL 注入**：用参数化查询/预编译，绝不字符串拼接 SQL。
- **越权**：每个操作**鉴权 + 校验资源归属**（玩家只能操作自己的数据，不能改 id 操作别人）。水平越权（同权限改别人）、垂直越权（普通用户调管理员接口）都要防。
- **逻辑漏洞**：刷道具/刷金币的业务逻辑漏洞（如重复领奖、负数购买、整数溢出）。靠代码审查 + 模糊测试 + 校验。
- **输入校验**：所有外部输入（客户端、API）校验长度/类型/范围。
- **最小权限**：服务/DB 账号最小权限，限制爆炸半径。
- **依赖安全**：第三方库漏洞（及时更新、SCA 扫描）。

### 8. DDoS/CC 防护

游戏服务端是公网高暴露目标，DDoS/CC（流量洪水、协议层洪水、慢速连接耗连接数）是资深架构岗高频问点：
- **网络/接入层**：高防 IP / Anycast 清洗（近源清洗流量洪水）、CDN/边缘节点吸收、按地区/运营商分流。
- **协议层前置认证**：未通过握手/认证的连接不进业务逻辑（防止裸连接洪水占资源）；首包 nonce/握手校验前置，过滤伪造包。
- **限流与配额**：按账号/IP/设备维度限流（令牌桶/漏桶），关键接口单独配额；慢速连接设超时 + 连接数上限。
- **业务层过滤**：异常请求特征（频率/分布）在网关层拦截，业务层只处理已清洗流量；服务端降级/熔断保护核心链路。
- **弹性容量**：攻击时弹性扩容 + 非核心功能降级（排行榜/聊天可挂，战斗/登录保住）。
游戏服务端 DDoS 防护是**清洗 + 限流 + 协议前置认证 + 业务降级**的多层纵深，单纯堆带宽扛不住协议层攻击。

### 9. 账号与认证安全

账号盗取（撞库、拖库、会话劫持）是威胁模型 L14 的直接相关项：
- **密码存储**：用慢哈希（bcrypt/argon2/scrypt）加盐，**绝不明文/裸 MD5**；argon2 为当前推荐。
- **防撞库**：登录限流（IP/账号维度）、失败锁定/验证码、异地登录二次验证；泄露密码库比对告警。
- **会话/Token 安全**：登录后下发会话 Token（JWT/自研），防会话固定（每次登录换 session id）、Token 有过期 + 刷新机制、泄露可吊销；HTTPS 传输防中间人。
- **多端登录与挤下线**：定义单端/多端策略，新登录挤旧会话时安全下线旧 Token；防止会话长期挂留被劫持。
- **二次验证**：敏感操作（改密/交易/解绑）二次校验（短信/TOTP/邮箱）。

### 10. 隐私与合规

玩家个人数据（账号、行为）的收集/存储/使用要合规（GDPR/个保法）：最小化收集、加密存储、访问审计、玩家权利（查询/删除）。抽卡概率公示、未成年人保护等法规要求。

## 面试题

### 【专家】深挖追问 · 服务端权威是反作弊根基

> 为什么说"服务端权威"是反作弊的第一原则？客户端篡改怎么防？

**参考思路**：客户端不可信——玩家完全控制自己的客户端（改内存、改逻辑、改协议）。如果关键判定（伤害/位置/掉落）放客户端，玩家就能篡改刷结果。**服务端权威**：所有影响真实结果的判定在服务端算，客户端只是表现。客户端篡改本地数据（改伤害秒杀、改坐标穿墙）只影响"自己看到的假画面"，不改服务端维护的真实状态——其他玩家与结算以服务端为准，作弊无效。防客户端篡改的本质就是"**不信任客户端、一切以服务端为准**"。代价是服务端算力（用简化判定模型）。

**考点解析**：客户端不可信、服务端权威、客户端篡改无效化的原理。资深要能讲清"为什么判定不能放客户端"。

**常见误区**：让客户端上报伤害/位置（必被篡改）；以为加密协议就防作弊（只防窃听）；把判定放客户端为省服务端算力。

**追问方向**：有些表现（如特效、镜头）放客户端不影响公平，怎么划界？（影响"真实结果"的（伤害/命中/位置/掉落）服务端；纯"观感"的（特效/音效/镜头）客户端。判据：能不能影响别人/结算。）

### 【专家】系统设计 · 协议加密防重放防篡改

> 怎么设计协议安全：防窃听、防重放、防篡改？

**参考思路**：
- **防窃听（加密）**：TLS 或自研对称加密（AES-GCM，带认证的加密模式）。会话密钥在登录握手时协商（非对称加密交换对称密钥）。
- **防重放**：每包带**序号 + 时间戳 + nonce**，服务端维护"已见序号/时间窗口"，拒绝重复/过时包。关键操作（购买/释放）尤其要防重放。
- **防篡改（认证）**：用带认证的加密（AEAD，如 AES-GCM 自带 MAC）或单独 HMAC，篡改内容则校验失败。
- **协议混淆**：增加逆向难度（但非主要防线）。
现实：客户端持有密钥，理论上能伪造合法加密包——所以协议安全主要是**防窃听/防重放/防被动篡改/抬高门槛**，真正反作弊靠服务端权威 + 行为检测。

**考点解析**：加密/防重放/防篡改三层、AEAD 一体化、协议安全的局限（客户端有密钥）。资深要能讲清"协议安全不等于反作弊"。

**常见误区**：以为加密就防作弊；防重放只靠时间戳（要序号+窗口）；用未认证的加密（可被篡改）。

**追问方向**：会话密钥怎么安全协商？（登录时用非对称（RSA/ECDH）协商对称会话密钥，后续用对称加密；密钥不长期固定、按会话动态。）

### 【专家】故障复盘 · 加速外挂

> 玩家用加速外挂（改本地时钟/移动速度），怎么检测与防？

**参考思路**：加速的本质是"单位时间做了更多事"（移动更远、攻击更快）。防御靠**服务端权威时间与上限校验**：① **移动校验**——服务端按自己的时间 + 玩家速度上限，校验客户端上报的位移：`实际位移 / 时间 > 速度上限` 则判异常（拒绝/纠正位置）。② **操作频率校验**——攻击/技能频率不超规则上限。③ **不信任客户端的时间**——用服务端时间作为权威，客户端的"我过了 1 秒"不可信。④ **累计异常**——偶发网络抖动可能误判，累计多次异常才封禁。核心：**用服务端权威时间 + 规则上限兜底，而非信任客户端时钟**。

**考点解析**：加速的本质（单位时间多做）、服务端时间权威 + 上限校验、累计异常防误判。资深要能讲清"为什么不信客户端时间"。

**常见误区**：信客户端上报的时间/位移；一次异常就封（误判）；只校验移动不校验操作频率。

**追问方向**：玩家网络好（低 RTT）确实比别人快一点，会不会被误判加速？（靠合理余量 + 累计判定，单次轻微超限不判；真加速是持续大幅超限，统计可区分。）

### 【专家】深挖追问 · 透视（信息泄露）

> 透视外挂怎么实现？怎么防？

**参考思路**：透视的本质是**客户端拿到了本不该有的敌人位置数据**，外挂读取并渲染出来。所以防御在**源头**——**服务端按 AOI 只下发玩家视野内该看到的实体**（见第 9 章），墙后/超视野的敌人**根本不下发给该客户端**。客户端没数据，透视外挂就读不到。这是"信息最小化"原则——**只给客户端它该知道的信息**。代价：服务端要做精确的可见性判定（不只是距离，还要遮挡判定——墙后的不发），算力开销。无法 100%（总有视野内的），但能把透视限制在"本就该看到的"范围内。

**考点解析**：透视=信息泄露、防御靠服务端 AOI/可见性裁剪、信息最小化原则。资深要能讲清"防透视是防信息下发，不是防客户端读"。

**常见误区**：全发实体让客户端自己裁剪（必被透视）；只按距离不按遮挡发；以为加密能防透视（数据到了客户端就能读）。

**追问方向**：精确遮挡判定（墙后不发）算力大，怎么平衡？（简化遮挡判定——粗粒度可见性 + 关键场景精判；或容忍少量信息泄露换算力，按游戏类型定。）

### 【进阶】权衡 · 数值校验的取舍：纠正还是踢线，模拟还是逐入口

> 客户端预演校验失败时，服务端该"纠正+继续"还是"直接踢线"？再往上一步：服务端是做"逐入口校验"还是干脆"服务端模拟推导免校验"？怎么权衡？

**参考思路**：校验位置毫无疑问在**服务端**（客户端校验不可信，只算体验优化）——这是反作弊入门共识，无需展开。真正资深向的取舍在两条轴上：① **校验内容五类**——范围（防负数/防超大）、频率（防加速/防刷）、状态（CD/蓝量/位置/解锁前置）、资源（消耗/获得对账）、一致性（客户端上报 vs 服务端推算）。② **失败处置策略**——纠正并继续（容错好、但放过了边缘作弊）vs 直接踢线（零容忍、但网络抖动/bug 误踢率高）。常规落法：高频/低危（移动越界）"纠正+记录"，关键/高危（交易/掉落/付费）"拒绝+计异常"，累计异常才封。③ **校验实现路线**——"逐入口校验"（侵入性高、易漏入口、但通用）vs "服务端模拟推导"（服务端自己跑权威逻辑，客户端上报只作输入意图，从根本免校验；代价是算力 + 输入延迟，靠预测/和解弥补）。后者更根治但更重，按业务关键度分层选用。

**考点解析**：校验失败处置的纠正/踢线权衡、逐入口校验 vs 服务端模拟推导两条路线的算力/侵入性/可靠性取舍、分级处置。资深要能讲清"校验在哪做是常识，怎么做、失败怎么办才是取舍"。

**常见误区**：一次校验失败就踢线（误踢率高）；所有校验同等对待（高频操作把服务端打挂）；只走逐入口校验不评估模拟推导（漏入口即被刷）；把判定放客户端为省算力。

**追问方向**：服务端模拟推导要做到什么粒度才真能免校验？（关键判定——伤害/命中/位置/掉落/经济——必须服务端权威算；客户端上报只作"意图"。若服务端对某类结果依赖客户端上报，那条链路仍需逐入口校验兜底。模拟推导的代价怎么摊？（只对关键/对局精算，高频表现降频或抽样。））

### 【专家】系统设计 · 异常行为检测/风控

> 怎么发现脚本/工作室/批量作弊？

**参考思路**：多层体系：① **行为统计**——操作频率/时长/分布异常（24h 不间断、毫秒级反应、轨迹完全重复、无社交）。② **设备/账号指纹**——多账号同设备、批量注册特征（IP 段、注册时间集中、设备指纹一致）。③ **经济异常**——异常金币/道具流转（刷金→集中账号→交易变现的模式）。④ **网络特征**——多账号同 IP/代理池。⑤ **机器学习**——训练模型识别异常模式（无监督聚类找离群、监督分类）。⑥ **人工审核 + 玩家举报**兜底。风控是**规则 + 统计 + ML + 人工**的多层体系，对疑似账号分级处置（观察/限制/封禁），平衡误封与漏封。

**考点解析**：多层风控（规则/统计/指纹/经济/ML/人工）、分级处置。资深要能讲清"没有单一银弹，靠组合 + 分级"。

**常见误区**：靠单一指标（易误判/易绕过）；不分级一刀切封（误封多）；忽略经济流转模式（工作室特征）。

**追问方向**：风控误封了正常玩家，怎么处理？（申诉通道 + 人工复核 + 解封补偿；降低自动封禁阈值、改"限制"代替"封禁"过渡；持续优化规则减少误判。）

### 【进阶】故障复盘 · 越权漏洞

> 玩家通过改请求参数（如把 target_id 改成别人）操作了别人的数据。怎么防？

**参考思路**：这是**水平越权**——同权限级别的用户 A 操作了用户 B 的数据。防御：① **每个操作鉴权 + 校验资源归属**——不仅验证"你是登录用户"，还要验证"你要操作的资源属于你"（如删背包道具：校验该道具 id 属于当前玩家）。② **不信任客户端传的归属标识**——target_id/user_id 这类参数要与服务端会话身份比对，不一致即拒绝。③ **用会话身份推导归属**——优先从服务端会话（token→玩家 id）取归属，而非客户端传。④ **接口最小化**——不暴露不该暴露的操作/参数。⑤ **审计 + 测试**——越权测试（用 A 的身份调 B 的资源应失败）。水平越权（改别人）与垂直越权（普通用户调管理接口）都是常见高危漏洞。

**考点解析**：水平/垂直越权、资源归属校验、不信任客户端归属标识。资深要主动讲"每个操作都要校验归属"。

**常见误区**：只验登录不验归属；信任客户端传的 user_id；接口暴露过多参数。

**追问方向**：怎么系统性防越权？（框架层统一拦截——所有涉及资源的操作自动校验"资源归属当前会话用户"，业务代码不必各处手写；加越权自动化测试。）

### 【专家】权衡 · 反作弊的强度 vs 误封 vs 性能

> 反作弊做太严会误封正常玩家、太松防不住，还要考虑服务端性能。怎么平衡？

**参考思路**：三方权衡：① **强度**——校验越严、检测越细，越能防作弊，但越易误判 + 越耗算力。② **误封**——严格规则可能误伤正常玩家（网络好、操作快的玩家）。③ **性能**——服务端全量精校验算力压力大。平衡手段：a) **分级处置**——不"一次判作弊即封"，而是"异常→观察→限制（如禁交易）→封禁"渐进，给正常玩家容错。b) **关键严、次要宽**——影响经济/公平的（交易/掉落）严校验，高频表现（移动）抽样/降频校验。c) **多指标综合**——不靠单一指标判定（易误判），多个异常综合才处置。d) **服务端模拟推导**——根本性减少对客户端上报的依赖（服务端自己算位置/伤害），从源头免校验。e) **申诉与复核**——给误封玩家出口。核心：**反作弊不是"严防死守一次性封"，而是"分层 + 渐进 + 综合 + 可申诉"**。

**考点解析**：强度/误封/性能三角、分级处置/关键严次要宽/多指标综合/服务端推导。资深要能讲清"反作弊是平衡的艺术"。

**常见误区**：追求绝对严格（误封多/性能崩）；单一指标判定（误判+易绕过）；无申诉通道（误封无解）。

**追问方向**：服务端"自己算位置/伤害"不依赖客户端上报，是不是最根治的反作弊？（基本是——服务端权威模拟推导，客户端上报只作"输入意图"（我要移动/攻击），结果服务端算，从根本上消除数值篡改。代价是算力 + 输入延迟（预测和解弥补）。）

### 【进阶】原理辨析 · 协议反逆向

> 加密 + 混淆 + 频繁换协议，能挡住外挂作者多久？

**参考思路**：协议反逆向只能**抬高门槛、拖延时间**，挡不住有决心的逆向者（客户端持有密钥/逻辑，理论上可被还原）。手段：① 加密（防简单抓包）；② 协议字段混淆/反汇编防护；③ 频繁变更协议结构（增加维护成本）；④ 反调试/反注入（增加客户端分析难度）。现实：每次更新后外挂作者会重新适配，形成"猫鼠游戏"。所以**协议反逆向是辅助手段**（抬高门槛、过滤低端外挂），**真正持久的反作弊靠服务端权威 + 行为检测**（这些不依赖协议保密）。不要把反作弊的希望全押在"协议保密"上。

**考点解析**：协议反逆向后抬高门槛、不持久、真正靠服务端权威+行为检测。资深要能讲清"协议保密不是反作弊的根基"。

**常见误区**：把反作弊全押在协议加密（更新后即破）；以为混淆能永久挡；忽视服务端权威的根本作用。

**追问方向**：客户端反调试/反注入有用吗？（有用——抬高分析门槛、过滤低端，但高端外挂仍能绕过；作为辅助手段，非主防线。）

### 【专家】系统设计 · 帧同步反作弊（重放校验）

> 帧同步怎么反作弊？服务端怎么校验？

**参考思路**：帧同步的特点是"相同输入 → 相同结果"，这给反作弊天然优势——**服务端可重放校验**：① 服务端记录所有玩家输入序列。② 周期性/抽查地，服务端（或专用校验节点）**用记录的输入重放模拟**，得到权威结果，与各客户端上报的状态哈希比对。③ 不一致即怀疑该客户端作弊/异常。④ 关键：**判定（伤害/死亡/胜负）以服务端重放结果为准**，客户端只是表现。这是帧同步反作弊的核心——服务端不信任客户端上报的结果，自己重放算权威。代价：服务端要跑模拟（算力），可只对关键对局/可疑客户端重放，不必全量。状态同步则靠"服务端本来就权威"反作弊。

**考点解析**：帧同步"相同输入相同结果"的反作弊优势、服务端重放校验、判定以服务端为准。资深要能讲清"帧同步反作弊比重放校验"。

**常见误区**：信任客户端上报的帧同步结果（可篡改）；服务端全量重放（算力爆）；不做状态哈希比对（无法发现不一致）。

**追问方向**：服务端重放发现某客户端 desync，是作弊还是网络/bug？（可能两者——先排除 desync 的常见技术原因（浮点/随机/迭代序，见第 9 章），排除技术原因后才倾向作弊；结合行为统计综合判定。）

### 【进阶】系统设计 · 游戏经济类逻辑漏洞体系化防御

> 游戏服务端真正高频高损的不是 SQL 注入（参数化查询已是常识），而是经济类逻辑漏洞——刷道具/刷金币/刷抽奖。这类漏洞怎么体系化防？

**参考思路**：SQL 注入用**参数化查询/预编译**防住即可（绝不字符串拼接、最小权限 DB 账号、ORM 默认参数化），不再展开。资深重心放在经济类逻辑漏洞的体系化防御——它们的共同特征是"产出/消耗接口被滥用"，防御要落到**幂等 + 原子 + 状态机**三件套：
- **幂等（重复领奖/刷道具）**：领奖/购买/签到这类接口必须幂等——用**幂等键（唯一业务 id）+ 状态机**：领过就不再发，领奖记录的唯一约束兜底。
- **原子操作（竞态/并发刷）**：高并发领奖/购买的常规落地不是"串行化/锁"，而是**幂等键 + Redis SETNX/原子 Lua + DB 唯一约束/乐观锁**——锁只是兜底而非首选，悲观锁全表会拖垮吞吐。典型：领奖前 SETNX 幂等键、Lua 原子扣资源+发奖、DB 唯一约束防重、乐观锁版本号兜底。
- **状态机（顺序绕过/跳步发货）**：付费/领奖流程用状态机约束流转，跳过付费步骤直接发货这类绕过被状态校验拦住。
- **负数/溢出（反向加钱/越界）**：购买数量、金额做范围校验（非负、不超上限、防 int 溢出）。
- **越权**（见上题）。
这些不是"黑客技术"，而是业务逻辑 bug，靠**代码审查 + 校验 + 模糊测试 + 状态机化 + 上线后经济监控**防。游戏的经济类漏洞比 SQL 注入更常见、损失更大。

**考点解析**：幂等键、原子操作（Redis Lua/DB 唯一约束/乐观锁）、状态机约束流转、范围校验防负数溢出。资深要能讲清"防竞态首选原子操作而非锁，锁只是兜底"，以及"游戏安全大头是经济类逻辑漏洞"。

**常见误区**：只防 SQL 注入忽视逻辑漏洞；防竞态一上来就悲观锁全表（吞吐崩）；领奖/购买非幂等；输入不校验范围；漏掉状态机让流程可跳步。

**追问方向**：怎么系统性发现逻辑漏洞？（威胁建模——对每个"产出/消耗"接口列"怎么被刷"；模糊测试（异常/并发输入）；代码审查关注资源变更链路；上线后经济监控——异常产出/集中流转告警。）

### 【专家】系统设计 · DDoS/CC 防护体系

> 游戏服务端是公网高暴露目标，被 DDoS（流量洪水）或 CC（协议层/慢速连接）攻击，怎么设计防护？

**参考思路**：分层纵深，每一层挡不同攻击：① **接入/网络层**——高防 IP / Anycast 近源清洗流量洪水，CDN/边缘节点吸收，按地区/运营商分流；大流量反射放大靠上游清洗，业务机房扛不住。② **协议层前置认证**——未通过握手/首包 nonce 校验的连接不进业务逻辑，过滤伪造包与裸连接洪水；握手校验前置到网关层，避免业务进程被未认证连接占满。③ **限流配额**——按账号/IP/设备维度令牌桶/漏桶限流，关键接口（登录/支付/领奖）单独配额；慢速连接设读写超时 + 单 IP 连接数上限，防慢速攻击耗尽连接池。④ **业务层过滤 + 降级**——异常请求特征（频率/分布）在网关拦截；攻击时非核心功能（排行榜/聊天/公告）降级或熔断，保住战斗/登录核心链路；弹性扩容应对尖峰。核心：**清洗 + 限流 + 协议前置认证 + 业务降级**多层叠加，单层都不够——堆带宽扛不住协议层洪水，只靠限流拦不住大流量。

**考点解析**：DDoS vs CC 的区别（流量洪水 vs 协议层/慢速）、多层纵深（清洗/限流/前置认证/降级）、协议前置认证的价值。资深要能讲清"为什么业务层做不了 DDoS 防护，必须前置"。

**常见误区**：以为堆带宽/机器就能扛（协议层攻击把连接数/状态表打爆，带宽没用）；限流只做账号维度不做 IP/设备（被分布式 IP 绕过）；未认证连接直接进业务逻辑（占满业务进程）；攻击时不降级，全链路一起崩。

**追问方向**：CC 慢速连接攻击（慢发慢收耗连接数）怎么识别和防？（连接级超时 + 单 IP 连接数上限 + 半连接数阈值；异常慢速连接在网关层踢除，不进业务层；必要时对可疑 IP 强制完整握手校验。）

### 【进阶】系统设计 · 账号与认证安全

> 账号盗取（撞库/拖库/会话劫持）怎么防？密码怎么存？Token 怎么管？

**参考思路**：① **密码存储**——用**慢哈希（bcrypt/argon2/scrypt）加盐**，argon2 为当前推荐；绝不明文、不用裸 MD5/SHA（彩虹表秒破）。② **防撞库**——登录限流（IP/账号维度）、连续失败锁定 + 验证码、异地/新设备登录二次验证；接入泄露密码库比对告警。③ **会话/Token**——登录下发会话 Token（JWT 或自研），**每次登录换 session id 防会话固定**；Token 有过期 + 刷新机制，泄露可吊销；全程 HTTPS 防中间人窃听。④ **多端登录与挤下线**——定义单端/多端策略，新登录挤旧会话时安全吊销旧 Token，防止旧会话长期挂留被劫持。⑤ **敏感操作二次验证**——改密/交易/解绑等敏感操作要二次校验（短信/TOTP/邮箱）。核心：账号安全是**密码慢哈希 + 撞库限流 + 会话动态/可吊销 + 敏感操作二次验证**的组合。

**考点解析**：慢哈希加盐（bcrypt/argon2）、会话固定/Token 刷新/吊销、撞库限流、多端挤下线、二次验证。资深要能讲清"为什么裸 MD5 不行、慢哈希防什么"。

**常见误区**：明文存或裸 MD5 存密码；登录不限制流（被撞库）；Token 永不过期/不可吊销；固定 session id（会话固定攻击）；敏感操作无二次验证。

**追问方向**：JWT vs 服务端 session 各自的取舍？（JWT 无状态、易水平扩展，但签发后难主动吊销（靠短过期+刷新+黑名单弥补）；服务端 session 可即时吊销但要集中存储、扩容复杂。游戏服务端通常规模可控、需要挤下线/封禁，session + Redis 存 Token 状态更常见。）

---

> **本章小结**：安全与反作弊的主线是"**服务端权威（客户端不可信）+ 协议安全（加密/防重放/防篡改，但只是辅助）+ 行为检测（统计/风控/重放校验）+ 服务端漏洞加固（注入/越权/逻辑）**"。记住三条铁律：**客户端永远不可信，影响真实结果的判定必在服务端**；**协议保密不持久，真正反作弊靠服务端权威 + 行为检测**；**反作弊是平衡的艺术——分层、渐进、综合、可申诉**。
