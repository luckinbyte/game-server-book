# 第18章 监控、运维与稳定性

> 代码写完只是开始——线上稳定运行才是考验。一次故障可能流失上万玩家，一次回滚可能损失真金白银。可观测性（指标/日志/追踪）、SLO 驱动、灰度发布、故障排查方法论、容灾演练——这些是把"能跑"变成"稳定可靠"的工程能力，是资深/主程岗的高频考点。

## 原理体系

### 1. 可观测性三支柱

线上系统的"眼睛"：
- **指标（metrics）**：聚合的数值时间序列（QPS、延迟分位 P50/P99、CPU、内存、错误率、在线人数）。擅长**告警与趋势**。用 Prometheus + Grafana 等。
- **日志（logs）**：离散事件的详细记录（请求日志、错误堆栈、关键操作）。擅长**根因定位**。要结构化（带 trace id/玩家 id/时间）+ 分级 + 集中收集（ELK/Loki）。
- **链路追踪（traces）**：一个请求穿过多个服务的完整调用链（每跳耗时）。擅长**跨服务定位慢/错**。OpenTelemetry/Jaeger。
三者互补：指标发现问题（告警）、日志/追踪定位根因。**带 trace id 串联**指标-日志-追踪是关键。

### 2. 关键指标

分层监控：
- **业务指标**：在线人数、登录成功率、匹配成功率、战斗完成率、付费——业务健康度的直接信号。
- **系统指标**：QPS、延迟分位（P50/P95/P99）、错误率、超时率。
- **资源指标**：CPU、内存、磁盘、网络、fd、连接数、GC 停顿。
- **依赖指标**：DB/Redis/下游服务的延迟与错误。
关注**长尾**（P99/P99.9）而非平均——平均好看但长尾差会毁玩家体验。

### 3. SLO / SLA / 错误预算

- **SLI（服务等级指标）**：可测量的信号（如"请求成功率"、"P99 延迟"）。
- **SLO（服务等级目标）**：对 SLI 的目标（如"成功率 99.9%""P99 < 50ms"）。
- **SLA（服务等级协议）**：对外承诺（违约赔偿），通常比 SLO 更宽松。
- **错误预算（error budget）**：SLO 允许的"出错额度"（如 99.9% 成功 = 每月允许 43 分钟错误）。错误预算用完则**冻结冒险变更、专注稳定**；预算充裕时可加速迭代。错误预算驱动"稳定性 vs 迭代速度"的平衡——不是无脑追求 100%，而是按 SLO 管控。

### 4. 告警体系

- **基于 SLO/阈值**：核心指标超阈值告警（错误率飙升、延迟突增、在线骤降）。
- **分级**：P0（立即处理，如服务不可用）、P1、P2——按严重度决定响应。
- **避免告警风暴**：合并相关告警、设持续时间阈值（短暂抖动不告）、收敛重复。
- **可操作性**：每个告警要有明确的"怎么处理"（runbook），避免告警来了不知道干啥。
- **避免漏报**：核心业务指标必须有告警覆盖（在线骤降、登录失败率）。
好告警：**少而准、可操作、分级**。坏告警：海量噪音、无动作、狼来了。

### 5. 故障排查方法论

线上故障排查的标准流程：
1. **确认影响**：哪些玩家/功能受影响、严重程度、是否在恶化（定 P0/P1）。
2. **止血优先**：先恢复服务（回滚、扩容、降级、切流量），再查根因——别在玩家掉血时慢慢 debug。
3. **定位根因**：用可观测性——指标看"什么时候开始坏"、日志/追踪看"坏在哪"、看变更记录（最近改了什么）。
4. **修复 + 验证**：修复根因、验证恢复。
5. **复盘**：根因/时间线/影响/改进项（5 why、防再发）。
关键纪律：**止血优先于查根因**；保留现场（截图/日志/核心转储）再操作；变更记录是定位的金钥匙（多数故障是变更引发）。

### 6. 灰度发布与回滚

- **灰度（canary）**：新版本先小流量（一个服/1% 玩家）验证，观察无异常再逐步放量。降低"全量翻车"风险。
- **回滚**：出问题能**快速回退**到上一版本。要求：版本可回滚（部署是可逆的）、数据兼容（新版本没写旧版本读不了的脏数据）、回滚快速（自动化，分钟级）。
- **金丝雀 vs 蓝绿**：金丝雀（小流量渐进）、蓝绿（两套环境切换）。游戏按服灰度常见。
铁律：**任何上线都要能回滚**；有破坏性变更（DB schema、协议不兼容）要特别小心（不可回滚的变更要分步、可验证）。

### 7. 混沌工程与容灾演练

- **混沌工程**：**主动注入故障**（杀进程、断网、延迟、CPU 打满）验证系统的容错与恢复能力，发现隐藏的单点/级联风险。Netflix Chaos Monkey 是代表。
- **容灾演练**：定期演练故障切换（主挂备顶、机房切换），验证容灾真的能工作（不演练的容灾等于没有）。
- **游戏化故障演练**：定期在测试服/低峰期注入故障，验证告警/降级/切换是否如预期。

### 8. 变更管理与 on-call

- **变更管理**：变更（代码/配置/扩缩容）是故障的头号来源。规范：变更评审、灰度、可回滚、变更记录（便于定位）、低峰期操作。
- **on-call**：值班响应故障。要有 runbook、escalation（升级路径）、postmortem 文化（无指责复盘，对事不对人）。
- **无指责复盘（blameless postmortem）**：故障复盘聚焦"系统为什么没挡住"而非"谁犯了错"——培养上报文化，否则问题被掩盖。

## 面试题

### 【专家】系统设计 · 可观测性

> 设计一个游戏服务端的可观测性体系。指标/日志/追踪怎么搭？

**参考思路**：三支柱：
- **指标**：Prometheus 采集 + Grafana 展示。业务（在线/登录率/匹配率/付费）、系统（QPS/延迟分位/错误率）、资源（CPU/内存/fd/GC）、依赖（DB/Redis 延迟）。
- **日志**：结构化（JSON，带 trace id/玩家 id/时间/级别），分级（ERROR/WARN/INFO），集中收集（ELK/Loki）。关键操作（交易/充值/掉落）必记。
- **链路追踪**：OpenTelemetry，请求入口生成 trace id，跨服务透传，记录每跳耗时。Jaeger 展示。
关键：**trace id 串联三者**——指标告警发现问题、用 trace id 在日志和追踪里定位根因。覆盖核心链路（登录/匹配/战斗/交易）。告警基于 SLO（错误率/延迟/在线骤降）。

**考点解析**：三支柱的职责与互补、trace id 串联、分层指标。资深要能设计完整的可观测闭环。

**常见误区**：只有日志无指标/追踪（定位难）；日志非结构化（无法检索）；无 trace id（跨服务断链）。

**追问方向**：可观测性本身会不会影响性能？（会——日志 IO、指标采集、追踪上报都有开销；按采样（追踪只采部分请求）、异步化、分级（核心链路详采、边缘粗采）控制。）

### 【专家】故障复盘 · 线上故障排查方法论

> 接到 P0 告警"玩家大面积登录失败"，你的排查流程？

**参考思路**：
1. **确认影响**：登录失败率多少、哪些服/玩家、何时开始、是否恶化、是否在影响新玩家进入。定级 P0，拉人。
2. **止血优先**：先恢复，别慢 debug——看最近变更（代码/配置/扩缩容），若是变更引发则**立即回滚**；若资源打满则**扩容/限流降级**；若依赖（DB/Redis）挂则切备用/重启。目标：尽快恢复服务。
3. **定位根因**（止血后或并行）：指标看"登录失败率何时飙升、关联什么"（DB 延迟？CPU 满？依赖错误？）；日志看失败请求的报错；追踪看登录链路卡在哪一跳；变更记录看最近改了什么。
4. **修复 + 验证**：修根因、验证登录恢复。
5. **复盘**：根因/时间线/影响范围/为何没更早发现/改进项（告警/熔断/回滚自动化）。
纪律：**止血优先、保留现场、变更记录是金钥匙、无指责复盘**。

**考点解析**：止血优先于查根因、用可观测性定位、变更记录、复盘改进。资深要能讲清"先恢复再查"的纪律。

**常见误区**：先慢慢 debug 不止血（玩家持续流失）；不查变更记录；无复盘（同类故障再发）。

**追问方向**：止血时回滚了，但故障依旧，说明什么？（不是这次变更引发，或变更引发了不可回滚的副作用（如 DB schema 已改/数据已写脏）——要进一步定位。）

### 【进阶】原理辨析 · SLO/SLA/错误预算

> SLO/SLA/错误预算是什么？错误预算怎么驱动发布节奏？

**参考思路**：SLI=可测信号（成功率/延迟），SLO=对 SLI 的目标（如 99.9% 成功），SLA=对外承诺（违约赔偿，比 SLO 宽）。**错误预算**=SLO 允许的出错额度（99.9% = 每月 ~43 分钟可错）。用法：① **驱动发布节奏**——错误预算充裕时可激进迭代（上新功能/冒险变更）；预算耗尽（最近故障多）则冻结冒险变更、专注稳定。② **量化稳定性 vs 迭代**的权衡——不是无脑追求 100%（成本无限），而是按 SLO 管控，把"稳定"变成可度量的预算。③ **告警基于错误预算消耗速率**（消耗过快提前预警）。核心：**把稳定性从"尽量不出事"变成"按预算管理"**。

**考点解析**：SLI/SLO/SLA/错误预算的定义、错误预算驱动发布节奏。资深要能讲清"稳定性是可度量的"。

**常见误区**：追求 100% 可用（成本无限、拖累迭代）；无 SLO（稳定性不可度量）；错误预算耗尽还激进上线。

**追问方向**：SLO 定多严合适？（按业务重要性——核心登录/战斗 SLO 严（99.95%+），边缘功能宽松（99%）；按用户期望与成本平衡，逐步收紧。）

### 【专家】系统设计 · 灰度发布与回滚

> 怎么设计灰度发布？怎么保证能快速回滚？

**参考思路**：
- **灰度（canary）**：新版本先小流量验证。游戏按服灰度——先一个服/少量服上新版本，观察一段时间（监控错误率/延迟/玩家反馈），无异常再逐批放量到全服。
- **回滚保障**：① 版本**可回滚**——部署是可逆的（保留旧版本镜像/包，一键切回）。② **数据兼容**——新版本不能写旧版本读不了的"脏数据"（DB schema 变更、协议变更要前向兼容，或分步：先让所有节点能读新格式、再写新格式）。③ **回滚自动化**——监控触发异常自动回滚（或一键人工），分钟级。④ **灰度期监控**——灰度服的关键指标与基线对比，异常即停。
铁律：**任何上线都要能回滚**；**破坏性变更（schema/协议）单独小心处理**——不可回滚的变更要分步、充分验证、低峰期。

**考点解析**：灰度渐进、回滚三保障（可回滚/数据兼容/自动化）、破坏性变更特殊处理。资深要能讲清"上线必可回滚"。

**常见误区**：直接全量上新版本（翻车全完）；写了不可回滚的数据格式；回滚靠手工（慢）。

**追问方向**：DB schema 变更（加列/改类型）怎么保证可回滚/不锁表？（加列给默认值/可空（前向兼容、可回滚）；改类型分步（先加新列、双写、迁移、切读、删旧）；大表变更用 pt-osc/gh-ost 在线 DDL 避免锁。）

### 【专家】故障复盘 · 一次重大故障复盘

> 讲一个你熟悉的服务端故障类型（如变更引发），怎么复盘改进？

**参考思路**（以"配置热更引发"为例）：
- **时间线**：14:00 热更了一个掉率配置（手误把 0.01 写成 1.0）→ 14:05 玩家疯狂刷稀有道具 → 14:10 经济监控告警 → 14:15 回滚配置 → 14:20 恢复。影响：5 分钟内刷出大量稀有道具，经济受冲击。
- **根因（5 why）**：为什么刷爆？掉率错。为什么错？手误 + 无校验。为什么没校验？配置热更流程缺校验。为什么没校验流程？热更未纳入变更管理。
- **改进**：① 配置**校验**（范围/引用/合理性，导出时强制）。② 热更**灰度**（先一个服）。③ 经济**监控告警**（稀有产出异常自动告警）。④ 热更纳入**变更管理**（评审/记录/可回滚）。⑤ 受影响玩家的**回收/补偿**。
- **文化**：无指责——聚焦"系统为什么没挡住"（缺校验/灰度/告警），而非"谁手误"。
复盘的价值在**防再发**（系统改进），而非追责。

**考点解析**：时间线/根因（5 why）/影响/改进/无指责文化。资深要能讲清"复盘是为防再发、改进系统"。

**常见误区**：复盘变追责（掩盖问题）；只修表面不查根因；无改进项跟踪。

**追问方向**：刷出的稀有道具已经流入玩家手里，怎么处理经济冲击？（评估规模——少量则容忍/回收，大量则回档（若可接受）或全服经济调整（贬值补偿）；根本是前置防（校验/灰度）避免发生。）

### 【进阶】权衡 · 告警阈值设计

> 告警阈值怎么定？怎么避免告警风暴和漏报？

**参考思路**：
- **基于 SLO**：核心指标（错误率、延迟、在线）告警阈值与 SLO 挂钩（如错误率 > 1% 持续 5 分钟）。
- **避免风暴**：① **持续时间阈值**——瞬时抖动不告，持续 N 分钟才告（过滤毛刺）。② **合并收敛**——相关告警合并（一次故障触发多个告警应聚合）。③ **分级**——P0/P1/P2，严重度决定响应，低级不半夜叫人。④ **去重/抑制**——同一问题短时间不重复告。
- **避免漏报**：① 核心**业务指标**必须覆盖（在线骤降、登录失败率、付费中断）。② 用"相对变化"告警（比基线骤降），不仅绝对阈值。③ 定期 review 告警（哪些从不响应该删、哪些漏了该加）。
好告警：**少而准、分级、可操作（带 runbook）**。告警的敌人是"狼来了"——噪音多导致真告警被忽视。

**考点解析**：SLO 挂钩、持续时间/合并/分级/去重防爆、业务覆盖防漏、定期 review。资深要能讲清"好告警少而准"。

**常见误区**：阈值拍脑袋；瞬时抖动也告（噪音）；无业务覆盖（漏报）；告警无 runbook（不知怎么处理）。

**追问方向**：告警太多团队疲劳（告警麻木），怎么改善？（砍噪音——删从不 actionable 的告警、调持续时间阈值、合并；确保每个告警都有明确动作；定期 review 告警质量。）资深级加分点：基于 SLO 的告警怎么做才不漏不噪？参考 Google SRE 的 **multi-window multi-burn-rate**——用快窗口（如 1h）+慢窗口（如 6h）组合按错误预算消耗速率告警（快燃快速止血、慢燃防长尾漂移），比"错误率>1%持续5分钟"的朴素阈值更贴合 SLO，且告警本身也要度量（actionable 率、MTTR、误报率）。

### 【专家】深挖追问 · 全链路追踪

> 全链路追踪怎么实现？怎么用它定位跨服务慢？

**参考思路**：① **trace id 透传**——请求入口（网关）生成唯一 trace id，随请求**跨服务透传**（RPC header/消息头），每跳记录 span（服务名 + 起止时间 + trace id）。② **收集展示**——各服务上报 span 到收集器（Jaeger/Tempo），按 trace id 串成完整调用链，可视化每跳耗时。③ **定位慢**——一个请求慢，看它的 trace：哪一跳耗时最长（是 DB 查？下游 RPC？自身计算？），针对性优化。④ **采样**——全量追踪开销大，通常采样（头部采样/尾部采样，错误/慢请求必采）。⑤ **串联日志**——日志带 trace id，追踪发现某跳慢后，用 trace id 查该请求的详细日志定位根因。全链路追踪是微服务/多服务架构定位慢/错的利器。

**考点解析**：trace id 透传、span 串联、采样、与日志配合。资深要能讲清"跨服务定位靠 trace id 串联"。

**常见误区**：无 trace id（跨服务断链）；全量追踪（开销大）；追踪与日志脱节（发现慢但查不到细节）。

**追问方向**：为什么不能全量追踪？（开销——每请求多跳、每跳上报 span，高 QPS 下上报量与 CPU/网络开销巨大；采样平衡覆盖与开销，错误/慢请求必采保根因可查。）

### 【进阶】原理辨析 · 混沌工程

> 什么是混沌工程？游戏服务端怎么做？

**参考思路**：混沌工程——**主动、可控地注入故障**（杀进程、断网、延迟、磁盘满、CPU 打满、依赖超时），验证系统是否如预期般容错与恢复，**发现隐藏的单点/级联/未覆盖的故障路径**。理念：与其等线上出事才发现系统脆弱，不如主动在受控环境"制造事故"暴露问题。Netflix Chaos Monkey 是代表（随机杀生产实例）。游戏实践：① 在**测试服/低峰期**注入故障（杀一个逻辑服、断 DB、延迟下游），验证：告警是否触发、降级/熔断是否生效、容灾切换是否工作、是否有单点拖垮全局。② 演练故障切换（主备切换、机房切换）验证容灾。③ 把发现的薄弱点改进。混沌工程把"假设的容灾"变成"验证过的容灾"。

**考点解析**：混沌工程的"主动注入验证"理念、发现隐藏风险、游戏实践（测试服注入+验证容灾）。资深要能讲清"不演练的容灾等于没有"。

**常见误区**：以为容灾设计好就行（不演练=未验证）；只在生产大规模注入（风险大，应渐进受控）；注入后不改进。

**追问方向**：混沌工程在游戏生产环境注入风险大，怎么平衡？（先测试服→灰度环境→小范围生产，渐进扩大；注入可控（能快速终止/回滚）；低峰期；有充分监控/告警/手动熔断保险。）

### 【专家】系统设计 · 容量与压测常态化

> 怎么发现系统的容量瓶颈？压测怎么做？

**参考思路**：① **压测**：模拟真实流量施压，阶梯加压找**拐点**（延迟非线性飙升处）与**单机承载**（SLO 约束下）。② **常态化**：不只在上线前压，定期压（架构变更后、流量增长后），跟踪容量变化。③ **全链路压测**：模拟真实流量穿过多服务，发现单点瓶颈与级联风险，比单服务压测更能反映真实。④ **关注长尾**：P99/P99.9，不只平均。⑤ **容量规划**：单机承载 × 机器数 × 余量（30-50%）= 集群容量，预留扩容缓冲。⑥ **瓶颈定位**：压测中用可观测性看 CPU/内存/IO/锁/网络/下游哪个先到瓶颈（见第 8 章）。⑦ **贴近真实**：生产容量数据要与真实流量分布匹配（压测环境 vs 生产的下游依赖、缓存命中率、数据量差异）。

**考点解析**：拐点/SLO 约束承载、常态化、全链路、容量规划、贴近真实。资深要能讲清"容量是测出来+规划出来的"。

**常见误区**：只上线前压一次（容量漂移无感知）；单服务压测（漏跨服务瓶颈）；压测环境与生产脱节（数据不准）。

**追问方向**：压测单机能扛 10k QPS，上线只到 6k 就慢，差在哪？（生产下游依赖、真实数据分布、缓存命中率、混部噪声、长尾——压测要贴近真实，否则高估容量。）

### 【进阶】故障复盘 · 变更引发故障

> 怎么设计一套变更管理流程，把变更引发的 P0 故障压到每年个位数？结合你的项目讲一次变更引发故障的根因与流程改进。

**参考思路**：统计上多数线上故障由**变更**（代码/配置/扩缩容/依赖升级）引发——系统稳定运行时不出事，一改就引入新变量。防范：① **变更评审**——重要变更需 review。② **灰度**——小流量验证再放量。③ **可回滚**——任何变更能快速回退（见上文）。④ **变更记录**——便于故障时快速定位"改了什么"。⑤ **低峰期操作**——降低影响。⑥ **变更窗口/冻结期**——重大节点（如活动期间）冻结非紧急变更。⑦ **自动化 + 预检**——部署前自动化测试、配置校验。⑧ **分步变更**——大变更拆成可验证可回滚的小步。核心：**把变更当作风险源，建立"评审-灰度-可回滚-记录-预检"的变更管理流程**。

**考点解析**：变更是头号故障源、变更管理流程（评审/灰度/可回滚/记录/窗口）。资深要能讲清"管好变更就管好了大半故障"。

**常见误区**：直接全量变更（无灰度）；变更不可回滚；无变更记录（故障时盲查）；活动期随意变更。

**追问方向**：紧急修复（hotfix）也要灰度吗？（也要——hotfix 虽急但同样可能引入新问题，至少小范围验证再放量；用"特性开关"快速关闭比回滚更快。）

### 【专家】权衡 · 稳定性与迭代速度的平衡

> 怎么平衡线上稳定性与业务迭代速度？

**参考思路**：靠**SLO + 错误预算**量化平衡：① 定 SLO（如 99.9% 可用）= 给定稳定性底线。② 错误预算（允许的出错额度）= 迭代空间。③ 预算充裕（近期稳定）→ 可激进迭代（上新功能、冒险变更）。④ 预算耗尽（近期故障多）→ 冻结冒险变更、专注稳定（修 bug、加固、降复杂度）。这样"稳定 vs 迭代"从口号变成**可度量的预算管理**——不是无脑追求 100%（拖累迭代、成本无限），也不是无脑冲速度（事故频发）。配套：灰度/回滚/可观测/变更管理降变更风险，让"冒险"可控。核心：**用错误预算把稳定性变成可消费的资源，按预算驱动节奏**。

**考点解析**：错误预算量化平衡、预算驱动节奏、配套手段降风险。资深要能讲清"稳定与迭代不是非此即彼，靠预算平衡"。

**常见误区**：无脑追求 100%（成本无限、迭代停滞）；无脑冲速度（事故频发）；无 SLO（无法量化权衡）。

**追问方向**：业务方强势要求上线一个风险较高的功能，但错误预算已紧，怎么应对？（用错误预算数据说话——预算紧说明系统已不稳，再冒险可能突破 SLO 影响所有玩家；建议先加固或等预算恢复，或只上低风险部分/带特性开关可快速关闭。用数据而非主观抗衡业务压力。）

---

> **本章小结**：监控运维的主线是"**可观测性（指标/日志/追踪 + trace id 串联）+ SLO/错误预算驱动 + 灰度/可回滚 + 故障排查方法论（止血优先）+ 变更管理 + 混沌验证容灾**"。记住三条铁律：**多数故障是变更引发的，管好变更就管好了大半故障**；**止血优先于查根因，先恢复再 debug**；**不演练的容灾等于没有，没 runbook 的告警等于噪音**。这套工程能力是把"能跑"变成"稳定可靠"的关键，也是资深/主程岗的标志。
