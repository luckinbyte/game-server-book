# 第19章 系统设计题集

> 系统设计是资深面试的"大题"——面试官给一个开放需求，看你怎么拆解、出方案、讲权衡、估瓶颈。这类题没有标准答案，考的是**工程思维的完整度**。本章把游戏服务端高频的系统设计题（背包/匹配/排行榜/跨服/聊天/网关/活动/存储）逐个做完整 walkthrough，培养"需求→方案→数据结构→瓶颈→扩展"的解题框架。

## 解题框架

拿到系统设计题，按这个框架展开（边讲边和面试官对齐）：
1. **澄清需求**：核心功能是什么？规模多大（玩家数/QPS）？一致性/延迟要求？别一上来就画架构。
2. **核心方案**：主流程怎么走、关键模块/服务划分。
3. **数据结构与存储**：用什么结构/库存、为什么。
4. **瓶颈与扩展**：热点在哪、怎么水平扩展、怎么容错。
5. **权衡与风险**：为什么这么选、有什么代价、什么场景会失效。
全程**讲清思路、暴露权衡、主动问规模**，比"给出唯一正确架构"更重要。

## 设计 1：背包系统

**需求**：玩家背包，支持增删改查、叠堆、扩容、排序；支持交易/合成涉及多道具原子操作。规模：单玩家数百~上千道具，全服百万玩家。

**规模估算**（把定性需求落到可量化约束）：单玩家均 500 道具、每条约 100 字节 → 单玩家 ~50KB；百万玩家 → 总存储 ~50GB（含索引/副本约百 GB 级）。读写 QPS：在线率约 10%（10 万在线），活跃玩家高频读（打开背包/排序）峰值 ~5k QPS、写（捡拾/合成/掉落）峰值 ~1k QPS；这量级单分片 MySQL + Redis 缓存即可支撑，关键约束在"单玩家串行 + 本地事务"而非总吞吐。

**核心方案**：
- **数据模型**：按玩家存道具列表，每条 = `{实例id, 配置id, 数量, 绑定, 位置}`。可叠道具记数量合并占格；不可叠（装备）每件独占（实例 id 唯一）。
- **存储**：玩家背包数据聚合同一存储分区（玩家 id 分片），保证玩家内操作本地事务。MongoDB（灵活/嵌套）或 MySQL（结构化）皆可，按团队栈选。
- **事务性**：增删改（尤其合成/交易/掉落涉及多道具）在一个**本地 DB 事务**里完成，配合操作流水审计。
- **并发**：同一玩家的操作**串行化**（按玩家 id 路由到固定逻辑线程/分片），避免并发竞态刷道具。

**瓶颈与扩展**：道具多时同步给客户端只发**变化 delta**（初次全量、之后增量）；按类型/页懒加载。跨玩家交易涉及双方 → 路由到同一分片做本地事务，避免分布式事务。

**常见追问**：叠堆上限怎么处理（超了占新格）？唯一道具怎么保证（实例 id + 校验）？道具操作怎么防并发刷（玩家级串行）？

## 设计 2：匹配系统

**需求**：5v5 竞技匹配，公平 + 合理等待。规模：百万玩家在线，每秒数千匹配请求。

**核心方案**：
- **实力分**：ELO/MMR，胜负动态调整。
- **匹配池**：按模式/段位分池，待匹配玩家进池（Redis 有序集合按 MMR 排，或内存匹配引擎）。
- **扩窗策略**：进池时严格按 MMR 范围找；超时逐步放宽（每 10s 放宽 100 分），平衡公平与等待。
- **组队**：取队伍平均 MMR + 人数权重（优先队伍 vs 队伍）。
- **凑局**：从池里选 MMR 接近的凑齐人数，分配到战斗服。

**瓶颈与扩展**：匹配池大时查找要高效（按 MMR 分桶/有序结构）；匹配是有状态（stateful）服务（池状态），按模式分片到多个匹配服；高峰期预扩战斗服。深夜池空时扩窗到全局/补 AI。

**常见追问**：怎么防连胜连败保护？组队匹配公平性？匹配等待时长怎么监控与调参？匹配服务单点/分片宕机时池里待匹配玩家怎么恢复（状态持久化 + 超时回流重新入池）？车队权重怎么防高 MMR 带低 MMR 炸鱼（按队伍最高/加权 MMR 而非纯均值）？匹配公平性怎么离线度量（对局胜率方差、平均时长、等待时长分布）？

## 设计 3：排行榜

**需求**：千万玩家、分数频繁变动、实时查名次与前 N、查自己名次。

**规模估算**：千万玩家单 ZSET，每成员约 80 字节（member + score）→ ~800MB 内存；分 16 段位 ZSET 后单分片 ~50MB。写 QPS：高峰每秒分数变动（结算/对战）约数万 → 批量攒批 + 管道降到 Redis ~数千 pipelined ZADD，单实例可扛；查前 N（ZREVRANGE）与查名次（ZREVRANK）峰值 ~万级 QPS，热 key（榜首）需多副本/本地缓存挡。

**核心方案**：
- **Redis ZSET**：`ZADD` 更新分数（O(log n)）、`ZREVRANGE` 取前 N（O(log n+N)）、`ZREVRANK` 查名次（O(log n)）。
- **分段/分片**：千万级单 ZSET 内存/性能吃紧，按段位或区间分多个 ZSET。
- **精确前列 + 近似尾部**：前列（前千/前 1%）实时精确；尾部定时快照近似；查自己名次在尾部用估算（分数→桶号→累计桶计数估算名次的桶计数法）。
- **批量写**：玩家分数变化先内存累加、周期批量 ZADD，减少 Redis 写压力。

**瓶颈与扩展**：千万级单 ZSET 内存 → 分片；写频繁 → 批量 + 管道；查自己名次百万名外 → 估算。

**常见追问**：赛季结算重置怎么高效？多维度排行（金币/战力/胜场）？实时性 vs 成本怎么平衡？Redis 主从切换/ZSET 持久化（RDB/AOF）期间排行实时性怎么降级（读副本 + 标记陈旧 + 故障转移后对账重算）？合并服排行/赛季切换瞬间写入尖峰怎么削（分时段切换、异步迁移、双 ZSET 切换）？

## 设计 4：跨服战场

**需求**：玩家从各服进入同一跨服战场，结束后回本服，结果正确回流。规模：多服、万级并发对局。

**核心方案**：
- **借出/回流模型**：① 本服收到匹配成功 → 把玩家**状态快照**发跨服进程，本服标记"跨服中"。② 跨服加载快照跑战场。③ 结束，跨服把**结果**（胜负/奖励/消耗）可靠发回本服。④ 本服**原子 + 幂等**应用结果，解除标记。
- **可靠回流**：结果走持久化消息队列 + 确认 + 重试，不丢。
- **幂等**：本服按唯一战斗 id 去重，重复消息不重复发奖。
- **崩溃恢复**：跨服持久化战场状态；本服持久化"跨服中"标记 + 战场 id，重启后等待/查询结果。
- **同步**：跨服战场内用帧同步或状态同步（按品类），见第 9 章。

**瓶颈与扩展**：跨服进程按对局分配 + 弹性扩缩容；跨服进程崩溃不丢玩家进度（持久化 + 恢复/补偿）。

**常见追问**：跨服中本服重启怎么办（标记 + 战场 id 待恢复）？结果回流丢失怎么办（可靠消息 + 对账）？玩家掉线重连回战场（按战场 id 重连跨服）？

## 设计 5：聊天系统

**需求**：世界/公会/私聊/队伍/附近频道，敏感词过滤，百万在线。

**核心方案**：
- **频道模型**：每条消息带频道 + 目标。私聊按玩家 id 路由；公会/队伍按群 id 广播。
- **世界频道（放大器）**：分线路由（玩家按 id 哈希固定分到某条世界频道线路、跨线不可见，发言只广播本线）+ 限频（每人发言间隔）+ 聚合（合并下发）。**不能裸广播全服**。
- **敏感词**：AC 自动机一次扫描匹配所有敏感词（O(n)）+ 变体处理（谐音/拆字）+ 人工审核兜底。
- **离线消息**：私聊对方不在线时存离线消息，上线推送。
- **记录**：聊天记录存证（审计/举报），定期按策略清理。

**瓶颈与扩展**：世界广播放大 → 分线/限频/聚合；敏感词库大 → 双数组 trie 压缩 + 增量构建。

**常见追问**：怎么防刷屏（限频 + 举报 + 风控）？跨服/跨区聊天怎么做（跨服聚合服务）？敏感词变体怎么处理（谐音/拼音、全角半角、零宽字符、unicode 同形字、emoji 注入等绕过手段 → 归一化前置（拼音转写 + 全角转半角 + 去零宽字符）后再过 AC 自动机 + 模糊匹配兜底 + 人工）？

## 设计 6：网关

**需求**：维持海量客户端长连接、加解密、限流、按玩家路由到逻辑服。规模：单机十万~百万连接。

**核心方案**：
- **IO 模型**：epoll + ET/LT + 主从 Reactor（main accept、sub IO），或 asio；one loop per thread 避免锁（见第 5 章）。
- **多核扩展**：SO_REUSEPORT 多 worker 各自 accept，内核负载均衡，无惊群。
- **协程/线程**：每连接一协程或 IO 线程池 + 业务投递逻辑线程。
- **路由**：按玩家 id（一致性哈希）路由到对应逻辑服分片。
- **职责边界**：网关只做连接/加解密/限流/路由，**不做业务逻辑**（无业务状态、加机器易扩展；但持有海量长连接会话——连接态/session/token 缓存属连接状态，单机故障会丢失其上连接）。
- **防刷/安全**：限流（IP/账号/连接数）、token 鉴权、加密、防重放。

**瓶颈与扩展**：连接数 → epoll+REUSEPORT+协程；无业务状态 → 加机器 + 负载均衡；连接态迁移有代价（单机宕机触发其上连接重连、需 graceful shutdown 排空连接 + 客户端退避重连防重连风暴）；连接内存 → 共享 buffer、精简每连接上下文。

**常见追问**：百万连接的心跳超时怎么高效（时间轮批量检测）？网关单点怎么办（多网关 + 客户端重连 + 负载均衡）？网关与逻辑服断开怎么办（重连 + 玩家会话保持）？

## 设计 7：限时活动系统

**需求**：限时活动整点开启、海量玩家涌入、限量奖励先到先得、配置化运营自助。

**核心方案**：
- **配置驱动**：活动/奖励/规则配置化，运营自助开/关/调，热加载（见第 12、13 章）。
- **削峰**：客户端**错峰**进入（按账号/区服错开）、排队；网关限流；非核心降级。
- **限量奖励防超发**：原子扣减库存（Redis DECR/Lua 原子），库存预扣 + 失败回退；**不能"查库存>0 再发"两步非原子**。
- **Redis 库存与 DB 对账/兜底**：Redis 库存为热路径权威，但需周期/活动结束时与 DB 落库库存对账；Redis 宕机丢库存时按 DB 已发放记录 + 发奖流水反推剩余库存并回补，防止少发/超发。
- **预扣 + 异步落库的崩溃回补**：领奖走"预扣 Redis 库存 → 异步落库发奖"路径，若领奖进程在预扣后、落库前崩溃，需定时扫预扣单据超时回补库存（预扣单据持久化或可重建）。
- **分片库存 vs 全局库存**：高并发下单一 Redis 库存 key 是热点；可按玩家 id/区服把库存拆多分片（各自 DECR 原子），代价是"先到先得"在全量层面退化为"分片内先到先得"且需防分片间局部超发（分片预留 + 动态借调 + 超发兜底回收）。
- **预热 + 扩容**：活动前预热缓存、预扩逻辑服/跨服进程。
- **异步化**：领奖/报名非即时操作异步处理 + 排队。

**瓶颈与扩展**：开启洪峰 → 错峰/排队/限流；限量抢 → 原子库存；配置 → 数据驱动 + 灰度。

**常见追问**：限量奖励库存放哪（Redis 原子 + 持久化兜底）？活动期间某服宕机怎么办（容灾 + 活动状态可恢复）？活动数据怎么结算（对账 + 持久化）？

## 设计 8：玩家数据存储方案

**需求**：玩家档案/背包/货币/社交/战斗记录的存储选型与分层。规模：百万玩家，热数据高频读写。

**核心方案**（按数据特征分层，见第 7、12 章）：
- **账号/账务**（强一致、强事务）→ **MySQL**。
- **玩家档案/背包**（灵活 schema、嵌套、频繁演进）→ **MongoDB**（或 MySQL JSON）。按玩家 id 分片，聚合同分区（玩家内本地事务）。
- **热数据**（在线状态、实时分数、会话）→ **Redis**（低延迟、高频读写）。
- **排行榜** → Redis ZSET。
- **战斗/日志** → MongoDB / 专用日志系统（ES）。
- **关系链/社交** → MySQL 关系表 + Redis 邻接表为主流（好友/公会/师徒），图数据库仅在多跳关系深度查询等特殊场景可选。
- **分层原则**：强一致用关系库、灵活/热数据用文档/KV；**强一致区（货币/账务走 MySQL 事务）与最终一致区（社交/排行/缓存态）显式划界**；玩家内强相关数据聚合（本地事务），跨玩家/全局数据按功能拆。

**瓶颈与扩展**：MySQL 分库分表（玩家 id 分片）+ 读写分离；Redis 集群 + 哨兵/Cluster；缓存穿透/击穿/雪崩防护（见第 7 章）。

**常见追问**：玩家上线怎么热数据（按需加载 + 缓存回填 + 下线脏写回）？数据回档怎么防（关键操作即时持久化 + WAL，见第 12 章）？分片键怎么选（玩家 id，保证局部性）？

---

> **本章小结**：系统设计题的胜势在**框架完整 + 权衡清晰 + 主动问规模**，不在唯一正确答案。记住：**先澄清需求再画架构**；**按数据特征选存储、按访问模式选结构**；**有状态分片、无状态扩展、热点单独拆**；**任何方案都要讲清瓶颈与扩展路径**。这八道题覆盖了游戏服务端最高频的设计场景，把每道的"需求→方案→瓶颈→追问"吃透，系统设计题就稳了。
