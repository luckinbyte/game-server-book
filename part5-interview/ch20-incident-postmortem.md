# 第20章 场景与故障复盘题

> "线上 CPU 飙到 100%，怎么办？""内存一直涨，查不到泄漏，怎么办？"——故障复盘题考的是**真实线上排障能力**：从现象出发，系统化地定位根因、止血、修复、防再发。本章把游戏服务端高频故障场景逐一拆解，给出**现象 → 可能原因 → 排查步骤 → 修复 → 预防**的完整链路。这类题的回答质量，直接区分"只会写代码"与"能扛线上"。

## 解题框架

故障复盘题按这个框架答：
1. **确认现象与影响**：什么坏了、影响谁、是否在恶化（定级）。
2. **列举可能原因**：系统性列出根因族（不是猜一个），体现知识广度。
3. **止血优先**：先恢复（回滚/扩容/降级/切流量），再查根因。
4. **定位手段**：用什么工具/指标定位（top/perf/pprof/日志/追踪/变更记录）。
5. **修复 + 预防**：修根因 + 加监控/熔断/演练防再发。
**列举多个可能原因 + 用工具逐一验证**，比直接报一个答案更显资深。

## 故障 1：线上 CPU 飙高

**现象**：服务 CPU 持续 90%+，响应变慢。

**可能原因**：① 死循环/忙等；② 热点函数被海量调用；③ GC/内存分配过频（Lua/Go）；④ 锁自旋（高竞争）；⑤ 正则/序列化等"隐藏昂贵"操作；⑥ 业务量真实上涨（活动/玩家增多）。

**排查**：① `top -Hp <pid>` 找占 CPU 最高的**线程**；② `perf record -p <pid> -g` 采样 + 火焰图，看 CPU 花在哪个调用栈；③ 火焰图找最宽的平台（自耗时大的函数）；④ 若是 GC，看 GC 日志/频率；若是锁，看锁等待；⑤ Go 服务用 `go tool pprof` 抓 CPU profile + 火焰图，Lua/Skynet 用各自的 trace 工具（与故障 11 的 pprof 思路一致）。

**止血**：扩容（CPU 真不够）、限流降级（挡住流量）、回滚（变更引发）。

**修复+预防**：优化热点（算法/cache/批处理，见第 8 章）；加 CPU 监控告警；压测提前发现。

---

## 故障 2：内存持续增长 / 疑似泄漏

**现象**：RSS 持续上涨，ASan/valgrind 未报泄漏。

**可能原因**（区分泄漏 vs 高水位，见第 2、8 章）：① 真泄漏（忘了释放/循环引用）；② **内存碎片**（malloc 拿不回还给 OS）；③ **arena 未 reset**；④ **make_shared 单块内存因 weak_ptr 未释放而无法回收**（对象已析构，但内存块被 control block 钉住，属"高水位"而非泄漏对象）；⑤ 容器只增不减；⑥ 缓存无淘汰；⑦ 对象池预分配过大。

**排查**：① `/proc/<pid>/smaps` 看 RSS 构成；② `malloc_trim(0)` 试探（回落则碎片）；③ 换 jemalloc/tcmalloc 对比（消失则碎片）；④ 给关键容器/缓存加大小监控；⑤ jemalloc `malloc_stats_print`；⑥ Go 用 pprof heap，C++ 用 ASan/tcmalloc heap profiler。

**止血**：定期重启（临时）、扩内存、限流降负载。

**修复+预防**：修真泄漏；治碎片（换分配器/对象池）；缓存加 LRU 上限；arena 确保 reset；内存增长监控告警。

---

## 故障 3：偶发卡顿（长尾延迟）

**现象**：平均延迟正常，P99 偶发飙升，玩家感觉卡。

**可能原因**（见第 8 章）：① GC 停顿；② IO 抖动（磁盘/网络毛刺）；③ 锁竞争偶发阻塞；④ cache miss 突发/冷数据；⑤ 定时任务/日志 flush 偶发占用；⑥ 邻居噪声（同机其他进程抢资源）。

**排查**：① **全链路追踪**看慢请求卡哪一跳；② 偶发长尾别靠 on-CPU 采样（单次毛刺在火焰图几乎不可见）——Go 用 `runtime/trace` + 调度延迟指标抓毛刺时刻，C++ 用 off-CPU 火焰图（perf sched / bpftrace）定位阻塞源头；③ GC 日志、IO wait、锁等待指标；④ 关注 P99/P99.9 不看均值。**关键：卡顿是间歇的，靠持续监控 + off-CPU/调度追踪 + 抓现场**。

**止血**：降负载、降级非核心。

**修复+预防**：调 GC（降 GOGC、sync.Pool）；IO 异步化/批处理；缩小临界区；隔离噪声（独占/绑核）；长尾监控告警。

## 故障 4：服务雪崩

**现象**：一个下游服务变慢，上游线程池耗尽，连锁拖垮所有依赖它的服务，全局不可用。

**根因**：下游慢 → 上游调它的请求堆积在线程池 → 线程池满 → 上游也无法响应 → 向上蔓延。没有熔断保护。注意模型差异：阻塞线程池模型下表现为"线程池打满"；异步/协程模型（Go/Actor）没有传统线程池，雪崩表现为**背压缺失 + 协程/请求内存与连接堆积 + 协程数暴涨**，熔断点也不同（按内存/协程水位而非线程数）。

**排查**：看调用链哪个下游延迟飙升/错误率高；阻塞模型看线程池/连接池水位，协程模型看 goroutine/协程数、内存、在途请求数；级联故障时间线。

**止血**：**熔断**异常下游（快速失败，不再调用，让上游线程释放）、降级（返回默认/缓存）、扩容上游。

**修复+预防**：每个下游调用都加**超时 + 熔断**（见第 15 章）；线程池/连接池隔离（不同下游不共享）；限流；混沌演练验证熔断生效。

---

## 故障 5：脑裂

**现象**：主备集群网络分区，两侧各选出一个主，双主写入导致数据分叉冲突。

**根因**：网络分区 + 无多数派/fencing 保护（见第 15 章）。

**排查**：看是否有分区（两个主同时活跃）、数据是否分叉（两侧数据不一致）。

**止血**：强制其中一个主降级、合并/修复分叉数据（可能需人工介入，按业务定）。

**修复+预防**：用**多数派（quorum）**选主（Raft/Paxos，少数派无法选主）；新主上任前 **fencing** 旧主（租约过期/STONITH）；脑裂监控告警。

---

## 故障 6：数据不一致 / 回档

**现象**：玩家充值/打到的装备丢失，或跨服结果没生效，或重复发放。

**可能原因**（见第 12、15 章）：① 跨服结果回流丢失/重复；② 应用非幂等（重复发奖）；③ 内存改了没落 DB 就崩了；④ 事务未真正提交；⑤ 异步落盘未刷。

**排查**：① 消息链路追溯（跨服结果是否发/收/处理）；② 幂等检查（是否按唯一 id 去重）；③ DB 事务/日志确认是否提交；④ WAL/流水对账。

**止血**：人工补偿（补发/扣回）、回滚（若可）。

**修复+预防**：可靠消息 + 幂等 + 对账（跨服最终一致三件套）；高价值操作即时持久化 + WAL；事务确认后才回客户端成功；支付/发奖幂等。

---

## 故障 7：连接数暴涨 / 句柄耗尽

**现象**：`accept` 失败、新玩家连不上，进程 fd 或 ESTABLISHED 连接数很高。

**可能原因**（见第 5 章）：① 进程 fd 上限（连接/文件泄漏）；② ESTABLISHED 堆积（建连不处理/不关）；③ **出向连接端口耗尽**（服务端连 DB/Redis/下游服务，TIME_WAIT 堆积占满本地临时端口）；④ accept 队列满（处理不过来被 RST）。

**排查**：① `ls /proc/<pid>/fd | wc -l` vs `ulimit -n`（fd 上限）；② `ss -s`/`netstat` 看连接分布（哪类滞留）；③ `ss -lnt` 看 accept 队列积压；④ 看是 socket/file/pipe 哪类泄漏。

**止血**：提 fd 上限（临时 ulimit）、重启泄漏进程、扩容。

**修复+预防**：修连接泄漏（RAII 管理连接、配对 open/close）；提 fd 上限（持久配置）；连接数监控告警。

---

## 故障 8：慢查询拖垮 DB

**现象**：接口越来越慢，DB CPU/连接数高，疑似 SQL 慢查询。

**排查**（见第 7 章）：① 慢查询日志抓慢 SQL；② `EXPLAIN` 看 type（ALL 全表扫？）、key（NULL 没走索引？）、rows、Extra（filesort/temporary）；③ 索引失效场景（函数操作列、隐式转换、LIKE '%x'、OR 部分无索引、违反最左前缀）。

**止血**：杀慢查询、加索引、限流降负载、读从库分流。

**修复+预防**：加合适索引（覆盖索引避免回表）、改写查询避免索引失效；慢查询监控告警；DB 连接池/超时保护防拖垮。

---

## 故障 9：缓存击穿 / 雪崩

**现象**：Redis 某热点 key 过期瞬间 DB 被打爆（击穿）；或大量 key 同时过期/Redis 宕机，请求全压 DB（雪崩）。

**区分**（见第 7 章）：击穿=单热点失效；雪崩=批量失效/整体宕；穿透=查不存在的数据穿到 DB。

**止血**：限流降级保 DB、重启/切换 Redis。

**修复+预防**：击穿——热点 key 永不过期 + 异步刷新、或互斥回源；雪崩——过期时间加随机抖动、多级缓存、Redis 高可用、限流兜底；穿透——布隆过滤器/缓存 null。

---

## 故障 10：帧同步 desync

**现象**：帧同步游戏各客户端结果不一致（玩家各自看到不同世界）。

**可能原因**（见第 9 章）：① 浮点不一致（未用定点数 / 浮点舍入模式 FPCR·MXCSR 不一致 / 跨架构 x86 与 ARM 浮点实现差异 / `-ffast-math` 等破坏 IEEE754 确定性的优化 flag）；② 随机数不一致（各自 rand）；③ 容器迭代序不一致（无序容器）；④ 依赖系统时间/不确定 API；⑤ 编译器/优化差异。

**排查**：① 每帧算**状态哈希**各端 + 服务端比对，定位**分歧帧**；② 从最近一致帧到分歧帧**二分重放**，找第一个分叉的操作；③ 对比该帧各端的输入、随机序列、浮点中间值。

**修复+预防**：定点数、统一 PRNG + 种子、有序容器遍历、锁编译环境；CI 多端重放比对哈希；desync 检测 + 上报。

---

## 故障 11：goroutine / 线程泄漏

**现象**：Go 服务 goroutine 数或线程数持续增长，内存/FD 跟涨。

**可能原因**：① goroutine 卡在 channel（向无人接收的 channel 发送、等不到的接收）；② context 未传导致协程不退出；③ 循环里 `go func` 但 func 永久阻塞；④ `time.After` 在循环里累积。

**排查**：① `net/http/pprof` 的 `/debug/pprof/goroutine?debug=2` 看每个 goroutine 完整栈；② `go tool pprof` 按调用栈聚合，找"只增不减"的那批卡哪。

**止血**：重启泄漏进程、扩容。

**修复+预防**：每个 goroutine 都有退出路径（context 取消、channel close、select 带超时）；goroutine 数监控告警；vet/lint 检查未 close 的 channel。

---

## 故障 12：变更引发故障

**现象**：一次发布/配置热更后，线上出问题。

**根因**：变更是故障头号来源（见第 18 章）——代码 bug、配置错误、不兼容变更。

**排查**：① 看**变更记录**（最近改了什么）——这是金钥匙；② 回滚验证（回滚后恢复 = 变更引发）。

**止血**：**立即回滚**（最快恢复）；不可回滚的（DB schema 已改）则热修/补偿。

**修复+预防**：变更管理（评审/灰度/可回滚/记录/窗口）；配置校验 + 灰度；DB schema 分步兼容变更；变更引发故障的复盘改进流程。

---

## 故障 13：死锁 / 互锁卡死

**现象**：部分玩家/逻辑卡住不动（请求无响应），CPU 反而下降（线程阻塞不再干活），但进程没崩。

**可能原因**：① **锁顺序反转**——跨玩家操作 A→B 加锁 vs 另一处 B→A 加锁导致互锁；② **持锁回调**（锁内调用外部/用户回调，回调里又取锁）；③ **锁内阻塞 IO/睡眠**（持锁等网络/磁盘，被等者又要取该锁）；④ **读写锁写者饥饿**；⑤ 分布式锁租约过期但本地仍持锁（与脑裂同源）。

**排查**：① C++ 用 `gdb` `thread apply all bt` 一次打全所有线程栈，找两个线程互相等对方持有的锁；② Go 用 pprof mutex profile + goroutine full stack 找互锁对；③ 锁竞争/等待指标（mutex wait、off-CPU 看阻塞）；④ 分布式锁看租约 TTL 与心跳。

**止血**：重启卡死实例（最快恢复），切流量到健康节点。

**修复+预防**：**统一全局锁顺序**（按对象 id 升序加锁，杜绝反转）；锁内绝不回调/IO，回调/IO 移出临界区；用 `std::lock`/层次锁（hierarchical mutex）等工具在编码期约束顺序；锁顺序检测工具（TSan/lock-order checker）；死锁监控（线程长时间阻塞告警）+ CHAOS 演练。

## 故障 14：写放大 / 磁盘满 / 落盘失败

**现象**：服务突然写 DB/日志/WAL 失败，或整盘打满后所有写入拒绝，开服/活动高峰尤甚。

**可能原因**：① **写放大**——一次逻辑写触发多次物理写（DB 刷脏页、WAL + 数据双写、索引/触发器连锁、SSD 放大系数）；② 日志无轮转/级别过低，高峰打爆磁盘；③ DB/WAL 持久化策略过激进（fsync 频率/全量刷盘）；④ 临时表/快照/备份占满；⑤ 监控/采集 agent 自身写大日志。

**排查**：① `df -h` 看盘水位，`du` 找最大目录（是 DB 数据、WAL、还是日志？）；② DB 看 `pg_stat_bgwriter`/InnoDB buffer pool 刷脏速率、WAL 增长曲线；③ 日志看写入速率与轮转是否生效；④ 业务侧找突发写量源头（活动/批量任务）。

**止血**：清日志/旧备份腾空间、日志降级（DEBUG→WARN）、关非核心写入、扩盘。

**修复+预防**：磁盘水位告警（85%/90%/95% 多级）；日志轮转 + 限流 + 分级；DB 调刷盘策略（写放大 vs 持久性的权衡）；WAL/归档定期清理；写放大压测；落盘失败要有降级路径（写本地队列延后回放，而非直接拒绝业务）。

---

> **本章小结**：故障复盘题的胜势在**系统化列举原因 + 用工具逐一验证 + 止血优先**，不在一击命中根因。记住四条铁律：**先列举多个可能原因，别只猜一个**；**止血优先于查根因，先恢复再 debug**；**变更记录是定位的金钥匙，多数故障是变更引发**；**修复要配预防（监控/熔断/演练），否则同类故障再发**。把每个故障的"现象→原因族→排查→止血→预防"吃透，线上排障能力就到位了。
